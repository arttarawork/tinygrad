Off master `7ca254099` (T4.40c's PR #6 merge). Three independent, small, GPU-free fixes flagged by
earlier tasks and left unfixed at the time: two from T4.42 (`T4.42_NOTES.md` §3b/§5, commit

## 1. Write-short deadlock (`tinygrad/device.py`)

**Bug.** `Compiler.compile_server`'s outbound write —
`unwrap(proc.stdin).write(struct.pack("I", len(src.encode())) + src.encode())` — discarded `.write()`'s
return value. `proc.stdin` is opened `bufsize=0` (raw, unbuffered), and per Python's own subprocess docs
a raw stream's `.write()` "can return short" on a single call. T4.42 traced the consequence in full: the
server side (`compileserver.py`'s `sys.stdin.buffer.read(n)`, a `BufferedReader`) blocks until it
assembles exactly `n` bytes, so a truncated client write leaves the server blocked waiting for bytes that
will never arrive, while the client has already moved on to *reading* a reply that will never come. Round
trip deadlocks; nothing is ever cached (a hang, not corruption) — but a real `DEV=NV` OSX-docker run on a
large kernel source could wedge indefinitely with no diagnostic.

**Fix.** `_write_exactly(f, data)`, the mirror of `_read_exactly`: loop `f.write(data)` until `data` is
fully sent. Two edge cases, both deliberate: `write()` returning `0` while data remains pending raises
`CompileError` (mirrors `_read_exactly` treating EOF as terminal — a real blocking pipe should never
sit at 0 with data still writable, so this is a safety valve, not an expected path); `write()` returning
`None` is treated as "fully sent" rather than raised on, because `None` is only a non-blocking-stream
convention (irrelevant to this blocking pipe) and several existing test doubles in `test/null/test_device.py`
(`_FakeCompileProc.write`, out of this task's touched scope) return `None` as a "didn't bother reporting a
count" stub — treating it as terminal would have broken those tests' write path before ever reaching what
they're actually testing (the read side). Single call site changed: `compile_server`'s write line now
calls `_write_exactly`. `compile_server` is shared by both the CUDA (OSX docker) and QCOM transports
(`compiler_qcom.py:35` also calls it), so both benefit without a QCOM-side change.

**Test** (`test/unit/test_compiler_cuda.py::TestCompileServerWrite`): `_ShortWriteProc`, a fake pipe whose
`write()` accepts at most `chunk` bytes/call and records everything actually delivered (`.written`,
`.write_calls`); its `read()` returns a canned reply unconditionally, so the test never risks the real
deadlock the bug causes — it isolates the write loop's correctness instead. `test_short_write_delivers_every_byte`
(chunk=7 against a 5000-byte source): asserts `proc.written == expected_wire`. `test_full_single_write_unchanged`
(negative control, chunk=10_000, healthy one-shot write): asserts identical output AND `write_calls == 1`,
pinning that the common case still takes exactly one syscall, not spurious looping.

**Proven failing pre-fix**: `git stash` on `device.py` alone → `test_short_write_delivers_every_byte` fails
(`proc.written` is 7 bytes of the 5004-byte message); `test_full_single_write_unchanged` still passes
(the healthy path was never broken — correct negative control). Both pass with the fix restored.

## 2. Retry leaks the evicted process (`tinygrad/runtime/support/compiler_cuda.py`)

**Bug.** `_compile_with_retry`, on `CompileTransportError`, did `_server_cache.pop((type(compiler).__name__,
arch, args), None)` and discarded the return value — the dead `Popen` object was never `kill()`/`wait()`-ed.
T4.42 §4 flagged this as real: if the process is still alive at the OS level when the transport dies (docker
CLI client up, container inside it dead; or a pipe-level-only death), it leaks until `atexit`'s
`_reap_servers` finally runs at interpreter exit.

**Fix.** Capture the popped value; if not `None`, reap it before respawning: `if dead.poll() is None:
dead.kill()` (guarded — killing an already-exited pid can raise `ProcessLookupError`, mirroring the exact
guard `_reap_servers` already uses two functions above), then unconditionally `dead.wait()` (reaps even a
process that died on its own, avoiding a zombie either way).

**Test** (`test/unit/test_compiler_cuda.py::TestCompileWithRetry`, extends the existing `_FakeProc` with
`.wait()` plus `killed`/`waited` tracking flags — purely additive, doesn't affect the 3 pre-existing
`TestServerCache` tests or the 3 pre-existing `TestCompileWithRetry` tests): `test_evicted_process_is_reaped_on_retry`
(still-alive case) asserts both `killed` and `waited` end up `True`. `test_already_dead_evicted_process_is_still_reaped_not_double_killed`
(process died on its own — `poll() != None`) asserts `killed` stays `False` (no kill on a reclaimed pid)
while `waited` is still `True` (still reaped).

**Proven failing pre-fix**: `git stash` on `compiler_cuda.py` alone → both new tests fail (`killed`/`waited`
never set, since the pre-fix code drops the popped proc on the floor); the 3 pre-existing tests
(`test_succeeds_first_try_no_respawn`, `test_retries_once_on_transport_error`,
`test_does_not_retry_or_respawn_on_genuine_compile_error`) are unaffected — negative control.

## 3. `wait_cond` raises `UnboundLocalError` instead of `TimeoutError` (`tinygrad/helpers.py`)

**Bug.** `while int(time.perf_counter()*1000) - start_time < timeout_ms: if (val:=cb(*args))==value: return val`
checks the deadline *before* calling `cb`. If the deadline has already elapsed by the time that first
check runs (a `timeout_ms` small enough that a slow first call already blew it, or — as T4.40c hit — a
clock/scheduling hiccup), the loop body never executes, `val` is never assigned, and the `raise
TimeoutError(f"...{val}...")` below throws `UnboundLocalError` instead — the wrong exception type, which a
caller catching `TimeoutError` (every NV/AMD boot-path caller in `am/ip.py`, `nv/ip.py`, `nv/nvdev.py`,
`mlxdev.py`) would not catch.

**Fix.** Restructure as call-then-check (`while True: if (val:=cb(*args))==value: return val; if
elapsed>=timeout_ms: break`) — guarantees at least one `cb()` call (and `val` bound) before the deadline
can ever be consulted. This is a standard while-to-do-while reshape: for every case where the original
loop body ran at least once (i.e. every real/normal case, since `timeout_ms` is always large relative to
one comparison), the sequence of `cb()` calls and elapsed-time checks is identical, just phrased as
"check-after-this-call" instead of "check-before-the-next-call" — same instants, same call count, same
outcome. The only behavior change is exactly the bug: zero-call deadline-already-passed now correctly
raises `TimeoutError` with a real `val` instead of crashing on an unbound name.

**Test** (`test/unit/test_helpers.py::TestWaitCond`): `test_returns_on_first_match` (immediate-match
path, unaffected). `test_normal_timeout_raises_timeout_error_with_last_value` (negative control — real
clock, `timeout_ms=20`, condition never met — pins `TimeoutError` still raised with the same message
shape on the ordinary timeout path). `test_deadline_already_elapsed_raises_timeout_not_unbound_local` —
mocks `tinygrad.helpers.time.perf_counter` with `side_effect=[0.0, 1000.0]` (one read for `start_time`,
one for the elapsed check — both pre- and post-fix code make exactly 2 calls in this scenario, so the
mock is exhausted correctly either way) and asserts `TimeoutError` is raised.

**Proven failing pre-fix**: `git stash` on `helpers.py` alone → `test_deadline_already_elapsed_raises_timeout_not_unbound_local`
fails with exactly `UnboundLocalError: cannot access local variable 'val' where it is not associated with
a value` at the old line 559; the other two (normal-path) tests are unaffected — negative control proving
the fix doesn't touch normal timing.
