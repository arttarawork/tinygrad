## 3. Search-time or replay-time — definitive, code-proven, and now empirically pinned down further

**Definitively search-time**, by construction, independent of whether a fault ever fires:
`codegen/opt/postrange.py:334-345` (`apply_opts`), the `beam >= 1` branch:
```python
rawbufs, var_vals = args_from_ast(ast, ren.target.device)
with Context(ALLOW_DEVICE_USAGE=1):
  k = beam_search(k, rawbufs, var_vals, beam, ...)
```
and `args_from_ast` (`postrange.py:330-332`):
```python
def args_from_ast(ast:UOp, dname:str) -> tuple[list[Buffer], dict[str, int]]:
  glbls = sorted([x for x in ast.backward_slice if x.op is Ops.PARAM and x.arg.slot >= 0], key=lambda x: x.arg.slot)
  return [Buffer(dname, x.max_numel(), x.dtype) for x in glbls], {...}
```
Every buffer `beam_search`'s own `_time_program` (`search.py:36-47`) executes candidates against is a
**freshly-allocated, single-device scratch `Buffer`** sized exactly to that PARAM's declared
`max_numel()`/dtype — never the model's real production tensors, never a cross-device split buffer.
This is true for *every* call to `beam_search`, on every device, regardless of `--device-map`. It
means: **a fault occurring anywhere inside `beam_search`'s candidate-timing loop cannot by
construction be a split/placement bug** (class b in the brief) — there is no METAL-resident buffer in
reach, no cross-device pointer, nothing sized by T4.21's blob-placement logic. The only two
possibilities for a fault reached this way are (a) a codegen/optimizer bug — some `Opt` combination
produces a kernel whose generated index arithmetic reads/writes outside its own correctly-sized
scratch buffer — or (c) transient hardware/driver flakiness unrelated to the code.

**Empirical confirmation this session, more precise than "search, not replay" alone:** this
qwen3next hybrid model has `has_recurrent_block=True`, which forces `chunk_size=1` inside
`generate()` unconditionally (`llm/model.py`, `generate()`) — **every** call, including the "prefill"
of the 512-token prompt, is processed as a sequence of single-token (chunk=1) forward passes, so
`is_prefill` (`tokens.shape[1] != 1`) is **always False** for this model. There is no separate
large-batch prefill JIT/kernel family to worry about here (unlike a non-recurrent model). Consequence,
verified directly in Run 1's log: **all 95 of 95 `beam_search()` completions happened before the
`warm 520.908s` print** — `model.warmup()`'s own `generate([0], ...)` calls (chunk=1, both
temperatures) already exercise every kernel shape the real benchmark will ever need; the subsequent
real `prefill`/`decode` calls triggered **zero** additional fresh searches. So: whatever T4.30's fault
was, it necessarily happened **inside `model.warmup()`**, before a single real token was produced —
not merely "search, not replay" in the abstract, but concretely inside the chunk-1 JIT capture's own
`beam_search` calls, exactly as `codegen/opt/search.py:157-161`'s except-block located it:
```python
try: tms = _time_program(prg, var_vals, rawbufs, ...)
except Exception as e:
  if BEAM_DEBUG: print(f"BEAM failed for opts: {candidates[i].applied_opts}\n{e}")
  if isinstance(e, RuntimeError): fails[type(e).__name__] += 1; continue
  raise
```
Call chain from there to the fault report: `_time_program` → `engine/realize.py:321 time_call` →
`exec_kernel` → `HCQProgram.__call__` (`support/hcq.py:356`, `wait=True`) → `self.dev.synchronize()`
(`support/hcq.py:425-437`) → the signal's `_sleep()` → `PCIIface.sleep()` (`ops_nv.py:624`, raises
`"Device fault detected..."` once `is_err_state` flips) → caught in `synchronize`'s
`except RuntimeError as e: self.error_state = e; on_device_hang(); raise e` — `on_device_hang()`
(`ops_nv.py:833`) itself raises the richer `MMU fault: ...`/`SM ... fault: ...` report, which is what
actually propagates (not the plain `e`). **Only the first fault in a process gets this rich report**:
`self.error_state` is set to the plain "Device fault detected" message *before* `on_device_hang()`
runs, so every subsequent `synchronize()` call in that process short-circuits at line 426,
`if self.error_state is not None: raise self.error_state` (`hcq.py:426` — **exactly the line T4.30's
own final crash names**, "NV synchronization failed before finalizing... in hcq.py:426's
synchronize": that crash was this short-circuit firing on a *later*, unprotected `synchronize()` call
outside `beam_search`'s own try/except, once `error_state` was already latched from the first fault)
and re-raises the cached plain message, cheaply, without calling `on_device_hang()` again. This is
why a captured log's first "MMU fault:"/"SM ... fault:" line (not just any "Device fault detected"
line) is the one to grep for — see §6.

## 4. Localization — could not shrink below the full cell-5 command; here's what was and wasn't ruled out

**Smallest repro found: none smaller than T4.30's own cell 5 command**, because localizing further
requires knowing *which* of the ~95 kernels/candidates faults, and no attempt this session produced
one to target. What this session *did* rule in/out as discriminators, all without needing a live
fault:
- **Not a compile-cache-poisoning replay** (§2, 46865/46865 valid cubins in the live cache today).
- **Not a code regression between T4.30's checkout and this one** (§2, `search.py`/`postrange.py`
  byte-identical; T4.31/T4.37 diffs are both orthogonal to codegen correctness).
- **Reproduces on neither backend tried this session** — nvcc/NVRTC (Run 1) and NAK/Mesa (Run 3)
  both ran the identical split/config/token-count clean. This is inconclusive rather than
  exculpatory: if the underlying bug is a genuine but *marginal* OOB (reads/writes a small, wrong
  offset past a buffer's true bound), whether it actually crosses into an *unmapped* page — and thus
  faults at all — depends on allocator-adjacency state that can differ between process launches
  (fresh `BumpAllocator`/`kernargs_offset_allocator` state per process, plus multiprocessing
  `imap_unordered` candidate-completion order, which is not guaranteed identical run to run even with
  the same `PARALLEL`). Such a bug would silently read/write adjacent-but-still-mapped garbage on
  *most* runs and only occasionally cross into a fault — consistent with T4.30 hitting it twice in
  one session and this session hitting it zero times in three, all four attempts otherwise identical.
  A **structurally** wrong address (wrong stride entirely, off by a huge margin) would be expected to
  fault ~100% of the time regardless of allocator layout — the fact that it does *not* reproduce here
  argues for the marginal/adjacency-dependent variant, not a categorically-wrong-address one.
- **Sequence position, inferred (not directly observed):** T4.30 reports 20 kernels degraded to
  `hand_coded_optimizations` after the fault ("20x per-round warnings, 20x final-fallback warnings").
  This session measured **95 total distinct `beam_search()` calls** for this exact
  model/split/context on a clean run. If T4.30's kernel-shape universe was the same size (same model,
  same split, same max-context — it should be, since that's determined by architecture + device_map,
  not by which candidates win), the fault first struck at roughly **kernel #75 of 95** (95−20), i.e.
  **about three-quarters of the way through** `model.warmup()`'s single-token JIT capture — not the
  very first kernel searched. This also gives a grounded answer to the brief's "does 109 equal a
  candidate count / per-layer count / amt-round artifact?" question: **it's most likely neither** —
  it's the sum of (kernel #75's remaining round) + (kernels #76-95's each single round, one round
  each since every candidate in each of those rounds cheaply short-circuits on the cached
  `error_state`). 109 ÷ 20 ≈ 5.45 candidates/kernel-round on average, which matches the small
  round sizes directly observed in this session's own clean `BEAM_DEBUG=2` output (e.g. rounds
  shrinking 15→13→...→5, or 10→5, in Run 1's log) — an ordinary candidate-count artifact of this
  model's many small/simple kernel shapes, not a structural constant tied to `amt`, layer count, or
  round number.
- **Prime suspect location, by source inspection (not confirmed live):** `GatedDeltaNetBlock._attention`
  (`tinygrad/llm/model.py:373-421`) builds its recurrent core as a **Python-level unrolled loop over
  `T_pad` timesteps** (`for t in range(T_pad): s1 = state*alpha[:,:,t]; delta = (...); state = s1 +
  delta*k[:,:,t]; outs.append(...)`), fed into one `stack(...).contiguous()` — this is exactly the
  "novel kernel family" the brief flags (3 of every 4 NV-range layers are this block), and it produces
  unusually large, deeply-indexed UOp graphs: this session's own logs show many candidates for
  *some* kernels rejected by `too many uops` at `len(uops)` in the **4362-9409** range (`BEAM_UOPS_MAX`
  default 3000) — far larger than the plain attention/FFN kernels' typical few-hundred-to-low-thousands
  uop counts also visible in the same logs. A large, indexing-heavy unrolled-scan AST is exactly where
  an UPCAST/GROUPTOP/LOCAL combination is most likely to compute a wrong per-step offset for *some*
  but not all optimization choices. This is circumstantial (source-level), not a confirmed
  fault-to-kernel correlation.

## 5. Class verdict

**(a) Codegen/BEAM-candidate bug — high confidence on "not (b)," moderate confidence on "specifically (a)."**

- **(b) split/placement correctness bug: ruled out for any fault inside `beam_search`'s timing loop**,
  by construction (§3) — the buffers involved are single-device scratch, not the split's real
  cross-device tensors, so there is nothing for a placement bug to act on at that call site. (A
  *different* fault at actual model-replay time, after warmup, using the real split buffers, would be
  a live candidate for (b) — but this session's evidence (§3, 95/95 searches complete before `warm`
  prints) says T4.30's fault happened *during* the search, not during any subsequent real-buffer
  replay, so (b) is not in play for the fault this task was asked to diagnose.)
- **(a) codegen/BEAM-candidate bug: the leading hypothesis**, on: the search-time proof (§3); the
  round-trip-consistent 109/20-kernel arithmetic (§4) pointing at ordinary small-candidate-round sums
  rather than a special structural number; the GatedDeltaNet unrolled-scan AST as a concrete, sourced
  mechanism for how *some* opt combinations could go wrong on *this* novel kernel family (§4); and
  T4.30's own within-session determinism (109, twice, identical) being far more consistent with "a
  specific candidate's compiled code has a real bug that reproducibly faults *when that same candidate
  gets picked and executed again in the same process/session's memory layout*" than with (c).
- **(c) transient hardware/driver flakiness: disfavored but not excluded.** Two identical-count
  repeats in one session argue against pure randomness; three-for-three clean repeats in a different
  session (this one, post-reboot, post-T4.36-panic-and-recovery) is also not proof of hardware
  flakiness — it's equally consistent with (a)'s marginal-OOB variant (§4) simply not crossing an
  unmapped-page boundary this time. Nothing this session points at genuine silicon/driver instability
  specifically (no faults of *any* kind were observed on either backend, at any point, across ~35 min
  of combined warm-up+prefill+decode GPU time).
- **On the "does an NV kernel reach a METAL-resident buffer" specific worry from the brief:**
  structurally impossible for the fault this task investigates, per §3 — `beam_search`'s rawbufs are
  always single-device. If a *separate*, real cross-device fault exists at actual replay time on this
  split, it hasn't been observed: TASKS.md's own T4.21 entry notes this split vs. all-NV "diverges at
  idx 8," but classes it as benign fluent-equivalent FP-drift (T4.19 class), not a crash or a
  correctness bug — and none of this session's three clean full-pipeline runs, which *did* reach real
  prefill+decode using the real split buffers, showed any sign of a crash or fault (divergence from a
  *different* run wasn't checked here — out of scope for this task's fault-focused mandate).

## 6. Recommendation for the next attempt

1. **Unblock the lane first.** The host-side docker socket wedged by Run 2 needs a colima restart
   from the main session (outside this agent's authority; confirmed not self-healing after ~20 min).
   T4.31 is now cherry-picked onto this branch, so a fresh attempt from `task/T4.34-fault-storm` (or
   anything rebased on it) won't re-trigger the storm — but Run 2's specific already-wedged docker
   daemon instance needs that restart before *any* nvcc-lane run can even start.
2. **Add `BEAM_DEBUG=2` to the logging recipe.** The brief's `DEBUG=2` + `BEAM_LOG_SURPASS_MAX=1`
   alone never print `candidates[i].applied_opts` on a failing candidate — only `BEAM_DEBUG`
   (any truthy value) gates that print (`search.py:158`). Without it, a captured fault gives you the
   MMU/SM report but not which specific `Opt` combination produced the faulting kernel. `BEAM_DEBUG=2`
   additionally prints per-successful-candidate uop-count/compile-time/run-time/shape lines, useful
   for confirming the kernel identity from the nearest preceding "BEAM_SEARCH:" pyrendered-AST block.
3. **On a captured fault, grep for the first rich report, not just any "Device fault detected."** Only
   the first fault in a process gets the `MMU fault: 0x... | <type> | <access>` (or `SM ... fault:`)
   detail (§3) — every later occurrence in the same process is a cheap re-raise of the plain cached
   message. `grep -n "MMU fault:\|SM .* fault:"` and take the first hit; the "BEAM failed for opts:"
   line immediately before it is the exact candidate; the nearest preceding "BEAM_SEARCH:" block is
   the kernel's unoptimized AST.
4. **`--decode-tokens`/`--prompt-tokens` don't matter for reproduction speed** — confirmed this
   session (§3) that 100% of fresh BEAM work for this model happens inside `model.warmup()`, before
   either flag's tokens are ever generated. They can be dropped to near-zero to shave a little
   post-warmup time without changing whether/when a fault occurs; `model.warmup()`'s own ~450-520s is
   the actual cost regardless.
5. **Do not spend a run on the compile-cache-poisoning hypothesis again** — checked clean this session
   (§2), read-only, reusable script pattern in `t434_cache_scan.py` if it's ever worth re-checking
   after more compiles accumulate.
6. **If it reproduces again, treat the applied_opts as the top lead**, and try replaying just that one
   AST/opt combination standalone (extract from the pyrendered `BEAM_SEARCH:` block + the failing
   candidate's opts, apply via `k.apply_opt(...)` in a small script, compile+run once against a
   `args_from_ast`-shaped scratch buffer) — this is the "single kernel replayed standalone" the brief
   asked for, blocked this session only by never having a captured fault to point it at.
