## 2. The panics (full detail: `T4.36_DART_PANIC.md`, TASKS rows T4.36/T4.37/T4.40; logs committed as `kernelPanic.txt`, `kernelPanic2.txt`)
- Mechanism #1 (panic 1, 01:15): GSP-RM's message queues live in HOST sysmem (`nv/ip.py:367`). A GPU fault
  storm = GSP DMAing fault events into them at high rate. Killing the TinyGPU server (our old recovery)
  tears down those DMA mappings while the GPU still has PCI bus-master → one GSP DMA into an unmapped
  IOVA → `AppleT8110DART REQUIRE` → host panic. T4.37 fixed THIS path: clear MASTER on fault
  (`PCIIface.sleep`/`on_device_hang`/`device_fini`-finally), recovery hint = fresh client, never pkill under fault.
- Mechanism #2 (panic 2, 12:06 — the hole): `_early_ip_init` (`nvdev.py:127`) **unconditionally re-enables
  bus-master on every fresh client open** (it must). With ≥2 TinyGPU servers alive (the T4.38 leak: every
  process that opens NV spawns one when a stale/faulted server lingers — serial pytest included), one
  server/session teardown can unmap GSP host queues while ANOTHER freshly-inited client has mastering
  enabled and the GSP is DMAing → same panic. Timeline: T4.35's run faulted 11:57 → T4.33's pytest opened
  NV (2nd server) → three agents finished 12:03-12:05 → panic 12:06:34.
- **T4.40 (open, CRITICAL)** = the real fix set: (a) single-instance server discipline enforced at open
  (no stale servers, ever — supersedes T4.38); (b) don't re-enable mastering while a stale GSP session
  exists / controlled reset must tear down the old session first; (c) never open NV from a second process
  while a measurement or live fault exists. Upstream prior art & constraints in `T4.36_DART_PANIC.md`
  §Upstream (PR #16007 merged precedent; #16536 teardown-clear broke CI; geohot closes dock-panic issues
  unless self-contained; nimlgen wants faulting addresses/RCA, not workarounds).
