# T4.47 — RCA: why a memory-starved fresh BEAM search "ends in a device fault"

All file:line refs = fork master `7ca254099` (bench worktree). Evidence: `t435_run2b_p2_t30.log`
(session scratch; DEBUG=2, the third wall incident), TASKS rows T4.30-cell-4 / T4.35 / T4.34, and
tonight's T4.29 headroom run. Status of the live confirming repro is marked at the end.

## Verdict in one paragraph
The OOM does not cause the fault, and the fault does not cause the OOM. **A BEAM candidate that the
search has abandoned (routine, by design) faults or overruns on the GPU; the fault event then sits
UNDRAINED — invisible — because the driver only polls the GSP status queue after 200 ms inside a
single wait; the memory wall then supplies both the first long wait (LRU eviction's synchronize)
and an uncatchable `MemoryError`, so the fault finally surfaces from an allocation/teardown frame
and LOOKS like "OOM → fault".** T4.23's guarantee (clean OOM never faults) still holds — the fault
pre-exists the OOM; the wall is an amplifier and a surfacing point, not the source.

## The verified chain (every link file:line)
1. **Abandonment is routine.** `beam_search` times candidates with a device-side timeout of
   `early_stop*3` ms — milliseconds — whenever a candidate is ≥3x slower than the best so far
   (`search.py:154-156`, `BEAM_DEV_TIMEOUT=1` default → `_time_program:41` → `time_call(timeout=)`).
   The wait raises `RuntimeError("Wait timeout: …")` (`hcq.py:283-296`); `_time_program` does not
   catch RuntimeError, and `beam_search`'s handler counts it and **`continue`s — no synchronize, no
   cancellation** (`search.py:157-160`). Nothing on any GPU cancels a dispatched kernel: the
   abandoned candidate keeps executing.
2. **A faulting candidate is indistinguishable from a slow one.** An executed candidate that reads
   OOB (T4.34's structural class — 66-170 oversized siblings per search are *rejected* pre-run at
   `search.py:71-73`, but the executed ones can still be marginal) faults the GPU: its completion
   signal never fires → the same `Wait timeout` RuntimeError → the same silent `continue`. The GSP
   queues `MMU_FAULT_QUEUED`.
3. **The fault stays invisible.** `is_err_state` is set ONLY when the GSP status queue is drained
   (`nv/ip.py:73`), and the queue is drained ONLY in `PCIIface.sleep()` (`ops_nv.py:632`), which a
   waiting thread calls ONLY after **200 ms** inside one wait (`ops_nv.py:30`). A healthy fresh
   search syncs in sub-200 ms slices, so a queued fault can ride along for entire rounds.
   (Run 2b: first `Device fault` line is 89 lines AFTER the fatal MemoryError, raised from
   `hcq.py:294 wait → ops_nv.py:30 _sleep → sleep():637` during unwind; mem already 0/24610 MB.)
4. **The wall supplies the surfacing.** At ≤1 GB headroom, allocations start failing
   (`memory.py:103/262-268`); the LRU retry path (`device.py:259-267 free_cache`) frees real
   buffers, and `HCQAllocator._free` **synchronizes first** (`hcq.py:553-554`) — the first long
   wait in minutes → 200 ms gate passes → stat_q drains → `RuntimeError("Device fault detected")`
   out of an *allocation* frame (run 1's exact signature), or out of teardown (run 2b).
5. **The 176.00 MB is a red herring for causality** — it is simply the model's largest per-tensor
   load unit (98 × `copy 176.00 MB, NV <- DISK` at load), re-surfacing as the biggest single
   allocation the JIT planner/`_ensure_buffer_alloc` retries at the wall (`jit.py:292 →
   engine/realize.py → device.py:230`). Same tensor at any context ⇒ identical number in all three
   incidents. It marks WHERE the OOM lands, not what faults.

## Why T4.23 doesn't cover this
T4.23 proved a *quiescent* OOM cannot fault: the allocator raises before any map/submit, and
`is_err_state` comes only from real GSP events. Both still true. The search adds the one
ingredient T4.23 didn't have: **abandoned-but-still-running kernels whose failure mode (fault) is
swallowed by the identical exception as their normal failure mode (slow), with no drain in
between.**

## T4.34 wall-causality verdict
**Not wall-caused; wall-amplified and wall-surfaced.** Fault source = executed candidates
(stochastic, headroom-independent — T4.29's earlier nvcc BEAM-1 faulted at ~7 GB free). The wall
adds (a) mass alloc-failure churn that masks the faulted candidate among dozens of benign
failures, (b) the eviction syncs that finally drain it, (c) 600 s+ grinding runs in a faulted
state producing the 109-fault "storms". Tonight's instrumented headroom datum: T4.29 fresh
JITBEAM=1 at ~13 GB free — 170 structural uop-rejects, 0 wait-timeouts, 0 faults [FINAL NUMBER:
see addendum below].

## Minimal fix set (fork-local; composes with T4.46)
- **F1 — drain before verdicts (the real fix, ~3 lines):** in `beam_search`'s RuntimeError
  handler (`search.py:157-160`), after counting the failure, drain + check:
  `dev.synchronize()`-lite (an `iface.sleep(0)`-style stat_q drain) and if `is_err_state`, abort
  the search immediately with the fault error instead of grinding out the remaining rounds
  against a dead device. Test: fake device whose signal never fires + fake stat_q that delivers a
  fault event → search raises `Device fault` on that candidate, not 600 s later. (Without F1 a
  faulted search burns the full budget producing all-inf rounds — run 2b ground ~10 min post-fault.)
- **F2 — first-sleep drain (1 line):** `ops_nv.py:30` also drain on the first `_sleep` call of a
  wait (keep the 200 ms rearm for spins). Bounds fault-detection latency to one wait instead of
  "whenever a long wait happens to occur". Cheap: one extra RPC per wait.
- **F3 — sync at search end (1 line):** `beam_search` returns only after `dev.synchronize()`
  (bounds abandoned-kernel lifetime; prevents rawbufs' eventual eviction from racing a
  still-running abandoned kernel — the only genuinely unsafe free-ordering in this area).
- T4.46 (in flight) gives the failure classes distinct names; with F1/F2 its Counter would have
  said `DeviceFault: 1, WaitTimeout: 20` instead of `RuntimeError: 21`.
