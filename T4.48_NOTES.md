# T4.48 — surface faulted BEAM candidates instead of masking them

Implements T4.47_RCA.md's fix set (F1/F2/F3) plus one coordinator-requested fold-in (same code region as F1,
folded into F1's commit). No hardware touched — worktree `tinygrad-t448`, `DEV=CPU` throughout, fakes only
(`Device["NULL"]`, `SimpleNamespace`/`unittest.mock.patch.object` for ifaces/signals). The real dock was left
alone per the HARD RULES; see "Open items for the hardware pass" at the end.

## F1 — abort the search on a real device fault (`tinygrad/codegen/opt/search.py`)

**Mechanism.** New module-level helper `_device_faulted(dev) -> bool` (~5 code lines + docstring), called from
`beam_search`'s `except Exception as e: if isinstance(e, RuntimeError):` handler (~search.py:157-160 pre-fix)
right after the failure is counted:

```python
def _device_faulted(dev) -> bool:
  iface = getattr(dev, "iface", None)
  if iface is not None and hasattr(iface, "sleep"):
    try: iface.sleep(0)
    except RuntimeError: return True
  return bool(getattr(getattr(iface, "dev_impl", None), "is_err_state", False))
```

and in the handler:

```python
if _device_faulted(dev):
  raise RuntimeError(f"BEAM: device fault detected during search -- aborting rather than continuing against "
                      f"a faulted device. Failing candidate's applied_opts: {candidates[i].applied_opts}. "
                      f"Original error: {e}") from e
continue
```

**Why the getattr chain, not a hasattr/isinstance check on a known type.** `dev` is whatever `Device[s.ren.target
.device]` is for the kernel under search — could be NULL, CPU, METAL, CUDA, CLANG, AMD, or NV. Only NV and AMD's
HCQ ifaces model a GPU fault at all, and both put it at the same place, `iface.dev_impl.is_err_state`
(`ops_nv.py:633`, `ops_amd.py:957` — grepped every `is_err_state` site in the repo to confirm this is the only
pattern, no third shape exists). Every other backend has no `.iface` attribute at all (confirmed for NULL by
reading `ops_null.py`'s `NullDevice(Compiled)` — no `iface` anywhere). A chained `getattr(..., default)` makes
the absence a plain `False`, never an `AttributeError`; `_try_compile`'s own compile-only failures never reach
this code path at all (they update a *different* `fails` Counter site, `search.py`'s `fails[exc_name or
"unknown"] += 1` a few lines above the loop this touches, untouched by this fix).

**Why `iface.sleep(0)` and why call it at all instead of just reading `is_err_state`.** T4.47_RCA.md's whole
point is that a fault sits *undrained* in the GSP status queue until something calls the drain — reading
`is_err_state` without draining first would miss a fault that just happened. NV's `PCIIface.sleep` (`ops_nv.py:
631-637`) is *also* T4.37's clear-bus-master-on-fault site (safety-critical: a faulted GPU's GSP keeps DMAing
into host-sysmem queues until MASTER is cleared, and clearing it late is what caused the 2026-08-26 DART panic,
T4.36). Calling it here — rather than re-deriving a second, parallel "just read is_err_state" path — means F1
automatically inherits that safety fix instead of risking a drain path that reads the fault but never clears
MASTER. `sleep(0)`, not `sleep(200)`: confirmed by reading the body that NV's `timeout` parameter is **entirely
dead code** on `PCIIface.sleep` — it drains+checks+raises unconditionally regardless of the argument value.
AMD's iface (`ops_amd.py:955-958`) does honor `timeout` as a real `irq_poller.poll(timeout)` wait, so passing 0
there keeps this a non-blocking probe on AMD too (0 = return immediately, standard poll semantics) rather than
accidentally introducing a real wait on a backend this task doesn't target (AMD is descoped per CLAUDE.md, but
the duck-typed helper happens to be safe there anyway — free correctness, not extra scope). `iface.sleep()`
itself already raises `RuntimeError` the moment it observes a real fault; that's treated as "faulted" too
(`except RuntimeError: return True`) rather than letting its generic "Device fault detected." message escape
here — the caller (the except-handler above) composes the richer message naming the actual failing candidate.

**Coordinator fold-in (same commit, same code region as F1).** `hcq.py:296`'s `RuntimeError("Wait timeout: ...")`
was the last failure cause in this Counter still reported as bare `"RuntimeError"`. Renamed to `"BeamDeviceTimeout"`
via a string-match (`str(e).startswith("Wait timeout")`), *not* a bespoke exception class: T4.46 (unmerged, see
"Merge overlap" below) added real `RuntimeError` subclasses at its own two raise sites, but those sites are
inside *this* file (`_try_compile`, `timeout_handler`); this RuntimeError is raised inside `hcq.py`, which is
explicitly out of scope to edit (generic runtime code used far outside BEAM). String-matching a message is
fragile by nature — if `hcq.py:296`'s wording ever changes, this silently reverts to lumping the count under
`"RuntimeError"` again. Blast radius is low: the name only feeds a `Counter[str]` used for a printed
WARNING/diagnostic dict, nothing in `beam_search`'s control flow branches on the string value.

**Tests** (`test/opt/test_beam_search.py`, new class `TestBeamSearchFaultSurfacing`, extends T4.27's module):

  `RuntimeError("Wait timeout: 1 ms! ...")` on NULL (no `.iface` at all → `_device_faulted` is a true no-op);
  asserts the per-round WARNING dict shows `'BeamDeviceTimeout'`, not `'RuntimeError'`.
- `test_fault_after_runtime_error_aborts_with_candidate_opts` — fakes `dev.iface` with `is_err_state=False`

## F2 — drain on the first `_sleep()` of every wait (`tinygrad/runtime/ops_nv.py`)

**Mechanism.** `NVSignal` gains a class-level sentinel and the `_sleep` override compares against it:

```python
class NVSignal(HCQSignal):
  _last_elapsed_ms: float = float('inf')

  def _sleep(self, time_spent_since_last_sleep_ms:int):
    wait_start = time_spent_since_last_sleep_ms < self._last_elapsed_ms
    self._last_elapsed_ms = time_spent_since_last_sleep_ms
    if self.owner is None: return
    if time_spent_since_last_sleep_ms > 200: self.owner.iface.sleep(200)
    elif wait_start: self.owner.iface.sleep(0)
```

**Why "elapsed went backwards" and not a plain boolean flag.** The RCA suggested "a `first_sleep` flag". A
plain flag needs something to *reset* it at the start of each `wait()` call, but `_sleep` receives no signal of
that other than the `time_spent_since_last_sleep_ms` argument itself — and touching `hcq.py`'s `wait()` to pass
an explicit "this is a fresh wait" flag was explicitly out of scope (F2's brief says fix `ops_nv.py` only).
`hcq.py:293-295`'s `wait()` loop sets `start_time = now` once before the loop and resets it again *every time
the signal's value changes* (`if self.value != prev_value: start_time = ...`) — so the elapsed-ms passed to
`_sleep` is monotonically non-decreasing *between* those resets, and unconditionally drops back down near 0 at
each one (a brand-new `wait()` call, or a progress event partway through a long one). Comparing the newly-seen
value against the previous call's value detects exactly that reset, self-contained inside `_sleep`, with no
`hcq.py` change. The `float('inf')` initial sentinel makes a signal's very first-ever `_sleep()` call also
register as a "wait start" (anything real is `< inf`). This also means a progress-reset mid-wait gets its own
early drain, which is arguably *more* correct than "exactly once per `wait()` call" — a progress event is
itself a good moment to check the device is still healthy before waiting on the next chunk.

**Cost analysis (the RCA explicitly asked for this to be reasoned through, not asserted).** `PCIIface.sleep`
(`ops_nv.py:631-637`) does one of two things depending on locality:
- **Direct PCI** (`is_local()`): `self.dev_impl.gsp.stat_q.read_resp()` walks a local mmap'd ring buffer
  (`support/nv/ip.py:62-85`) — pure memory reads, no syscall, no network. Free.
- **Remote** (the dock's actual path, TinyGPU.app server over a Thunderbolt-backed socket): the queue's
  `tx_view`/`rx_view` are `RemoteMMIOInterface` (`support/system.py:312-331`), so each `[]` access is one
  blocking RPC round trip (`is_remote = True`, "reads/writes are blocking round trips" per its own docstring,
  `support/hcq.py:15`). `read_resp()` does a handful of small reads per call when the queue is empty (the
  common case) — call it "a few RPCs", not one, but each is a tiny fixed-size message, not the multi-hundred-KB
  transfers this codebase optimizes elsewhere (T4.18/T4.20's slab pooling). **This is added once per wait-start
  event, never per spin iteration** — proven by `test_drains_at_most_once_across_a_whole_sub_200ms_wait` (9
  simulated spin calls between 0-199ms produce exactly 1 drain).
- **Compounding with F1**: F1's `_device_faulted` also calls `iface.sleep(0)` once per caught `RuntimeError` in
  `beam_search`, which is itself downstream of a `wait()` that (per F2) already drained at its own start. So a
  timed-out candidate now triggers roughly 2 drains total (F2's wait-start drain + F1's post-failure drain),
  where pre-fix it triggered 0-1 (only if the wait happened to run past 200ms). T4.46's own data point — a
  full wipeout round logging `{'RuntimeError': 21}` — upper-bounds this at roughly 21 candidates × ~2 drains
  = ~42 extra small round trips per *wipeout* round (the pathological case); a healthy round with mostly-fast
  candidates whose waits never even call `_sleep` (loop exits before `_sleep` is reached) adds far less. This
  reads as consistent with the RCA's own framing ("Cheap: one extra RPC per wait") but the *number* of waits
  that hit this path in a real wall search, and its effect on real wall-clock, is exactly what's unverified —
  see "Open items" below.
- **NVKIface/MOCKIface**: `sleep(self, tm): pass` — unconditionally a no-op regardless of call frequency, so F2
  costs nothing extra there by construction.

**Tests** (`test/unit/test_nv.py`, new class `TestNVSignalSleepFaultDrain`, follows the existing fake-iface/
`SimpleNamespace` house style used by `TestNVFaultRecoveryHint`/`TestNVQuiesceOnFault`):
- `test_drains_on_first_sleep_of_a_wait` — `_sleep(0)` on a fresh signal drains once (pre-fix: `0 > 200` is
  False, zero drains).
- `test_drains_at_most_once_across_a_whole_sub_200ms_wait` — 9 calls with elapsed in `[0..199]` produce exactly
  1 drain (the "not per poll iteration" bound).
- `test_still_drains_past_200ms_unchanged` — the pre-existing >200ms path still fires, unchanged (passes `200`,
  not `0`, distinguishing "long-wait drain" from "wait-start probe" in the call log).
- `test_drains_again_when_a_new_wait_starts` — the same long-lived signal instance (mirrors `timeline_signal`,
  which persists across the device's whole life) gets a fresh drain on a *second* `wait()`'s first call, proving
  this isn't a one-time-ever flag.
- `test_noop_without_owner` — `owner=None` stays a no-op (pre-existing behavior, unchanged).

Test fixtures construct `NVSignal` via `NVSignal.__new__(NVSignal)` (skip `HCQSignal.__init__`, no real buffer
needed since `_sleep` only reads `self.owner`) and set `should_return = False` so `HCQSignal.__del__` doesn't
throw on GC (it unconditionally reads `self.should_return`, which a bare `__new__` never sets) — first pass hit
this as a `PytestUnraisableExceptionWarning` on every such test; fixed in the fixture, not by touching `hcq.py`.

## F3 — synchronize before `beam_search` returns (`tinygrad/codegen/opt/search.py`)

**Mechanism**, placed as the last statement before `return beam[0][0]` (after the disk-cache write and
`BEAM_DEBUG` print, which don't touch the device and shouldn't be gated on hardware state):

```python
try: dev.synchronize()
except RuntimeError as e: raise RuntimeError(f"BEAM: device faulted during search cleanup (synchronize after "
                                              f"search) for {s.colored_shape()}: {e}") from e
return beam[0][0]
```

**Why this bounds abandoned-kernel lifetime.** Every candidate's timed run (winners and abandoned losers alike)
is submitted through the same device queue in program order; `HCQCompiled.synchronize()` waits on
`self.timeline_signal` reaching `self.timeline_value - 1`, which only advances once everything queued ahead of
it — including every abandoned candidate from every earlier round — has actually completed on the GPU. So this
one call forces the driver to fully drain the backlog of "abandoned but never cancelled" kernels before handing
the winning `Scheduler` back to a caller that may immediately start freeing/evicting `rawbufs` (the RCA's
concern: LRU eviction's `synchronize()`-before-free in `HCQAllocator._free`, `hcq.py:553-554`, would otherwise
be the *first* place this drain incidentally happened, possibly minutes later under memory pressure).

**Why the winning candidate itself is safe to cache/return even if `synchronize()` here raises.** `beam[0][0]`
is only ever a candidate whose `_time_program` call already completed normally (candidates that raised were
excluded from `timed` and never entered `beam`), so a *later*, unrelated abandoned candidate faulting doesn't
retroactively invalidate the already-validated winner or its disk-cached `applied_opts` — `diskcache_put`
intentionally still runs before this sync, not gated on it.

**Tests** (`test/opt/test_beam_search.py`, new class `TestBeamSearchSyncsBeforeReturn`):
- `test_synchronize_called_before_return` — patches `Device["NULL"].synchronize` (a real inherited no-op
  normally) with a counting stub; asserts it's called exactly once.
- `test_synchronize_fault_gets_clear_search_message` — patches it to raise `RuntimeError("Device fault
  detected.")`; asserts the propagated message contains both "search" (the added context) and the original
  text (not swallowed into an opaque wrapper).

## Open items for the hardware wall-repro (RCA's own "phase-3 repro: NOT RUN")

1. **The actual distinguishing behavior is unverified on real silicon.** Everything here is proven at the level
   of "these functions get called with these arguments the RCA says they'll get called with" — a real
   memory-wall BEAM search on the RTX 3090/AG02 dock is what actually exercises `is_err_state` transitioning
   True from a genuine GSP fault event while search.py is mid-loop. Run one and confirm F1's abort message names
   a real faulting candidate (not just that the code path is reachable).
2. **F2's real-world RPC cost is reasoned, not measured.** The cost analysis above bounds it structurally (≤1
   drain per wait-start, never per spin iteration) but the *number* of wait-starts a real wall search produces,
   and the wall-clock this adds against DEXT/socket latency on the actual Thunderbolt path, is unmeasured. T4.46's
   `{'RuntimeError': 21}` wipeout-round datum is the closest existing evidence of scale; worth a before/after
   wall-clock comparison on a real search that hits that failure volume.
3. **`PCIIface.sleep`'s dead `timeout` parameter was confirmed by reading the Python source only.** Nothing here
   verified that the remote server/DEXT binary itself treats a `sleep(0)`-triggered RPC identically to a
   `sleep(200)`-triggered one at the wire/opcode level (both currently produce the exact same RPC traffic from
   the Python side, since the value is never encoded into any message) — should still hold given the client-side
   code is unconditional, but flagging since the RCA specifically asked to verify no server-side behavior is
   keyed off this value before relying on it.
4. **F1's added `iface.sleep(0)` fires on every caught `RuntimeError` in `beam_search`'s loop now, not just
   wait-timeouts** (any `RuntimeError` from `_time_program`, including ones unrelated to a hung wait). This is
   intentional per the RCA's brief ("after counting a RuntimeError, drain/check") but its effect on wall-clock
   for a compile-error-heavy (not timeout-heavy) search is unverified; compile-time failures from `_try_compile`
   go through a separate, untouched Counter site and never reach this code, so they should be unaffected, but
   worth eyeballing on a real long BEAM run alongside item 2.
