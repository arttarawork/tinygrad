Both panics: `panic(cpu N): (dart-apciec2) AppleT8110DART.cpp:2183: REQUIRE failed` — the Apple-Silicon IOMMU
(DART) behind the Thunderbolt PCIe tunnel caught a **device DMA to a host IOVA it has no translation for**.
Neither report records the faulting IOVA or stream (kernelPanic.txt:1-10, kernelPanic2.txt:1). All file:line
refs = `integration/phase1b` (`b37c792c6`); log refs = `ulog_tinygpu_2026-08-26.txt` (times local, UTC−4).
Written by a Fable fork of the main session, 2026-08-26 PM. Unknowns are marked **UNKNOWN**.

## 1. DMA-mapping lifecycle (DEXT + server) — the teardown half of every mechanism

- One `TinyGPU … server` process serves **exactly one python client at a time**: `listen(...,1)` +
  `g_client_active` reject-and-close for a second concurrent connect (server.c:268,274). A "busy" server is
  indistinguishable from a dead one to the connecting client → the client spawns a new server
  (system.py:441-449), whose `unlink(sock_path)` before bind (server.c:265) **steals the socket path**; the
  old server keeps its current client but becomes unreachable forever → the T4.25/T4.38 pileup, at source.
- **Per-client UserClient**: every python connect makes the server open a fresh DEXT user client
  (`open_tinygpu()` inside `handle_client`, server.c:191 → "NewUserClient created", TinyGPUDriver.cpp:78-93).
  84 such opens on 2026-08-26.
- **Mappings are created** by `PrepareDMA` (UserClient.cpp:132-161 → `SetupDMA` → `IODMACommand::PrepareForDMA`,
  TinyGPUDriver.cpp:121-136; ≤32 segments, 40-bit) for each `alloc_sysmem` (system.py:452-459 → CMD_MAP_SYSMEM_FD,
  server.c:129-165). Server cap: **MAX_SYSMEM=128** (server.c:42) — the T4.18 "~128-slot ceiling", source-confirmed.
- **Mappings are destroyed all at once, with zero quiescing**, when the client's socket closes:
  `handle_client` returns → `cleanup()` (server.c:255-256,171-183): munmap+shm_unlink every buffer, then
  `IOServiceClose(g_conn)` → UserClient `Stop_Impl` → **`CompleteDMA()` for every allocation**
  (UserClient.cpp:81-94). Same on server death (connection terminated → Stop). **Nothing clears PCI
  bus-master or resets the device first** — the teardown assumes the GPU is no longer DMAing.
- The python socket lives exactly as long as the **process**: `@functools.cache` on `bar_info`
  (system.py:447-448) keys on `self` → every `APLRemotePCIDevice` (and its socket) is retained until process
  exit, even if `NVDevice.__init__` raised and the object is otherwise unreachable. ⇒ **"client teardown"
  ≡ process exit (or server death). Every NV process exit unmaps its whole session.**
- Protocol has **no unmap verb** (RemoteCmd, system.py:309-310) and the in-tree server has no PING case
  (server.c:19-33 tops out at RESIZE_BAR; python's RemoteCmd.PING=12 would get RESP_ERR from `default:`).
  **Caveat**: in-tree source vs shipped app pinned at `c0d024f9` (system.py:419-425) may differ; observable
  behavior in the log (per-open NewUserClient, PrepareDMA, no teardown events) matches the in-tree code.

## 2. What `RemoteCmd.RESET` does, and what nobody verifies

- Client `reset()` (system.py:413) → CMD_RESET (server.c:231-233) → selector 2 (UserClient.cpp:129-131) →
  `ResetDevice()` = `Reset(kIOPCIDeviceResetTypeFunctionReset)`, HotReset fallback **only if the FLR call
  itself errors** (TinyGPUDriver.cpp:188-193). No post-reset verification anywhere in the stack.
- `_early_ip_init` (nvdev.py:113-137): if `NV_PFB_PRI_MMU_WPR2_ADDR_HI != 0` (a previous GSP session exists —
  WPR2 survives FLR by design; the next boot *requires* it, see below) → clear MASTER → FLR →
  **`time.sleep(0.1)`** → **unconditionally set MASTER** (nvdev.py:127). No WPR2 re-check, no core-halt check.
- The **old GSP-RM core is halted only later**, by `init_hw`'s first step `self.reset(self.falcon)`
  (ip.py:189, engine reset at ip.py:271-282) — i.e. AFTER `_early_mmu_init` + the whole `init_sw`
  (VBIOS read, fw fetch, ~66 MB of PrepareDMA staging: ulog 12:00:31.089 MASTER on → PrepareDMA to
  12:00:32.04). **Window: ~1-1.5 s in which a not-FLR-halted previous GSP-RM would be live with bus-master
  on and its own queues already unmapped.** Whether an FLR halts a *wedged* GA102 GSP-RM riscv core:
  **UNKNOWN** (needs NVIDIA semantics or the §7 register test; fix 40-4 makes it moot).
- Boot then: FRTS HS ucode on the GSP falcon → `assert WPR2 != 0` (ip.py:194) → riscv BCR → booter on sec2 →
  `RISCV_CPUCTL.active_stat == 1` (ip.py:210). The DEXT itself enables IO|MASTER|MEM at service start
  (TinyGPUDriver.cpp:57-60), so MASTER is on from plug-in even with no client.

## 3. The `fini`/unload path, and every timeout in the stack

- Clean exit: `atexit` → `Device[dn].finalize()` for **registered** devices only (device.py:57, 36) →
  `device_fini` (device.py:426) → `NVDev.fini` → `gsp.fini_hw` = `rpc_unloading_guest_driver`
  (ip.py:518,600-603, FAST_UNLOAD). After a successful unload the resident GSP-RM is quiescent (WPR2 stays
  up — every later open logs a reset: 15+/day, all healthy).
- **Every RPC wait and every hardware wait times out at 10 s**: `wait_resp(timeout=10000)` (ip.py:87-91) and
  `wait_cond(timeout_ms=10000)` (helpers.py:555-559) — and **raises**. Observed live: `fini()`'s unload to a
  dead/wedged GSP times out after 10 s with "cmd 47" (T4.37 step A, extra/t437/stepA log; TASKS T4.37 row).
- `is_err_state` is set **only** by GSP-delivered events (OS_ERROR_LOG / MMU_FAULT_QUEUED, ip.py:73-74).
  A timeout does NOT set it. Consequences on phase1b:
  - `device_fini`'s T4.37 clear runs only `if is_err_state` (ops_nv.py:614-621) — a session that fails by
    **timeout without processed fault events** exits with MASTER on.
  - A session whose `NVDevice.__init__` **raises** (any 10 s boot timeout) is never registered
    (device.py:36) → **no finalize, no unload, no T4.37 site ever runs** → GSP-RM left running, MASTER on,
    mappings armed until process exit. `Device.get_available_devices()` swallows the exception
    (device.py:40-42) and the *probing process keeps living* with that armed state.

## 5. Mechanisms, ranked

**M-A — "orphaned-session teardown" (root cause; panic 1 CONFIRMED at every link, panic 2 LEADING):**
a process exits without a *successful* GSP unload while PCI bus-master is set → the server/DEXT unmap the
session's host IOVAs (§1) → the still-running GSP-RM DMAs into them → DART panic. Sub-variants:
- **A1** fault → fini/unload times out at exit (panic 1; pre-T4.37 tree left MASTER on). **T4.37 already
  covers A1** when `is_err_state` is set — proven live at 11:50/11:57:42.
- **A2** init/probe failure: any 10 s boot timeout raises out of `NVDevice.__init__` → unregistered device,
  no unload, no clear, exception swallowed by `get_available_devices` → armed until process exit (panic 2's
  best fit). **Nothing covers A2 today.**
- **A3** hard kill (SIGKILL/crash/pkill) of a client or server with a live session. Client-side uncoverable;
  needs the DEXT-side fix (§6-5, §8). The historical pkill protocol is A3; **neither panic actually involved
  a pkill** (transcripts: the only pkill of the day was 08:18:44, T4.37 step B, survived).
Evidence FOR M-A: the whole causal chain is in source (§1-§3); the 10 s offset in both panics; T4.37's
partial fix visibly interrupting A1 at 11:50-11:57; ~15 healthy open/close cycles/day (successful unload)
never panic. AGAINST: no faulting IOVA recorded; panic-2's final-seconds events lost.
**H7 (contributor to panic 2's A2; PLAUSIBLE, unverified):** the merge adds a **new boot-time RPC**
(`NV2080_CTRL_CMD_FIFO_GET_DEVICE_INFO_TABLE` + `runlists` table) and a changed workSubmitToken path
(merge diff, ip.py:471-476,585-591 vs phase1b; upstream `4fd4eafb2 nv: hevc`) — first executed ever at
~12:06:30 on this GPU. A failure/timeout right there is A2's trigger. GA102 keeps `viddec_class=None`, so
the rest of the hevc change is dormant. T4.37's five clear sites survive the merge intact.
**M-C (possible DMA-source variant inside A2's window; UNPROVEN):** if FLR does not halt a wedged GSP-RM,
the *previous* session's core is live during the new client's MASTER-on pre-halt window (~1-1.5 s, §2) and
can hit its own unmapped queues. Cannot explain the +10 s alone. Closed by fix 40-4 regardless.
**H1 (the 13:00 handoff's "two servers + re-enabled mastering") — DEMOTED to enabler:** multi-server pileup
(§1) is why wedged sessions linger and probes spawn servers, but the log shows the panic-2-adjacent resets
were real and the fatal DMA needs M-A's teardown either way.
**Missing discriminating fact (top two):** for A2 — did the 12:06 probe's init fail, and at which step
(log tail lost)? Answerable by §7 hardware step H3 and by the T4.33 validation gates (if the merge tree's
collection errors persist, the early-exit path is confirmed cheaply). For M-C — `RISCV_CPUCTL.active_stat`
readout immediately after FLR on a previously-booted GPU (§7 step H2).

## 6. Fix set for T4.40 (minimal, exception/fault-path-only; respects #16536; composes with T4.40(a))

1. **Quiesce on failed init** — in `NVDev.__init__` (nvdev.py:91-102), wrap everything after the MASTER set
   in `try/except BaseException: clear MASTER (write_config_flush, the #16007 idiom); raise`. Covers A2 at
   the source regardless of which boot step times out. ~4 lines. Test: fake pci config space + an `init_sw`
   stub that raises → assert MASTER bit cleared and the exception propagates (mirror of T4.37's fake tests).
2. **Quiesce on failed fini** — `PCIIface.device_fini` (ops_nv.py:614-621): clear MASTER when `fini()`
   *raises*, not only when `is_err_state` (keep the healthy-exit no-clear): `except BaseException: clear;
   raise` inside the existing try, retaining the `finally`-style err_state clear. Covers A1 for wedges that
   never delivered fault events. ~3 lines. Test: fake `fini` raising TimeoutError → MASTER cleared; healthy
   fini → untouched (negative control, the #16536 guard).
3. **Halt-before-mastering** — reorder `_early_ip_init` (nvdev.py:121-127): after the FLR, do **not** set
   MASTER; perform `init_hw`'s GSP falcon engine reset (ip.py:189/271-282 — pure MMIO, needs no bus-master)
   and verify `NV_PRISCV_RISCV_CPUCTL.active_stat == 0` **before** enabling MASTER (replaces the blind
   `sleep(0.1)` with `wait_cond` on scrub/halt). Closes M-C's window and makes FLR semantics irrelevant.
   ~6-line reorder; the one fix that needs §7 hardware verification before trusting.
4. **(a) single-server discipline** — in flight (T4.40a agent, `task/T4.40a-server-discipline`): never spawn
   beside a live server; probes/xdist never spawn. Cuts the stale-session population that feeds A1/A2.
5. **DEXT/server ask (upstream, §8):** quiesce before unmap — clear PCI bus-master (CfgWrite cmd&~4) in
   `server.c cleanup()` before `IOServiceClose`, or in `UserClient::Stop_Impl` before the `CompleteDMA` loop.
   This is the only cover for A3 (SIGKILL/pkill/crash) and makes the host safe by construction.
6. Not proposed: touching `get_available_devices` upstream (probe-without-boot is a design change; T4.40a's
   no-spawn + the DEV=CPU gate rule close it operationally).
What this set does NOT cover: a mid-run hard kill before the DEXT fix lands (A3 — ops rule stays: never
kill an NV process/server); multi-GPU; and any DART fault from a genuinely wrong PTE (no evidence of one).

## 8. Draft report for tinygrad/tinygpu_releases (submission + AI disclosure = Artur's call)

> **TinyGPU server/DEXT tears down a client's DMA mappings without quiescing the GPU — can panic the host
> (AppleT8110DART REQUIRE) when a client exits with GSP-RM still running.**
> Setup: MacBook Pro M3 Pro, AG02/USB4, RTX 3090, TinyGPU @ c0d024f9. Two kernel panics on 2026-08-26
> (01:15, 12:06), both `(dart-apciec2) AppleT8110DART.cpp:2183 REQUIRE failed`, no tinygrad frames.
> Mechanism (source-level): on client disconnect the server runs `cleanup()` → `IOServiceClose` →
> `UserClient::Stop` → `CompleteDMA` for every allocation (server.c:255,171-183; UserClient.cpp:78-97),
> while nothing clears PCI bus-master or halts GSP-RM. GSP-RM's message/status queues live in that sysmem.
> Any client that exits without a successful `rpc_unloading_guest_driver` — a fault (the unload RPC times
> out), a failed boot (exception mid-`__init__`), or a kill — leaves GSP-RM bus-mastering into IOVAs the
> DART no longer translates. Both our panics land ~10 s after such a session start, matching the driver's
> universal 10 s RPC timeout → raise → exit → unmap. Repro preconditions and unified-log timeline available.
> Ask: quiesce before unmap — clear bus-master (config 0x4 &~4) in `cleanup()` before `IOServiceClose`, or
> in `Stop_Impl` before the `CompleteDMA` loop (~3 lines). Also useful: an unmap verb, and accept>1 or a
> busy-reply so a second client doesn't spawn a path-stealing second server (the multi-server pileup that
> keeps wedged sessions alive). Client-side mitigations (clear MASTER on failed init/fini) are in our fork.
