# T4.39 — beam_search's fallback result gets persisted to the disk cache

Host-side codegen fix, no GPU touched (`NULL` device only, `DEV=CPU` throughout). Branch
`task/T4.39-beam-inf-cache` off fork master `cb05a6c64` (carries T4.27).

## 1. Mechanism

`beam_search` (`tinygrad/codegen/opt/search.py`) seeds `beam = [(s, inf)]`. Post-T4.27, when every
candidate in every round fails to compile/time, the search never advances `beam` past that seed, so
after the `while` loop `beam[0][0] is s` and `beam[0][1]` is still the untouched `float("inf")`. T4.27
made this loud (an ungated WARNING per round, a second WARNING at the end) and replaces `beam[0][0]`
with `hand_coded_optimizations(s.copy())` so the *in-process* return value is never worse than not
asking for BEAM at all.

But the very next line was, and until this fix remained, unconditional:

```python
if CACHELEVEL >= 1: diskcache_put("beam_search", key, beam[0][0].applied_opts)
```

This persists `hand_coded_optimizations`'s opts — a result that was never actually measured on the
target device, only guessed by the same heuristic `postrange.py` already falls back to at `beam==0` —
keyed on the ast/amt/device/suffix, indistinguishable from a real, validly-timed BEAM winner. A later
call for the identical kernel hits this cache entry and returns it via the early-return branch at the
top of `beam_search`, **before `_try_compile` is ever invoked and before either WARNING can print** —
T4.27's diagnostics only fire during the search that produced the bad result, never on replay. Seen
live: 4x in T4.29's nvcc fault run, 3x in T4.35 run 1 (`final tm=infs` in `BEAM_DEBUG` output).

Confirmed empirically pre-fix (not just read): stashing only the `search.py` diff and running the new
test against `cb05a6c64` fails with
`AssertionError: [Opt(op=OptOps.UPCAST, axis=1, arg=4)] is not None` — i.e. the fallback's
`hand_coded_optimizations` opts land in the (faked, in-memory) disk cache exactly as described.

## 2. Fix (`tinygrad/codegen/opt/search.py`, +4/-1, one line changed)

```python
if CACHELEVEL >= 1 and not math.isinf(beam[0][1]): diskcache_put("beam_search", key, beam[0][0].applied_opts)
```

**Why `math.isinf(beam[0][1])` and not a separate "did we fall back" flag:** the task's own fix-shape
guidance names both symptoms — "best time is inf / the chosen opts came from the fallback" — and they
collapse into the same check. Tracing the loop: `beam[0]` is only ever reassigned from candidates that
survived `_time_program` (real, finite timings) via `beam = opts[:amt]` or
`beam = opts[:1]` (`opts` sorted by finite time — except the one edge case below). The two cases where
`beam[0][1]` ends up `inf`:

1. **Total failure (the T4.27 fallback path).** `beam` is never reassigned at all, so it's still the
   seeded `(s, inf)` (or, after the fallback line, `(hand_coded_optimizations(...), inf)` — the
   fallback only replaces `beam[0][0]`, never `beam[0][1]`). This is the exact case T4.39 was filed for.
2. **A "successful" candidate whose only timing attempt hit `_time_program`'s `AssertionError`
   handler** (search.py:50, `return [math.inf] * cnt`) and ended up the round's best (or only) option.
   T4.27's own commit message calls this out as the reason it uses object identity
   (`beam[0][0] is s`) rather than an inf-score check to detect the *fallback* case specifically — a
   real, distinct-from-`s` candidate can legitimately carry score `inf` too. That candidate was never
   actually measured any more than the fallback was (the assertion means the timing run itself didn't
   produce usable numbers), so it belongs in the same "don't persist" bucket for the *caching*
   question, even though T4.27 was right to keep it out of the *fallback/warning* classification.

A single score check on the final `beam[0][1]` catches both without adding new state, without
touching the T4.27 identity check, and without narrowing anything — the smallest diff that is still
correct for both cases named in the task.

**In-process behavior (T4.27) is unchanged**: `beam_search` still returns
`hand_coded_optimizations(...)` in the total-failure case, still prints both WARNINGs. Only the disk
write is skipped. A later call for the same key simply finds no cache entry, so it re-enters the full
search (`get_worker_pool()`, the `while` loop, `_try_compile`, etc.) exactly as if it were the first
call ever made for that kernel — including re-emitting the WARNINGs, which is the whole point (the
next run gets to notice the flake instead of inheriting a silently-cached guess).

## 3. What was deliberately not touched

- **`_try_compile`'s exception handling** — untouched, per the task's explicit instruction and T4.27's
  own reasoning (a real non-`RuntimeError` case, `BrokenPipeError` from a flaky compile transport,
  legitimately means "retry another candidate" and narrowing it without dock evidence risks turning a
  transient flake into a hard crash on some backend this host-only task can't exercise).
- **Nothing outside `search.py` + tests.**
- **The trivial "kernel has no tunable axes" case** (`candidates == []` on round 1, so
  `beam[0][0] is s` but the fallback/WARNING branch is correctly skipped since it's gated on
  `beam[0][0] is s and candidates`): this also has `beam[0][1] == inf` (beam is never touched), so it
  now also skips the cache write, where before it wrote a harmless no-op entry (re-applying `[]` opts
  onto a fresh copy is a no-op). This is a strict improvement, not a regression: previously-cached
  no-op entries for such kernels were free but pointless; skipping them costs an extra pass through an
  empty `while` loop next time (no candidates generated, no compiles attempted — cheap) in exchange for
  one less special case in the fix. Not worth a second flag for.
- **Same pattern elsewhere, flagged out of scope:** T4.31's escalation note already named
  `device.py:317-327`'s `compile_cached`/`compile_server` path as having no protection at all against a
  flaky transport (a different, upstream-side call site, not `search.py`). Unrelated to this fix but
  worth keeping on the radar for the same "cache the flake permanently" failure shape.

## 4. Tests — `test/opt/test_beam_search.py` (extends T4.27's module, its 2 existing tests untouched)

Both new tests build the same real, hardware-free `NULL`-device ast/Scheduler as T4.27's
`_build_seed()`, and monkeypatch `search_mod.diskcache_get`/`diskcache_put` to a tiny in-memory
`_FakeDiskCache` (scoped to the test via `setUp`/`tearDown`) instead of touching the real, multi-GB,
hardware-measured `beam_search` disk cache that lives at `~/Library/Caches/tinygrad/cache.db` on this
machine — sqlite file isolation (temp `CACHEDB` + reopening the module-level connection) was considered
and rejected as more moving parts for no extra correctness; patching the two names `search.py` imports
achieves the same isolation with zero real file I/O.

- `test_total_failure_is_not_cached_and_replay_call_resarches` (the core T4.39 test, **fails on
  `cb05a6c64`**): every candidate fails via a monkeypatched `_try_compile` (non-`RuntimeError`, mirrors
  T4.27's own `BrokenPipeError` choice). First call: asserts the WARNING fires and
  `result.applied_opts == hand_coded_optimizations(s.copy()).applied_opts` (T4.27 behavior, unchanged),
  **then asserts the fake cache holds no entry for the key** — the direct T4.39 assertion. Second call
  for the identical `s`/key: asserts `_try_compile`'s call count strictly increased (proves a real
  re-search happened, not a cache hit — on a hit `_try_compile` is provably unreachable, since
  `get_worker_pool()` and the `while` loop only run past the early-return cache-hit branch) and that
  the WARNING fires again, then re-asserts the cache is still empty after the replay attempt.
- `test_successful_search_is_still_cached_and_replayed` (positive control, **passes on `cb05a6c64`
  too** — this path is untouched by the fix): a real (unpatched) search reaches a finite time; asserts
  the fake cache **does** get a matching entry after the first call. Second call: monkeypatches
  `_try_compile` to `raise AssertionError(...)` and asserts no exception surfaces and the result matches
  the first call's opts — if this call had NOT been served from the cache, `_try_compile` would have
  blown up the test immediately, so a clean pass is direct proof of a real cache hit.

**Proven failing pre-fix**: `git stash push -- tinygrad/codegen/opt/search.py` (keeping both new test
methods and T4.27's originals), reran `test/opt/test_beam_search.py` against `cb05a6c64`'s
`search.py`:

i.e. exactly the fallback's `hand_coded_optimizations` opts landing in the cache. The other 3 (T4.27's
2 originals + the new positive control) pass unchanged pre-fix, confirming the positive-control path
