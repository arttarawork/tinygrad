# T4.40c — halt-verify before re-enabling bus-master

**HARDWARE-VERIFIED 2026-08-26 22:09 (RTX 3090 / AG02 / USB4, NAK lane) — CLEARED TO MERGE.** The fake-register model
matched real GA102 silicon; the full T4.40c path executed correctly on hardware and the machine never
panicked across 6 NV opens (incl. a deliberate fault and two forced init failures).

**Key finding (RCA §7 H2 answered): on this GA102 the FLR alone already halts the previous GSP-RM core** —
`active_stat == 0` was read *before* the falcon engine reset, on both a fresh-after-healthy and a
fresh-after-FAULT open. So 40-3's falcon reset is **redundant on GA102** (the FLR suffices) — it is now
**defense-in-depth**, and the load-bearing change is that the blind `sleep(0.1)` is replaced by a *verified*
halt (`wait_cond active_stat==0`) that also refuses to re-enable mastering on a core that did NOT halt. This
also confirms **M-C was never the panic mechanism** — a live old core racing the next boot does not occur;
the panics were A1/A2 (covered by T4.37/40-2 and 40-1, both re-verified here). **Session results:** H1 MASTER
1→1; H2 active_stat 0 pre-reset (both opens), verify passed; H4 fault → MASTER→0; recovery (panic-1 sequence)
clean; H3 forced init-fail → MASTER 1→0. Protocol + probes: `extra/t440c/`. The `NV_HALT_DEBUG` prints are
kept (env-gated, off by default) as reusable dock diagnostics.

## 1. The reorder — old vs new

Baseline (pre-T4.40c, `tinygrad/runtime/support/nv/nvdev.py` on the PR #5 branch head `6d035b93d`,
`_early_ip_init` at lines 124-148):

```
124  def _early_ip_init(self):
125-130  reg_names/reg_offsets init; include(nv_ref/dev_fb/dev_gc6_island)
132  if WPR2 != 0:                       # a previous GSP-RM session exists
133    clear MASTER
134    print (DEBUG>=2)
135    pci_dev.reset()                   # the FLR
136    time.sleep(0.1)                   # "wait until device can respond again"
138  set MASTER                          # UNCONDITIONAL -- no check the previous core is halted
139-143  read chip_id/chip_details, derive chip_name/fw_name/mmu_ver/fmc_boot, construct self.flcn/self.gsp
148  self.flcn.wait_for_reset()
```

The gap: between the FLR (135) and MASTER going back on (138), the only thing standing between "maybe a
wedged GSP-RM core is still alive" and "the GPU can bus-master again" is a blind 100ms sleep. Nothing
reads any register that would tell you the previous core actually stopped.

New (this branch, same method, now 124-165 — see the file for the exact text):

```
124-130  unchanged (reg_names/reg_offsets init; include(nv_ref/dev_fb/dev_gc6_island))
132-140  chip_id/chip_details/chip_name/fw_name/mmu_ver/fmc_boot   <- MOVED UP (was after the old line 138)
142-143  construct self.flcn/self.gsp                              <- MOVED UP (was after the old line 138)
145  if WPR2 != 0:
146    clear MASTER
147    print (DEBUG>=2)
148    pci_dev.reset()                   # the FLR -- unchanged
149    time.sleep(0.1)                   # unchanged, kept (see Sec2)
151-163  NEW: if isinstance(self.flcn, NV_FLCN):
157-159    include(dev_gsp/dev_falcon_v4/dev_riscv_pri, "ga102")   # need these 3 groups early; see Sec4
160        self.flcn.falcon = 0x00110000                            # GSP falcon engine base (same constant
                                                                      # ip.py NV_FLCN.init_hw/NV_FLCN_COT.init_hw use)
161        self.flcn.reset(self.flcn.falcon)                        # ip.py NV_FLCN.reset(), REUSED verbatim
162-163    wait_cond(active_stat == 0, msg="previous GSP-RM core did not halt after FLR + falcon engine reset")
165  set MASTER                          # now only reached once the if-branch's verify (when taken) passed
166  self.flcn.wait_for_reset()          # unchanged
```

Net: MASTER is set exactly where it always was (one unconditional write, same line role), but on the
WPR2-up path it is now gated by a real verification instead of a blind sleep. On timeout, `wait_cond`
raises `TimeoutError` with MASTER still clear (never reached line 165), and T4.40b's `__init__` wrapper
(`nvdev.py:104-113`, unmodified) catches it, re-clears MASTER (a no-op AND on an already-clear bit — see
its own comment) and re-raises. Confirmed by
`TestNVHaltVerifyBeforeMaster.test_composes_with_t440b_wrap_master_stays_clear_through_full_init`.

## 2. Why chip-id detection moved up (not just the WPR2 block)

`NV_FLCN.reset()` (ip.py:271-282) needs three things that weren't available yet at the old FLR site:
`self.flcn` (a real `NV_FLCN`/`NV_FLCN_COT` instance, to know COT vs classic), `self.flcn.falcon` (compared
against inside `reset()` to pick `NV_PGSP_FALCON_ENGINE` vs `NV_PSEC_FALCON_ENGINE`), and `self.nvdev.chip_id`
(written into `NV_PFALCON_FALCON_RM` in `reset()`'s `elif` branch, taken when a previous boot already put the
falcon into riscv mode — the exact case this fix targets). All three come from chip-id detection, which was
previously read only *after* the unconditional MASTER-set.

Moving it up is safe: `NV_PMC_BOOT_0`/`NV_PMC_BOOT_42` (chip_id/chip_details) are static hardware identity
(architecture/implementation straps), invariant across an FLR, and are plain BAR0 MMIO reads satisfied by
the *same* three includes (`nv_ref`, `dev_fb`, `dev_gc6_island`) already loaded before this code runs — no
new include needed for the move itself. The existing WPR2 check *already* reads BAR0 MMIO (`dev_fb`) before
any FLR or MASTER touch, at the very top of this method, so reading chip identity at the same point is no
new assumption, just more of the same one.

## 3. The MMIO-without-MASTER justification (the premise this whole fix depends on)

PCI bus-master (`PCI_COMMAND_MASTER`, bit 2) gates whether the *device* can initiate outbound DMA. It is a
separate bit from PCI memory-space enable (`PCI_COMMAND_MEMORY`, bit 1), which gates whether the *host* can
reach the device's BAR-mapped registers (`self.mmio`, BAR0) at all. `nvdev.py` never touches the MEMORY bit
anywhere — every `write_config_flush(PCI_COMMAND, ...)` call in this file (and in `ops_nv.py`/`amdev.py`)
ANDs/ORs `PCI_COMMAND_MASTER` specifically, leaving MEMORY untouched.

MEMORY is enabled once, well before any `NVDev` is ever constructed, and stays on regardless of what
`_early_ip_init` does to MASTER:
- `system.py:103` and `:137` (`pci_setup_usb_bars`, the USB4/Thunderbolt bridge bring-up) write
  `PCI_COMMAND_IO | PCI_COMMAND_MEMORY | PCI_COMMAND_MASTER` together, once, at BAR-sizing time.
- Per RCA `T4.40_RCA.md` Sec2 last bullet, on the real Mac/dock path the TinyGPU DEXT does the same at
  service start (`TinyGPUDriver.cpp:57-60`): "MASTER is on from plug-in even with no client."

So BAR0 reads/writes (`self.mmio[addr//4]`, i.e. every `NVReg.read()`/`.write()`/`rreg()`/`wreg()` call) work
identically whether MASTER is set or clear. This is the premise the whole fix stands on — verified by reading
`system.py`, not assumed. If this turns out to be wrong on real Mac/USB4-dock hardware specifically (as
opposed to the Linux/ASM2464 path `pci_setup_usb_bars` actually serves), the fix does nothing useful and
falls back to timing out uselessly; see the hardware checklist below.

## 4. Design decisions worth flagging

- **`self.flcn.falcon = 0x00110000` set early, again in `init_hw()`.** `NV_FLCN.init_hw()`
  (ip.py:187) and `NV_FLCN_COT.init_hw()` (ip.py:312) both set this exact constant as their own first act.
  Re-assigning the same int is not "work" in any sense that matters — no register touched, no RPC, no
  timing. Left `init_hw()` untouched rather than threading a "did we already set this" flag across files.

- **`self.flcn.reset(self.flcn.falcon)` runs twice on the WPR2-up path** — once here, once more as
  `init_hw()`'s own first line (ip.py:189), unmodified. This *is* the literal duplicate-work the task asked
  to avoid where reasonably avoidable, and I chose not to avoid it. Reasoning: `reset()` is a hardware
  primitive explicitly built to be safely re-invocable (assert engine reset, wait for scrub, de-assert) —
  invoking it from an already-just-reset state is the textbook idempotent case, costing one extra ~0.1-0.2s
  engine-reset-and-scrub cycle. The alternative was adding cross-file state (e.g. a `self.flcn._early_reset_done`
  flag `init_hw()` checks) purely to shave that ~0.1-0.2s off the WPR2-up boot path — more surface area in
  `ip.py` (which the task said to touch only if strictly required; it isn't) for a micro-optimization, on a
  boot sequence RCA's own timeline already measures in seconds. The hardware session should confirm this
  really is harmless on real GA102 (see checklist item 4) and time whether the extra reset is worth
  eliminating later if it isn't.

- **`isinstance(self.flcn, NV_FLCN)` gates the whole new block.** `NV_FLCN_COT` (Blackwell/GB2xx, FSP-based
  chain-of-trust boot) is a *different, non-inheriting* class with no `.reset()` method, no riscv-CPUCTL
  concept, and no equivalent in the RCA's analysis or the actual target hardware (GA102/RTX 3090, confirmed
  by `chip_details['architecture']` mapping to `"GA1"`, i.e. `fmc_boot=False`, i.e. always `NV_FLCN` — see
  `nvdev.py:138,140`). Inventing a halt-verify for COT would be exactly the kind of unverified, unanalyzed
  code path this task's "must not be trusted until hardware-verified" framing warns against — worse, there
  is no dock with Blackwell hardware to ever verify it on. Left byte-for-byte unchanged (still just the FLR
  + blind 0.1s sleep) for that path.

- **`active_stat` chosen over `NV_PRISCV_RISCV_CPUCTL`'s own `halted` field** (bit 7 vs bit 4 of the same
  register, `tinygrad/runtime/autogen/nv_regs/dev_riscv_pri.py:5`) — not `NV_PFALCON_FALCON_CPUCTL.halted`
  either (a *different* register, used by `wait_cpu_halted()` for a different purpose: waiting for HS-ucode
  execution to finish post-`execute_hs`). `active_stat` is what the task and RCA Sec7 H2 both name explicitly,
  and it's the same register+field `ip.py:210` already relies on post-boot (`assert ...active_stat'] == 1`,
  "GSP Core is not active") — this fix checks for the opposite value at the opposite end of the boot, which
  de-risks the semantic interpretation since it's a field the existing codebase already trusts, not a novel
  reading.

- **The FLR-settle `time.sleep(0.1)` was kept, not replaced.** RCA Sec6 fix 3 describes the net effect as
  "replaces the blind sleep(0.1) with `wait_cond` on scrub/halt" — read here as replacing the *unconditional
  MASTER-set* that used to follow the sleep, not necessarily the sleep itself. The sleep's own comment
  ("wait until device can respond again") is about the PCI device recovering from the FLR at all, a
  different concern from whether the *previous GSP-RM core* is halted. Removing it and immediately issuing
  MMIO writes right after `pci_dev.reset()` returns is untested territory this task has no hardware to check;
  keeping it is the more conservative choice and costs one line, not zero. The hardware session should
  confirm whether it's actually still needed (checklist item 3) now that a real verify step follows it.

## 5. Test evidence

`test/unit/test_nv.py`, new class `TestNVHaltVerifyBeforeMaster` (4 tests), fixtures `_RegProbe`, `_reg`,
`_FakeIpInitDev`, `_FakeFLRPCIConfig`, `_EventBar0`, `_poke`, `_make_fake_hw`, `_fast_timeout_clock`:

- Drives the **real** `NVDev._early_ip_init()` / `NVDev.__init__()` (not copies) against a fake BAR0 register
  file. `_EventBar0` models the RCA's M-C hypothesis as a mechanism, not an assumption: `CPUCTL.active_stat`
  only clears once `NV_PGSP_FALCON_ENGINE`'s reset=1-then-reset=0 sequence (ip.py `NV_FLCN.reset()`,
  unmodified) actually completes — so a passing test proves the code's *actions* cause the observed halt,
  not that the fake merely started pre-halted. `wedged=True` makes that sequence have no effect, modeling a
  core neither the FLR nor an engine reset brings down.
- `test_master_not_set_before_core_verified_halted`: orderable event log (mmio reads + PCI_COMMAND config
  writes in one ordered list) proves the MASTER-set write happens strictly after the first CPUCTL read
  that returns "halted". **Proven failing pre-fix**: pre-T4.40c code never reads CPUCTL at all, so the
  "halted_reads" list is empty and the first assert fails (confirmed by reverting nvdev.py and re-running).
- `test_healthy_fake_boots_exactly_as_before_master_ends_set`: negative control — a core that halts as soon
  as `reset()` runs boots straight through, MASTER ends set. **Proven failing pre-fix** (`self.flcn.falcon`
  is never set that early in the old code).
- `test_never_halting_core_raises_and_master_stays_clear`: wedged fake -> `TimeoutError`, MASTER stays
  clear, no MASTER-set write ever appears in the event log. **Proven failing pre-fix** ("TimeoutError not
  raised" — old code just sleeps and sets MASTER regardless).
- `test_composes_with_t440b_wrap_master_stays_clear_through_full_init`: drives the real `NVDev.__init__`
  (not just `_early_ip_init`) with the wedged fake, proving the T4.40b `except BaseException` wrapper and
  this fix's own raise-with-MASTER-clear compose without double-clear breakage. **Fails pre-fix** too
  (differently — pre-fix code doesn't raise here at all, so it runs on into `_early_mmu_init()` and hits an
  unrelated `AttributeError` against the deliberately-minimal fake; still a genuine pre/post behavior
  difference, just a less on-topic failure mode than the other three).
- `_fast_timeout_clock()` mocks `time.perf_counter` (NOT `time.sleep` — the two real ~0.1s hardware-settle
  sleeps in `reset()`/`_early_ip_init` still run for real) so the never-halts tests hit the real, unmodified
  10s `wait_cond` default timeout in ~200 fast iterations instead of a real 10s busy-spin. Caught and fixed
  a latent pre-existing bug in this process: `helpers.wait_cond` references its loop-local `val` in the
  timeout message, which is `UnboundLocalError` (not `TimeoutError`) if the very first while-check already
  exceeds `timeout_ms` — the mock steps in 50ms (0.05s) increments specifically so the loop body always runs
  at least once before that. Not fixed in `helpers.py` (out of scope, shared/safety-critical file, real
  hardware never hits it since real elapsed time between two `perf_counter()` calls is never >10s on its own).

Preconditions per RCA Sec7: fixes 40-1/40-2 (T4.40b) already in tree (they are, this branch is based on the
PR #5 head which includes them); exactly one server; `DEV=NV:NAK`; abort on ANY unexpected fault — stop,

1. **RCA H2 itself, now answerable live**: healthy boot -> clean exit -> fresh client. Instrument
   `_early_ip_init` (e.g. a print right before the `if isinstance(self.flcn, NV_FLCN):` block and another
   right after the `wait_cond` returns) and read `WPR2_ADDR_HI` (expect != 0) and `RISCV_CPUCTL.active_stat`
   **immediately after the FLR, before this fix's `reset()` call** — this is the actual open question the
   whole fix is scoped around: does the FLR alone already halt the core (making this fix's own `reset()`
   call redundant-but-harmless), or is `reset()` doing real work? Either answer is fine; either way MASTER
   ends up gated on a real read, but it changes whether fix 40-3 is load-bearing or just cheap insurance.
2. **Does the verify step ever actually have to wait?** Log how many `wait_cond` iterations the new
   `active_stat` check takes on real hardware. If it's always 1 (immediate pass), that's consistent with
   `reset()` alone being sufficient and the register semantics being what this branch assumes. If it takes
   several iterations, that's the mechanism actually mattering on real silicon, not just in the fake.
3. **Is the pre-`reset()` `time.sleep(0.1)` still load-bearing?** With the new verify step now present as a
   backstop, try removing it (or shortening it) on a scratch branch and see if `reset()`'s first MMIO write
   (`NV_PGSP_FALCON_ENGINE.write(reset=1)`) ever misbehaves (hangs, wrong readback) immediately post-FLR. If
   the sleep turns out to be unnecessary now, that's a legitimate future simplification — not made here
   because removing a working safety margin without hardware evidence is worse than one redundant line.
4. **Confirm the double-`reset()` call is actually harmless on GA102.** Time the WPR2-up boot path
   before/after this branch; the only expected delta is one extra `NV_PGSP_FALCON_ENGINE` reset-and-scrub
   cycle (~0.1-0.2s per Sec4 above). If it's meaningfully more, or if two consecutive engine resets ever
   produce a different `WPR2`/boot outcome than one, that invalidates the Sec4 tradeoff and `init_hw()`
   should be revisited to skip its own call when this one already ran.
5. **RCA H3/H4 (A2/A1 repro)** are unaffected by this specific fix and can be (re-)run per the RCA's own
   protocol once 40-3 is confirmed safe, to check nothing about this reorder regressed T4.40b's coverage.
6. **The MEMORY-vs-MASTER premise (Sec3 above) on the actual Mac/USB4/DEXT path**, not just read from
   source: confirm a BAR0 read genuinely succeeds (returns real, non-garbage data — e.g. `WPR2_ADDR_HI`
   reading a value consistent with a prior boot, or `NV_PMC_BOOT_42` decoding to a sane GA102 architecture)
   while MASTER reads back 0 (right after the pre-fix-equivalent clear, before this fix's `reset()` runs).
   This is the one assumption that, if wrong, means the whole fix is inert rather than merely redundant.
