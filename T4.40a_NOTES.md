# T4.40a — single-instance TinyGPU server discipline at open

Scope: `APLRemotePCIDevice.__init__` in `tinygrad/runtime/support/system.py` only. Implements item (a)
from the T4.40 breakdown (HANDOFF_2026-08-26.md §2 / TASKS.md T4.40 row): never spawn a second TinyGPU
server while any server process is alive, and never spawn at all from a probe or an xdist test worker.
Base commit `b37c792c6` (fork master + T4.37 + T4.31). Does not touch `_early_ip_init`, resets, PCI
config, `ops_nv.py`, `nvdev.py`, `ip.py`, or the DEXT sources — that is T4.40 (b)/(c) and a separate RCA
agent's territory.

## Behavior table

Rows = real-world server state, columns = calling context. "Spawn?" = does this `__init__` call ever
invoke `subprocess.Popen([APP_PATH, "server", sock_path])`.

| Server state \ Context | Normal (no xdist, no `NV_NO_SPAWN`) | xdist worker (`PYTEST_XDIST_WORKER` set) | `NV_NO_SPAWN=1` |
|---|---|---|---|
| **Absent** | Spawns exactly once (i=0), retries connect for 5 s, succeeds once the server binds. Unchanged T4.25 behavior. | **No spawn.** One connect attempt; fails immediately (`FileNotFoundError`/`ConnectionRefusedError`) → raises `"no TinyGPU server process found for <sock> (spawning is disabled here: xdist worker or NV_NO_SPAWN=1; see T4.40)."` | Same as xdist column, same message, `NV_NO_SPAWN=1` named instead. |
| **Alive + responsive** (bound, listening) | **No spawn** — `pre_existing=True` skips the i==0 spawn; first `connect()` succeeds immediately (server already has it bound). Proceeds normally. | **No spawn.** One connect attempt succeeds → proceeds normally. | Same as xdist column. |
| **Alive + unresponsive** (process running, socket not accepting — e.g. bound to a faulted GSP session per HANDOFF §2) | **No spawn** — `pre_existing=True`. Retries connect for the full 5 s budget, all fail, then raises `"a TinyGPU server (pid N, age A) is alive but not accepting connections -- it is probably bound to a faulted GSP session; do NOT pkill it under a live fault; see HANDOFF_2026-08-26.md §2 / T4.40."` | **No spawn.** One connect attempt fails → raises `"a TinyGPU server (pid N, age A) is alive but not accepting connections (spawning is disabled here: xdist worker or NV_NO_SPAWN=1; see T4.40)."` | Same as xdist column. |

The critical cell is "Alive + unresponsive": before this fix, **every** context spawned a sibling server
next to it (proven below) — the exact precondition ("≥2 servers alive, one bound to a faulted GSP
session") both 2026-08-26 host panics share.

## Diff rationale

**Liveness detection: `pgrep -f "<APP_PATH> server"`, not a pidfile.** The task brief offered both. A
pidfile is only as trustworthy as our own bookkeeping — and the servers piled up on the dock *today*
(T4.25's peak-15, T4.38's 12-from-one-`-n12`-run) were all spawned by code that never wrote one, so a
pidfile-based check would see "no server" for every real leaked process that predates this patch and
spawn a sibling anyway — precisely the bug this closes. `pgrep` reads the actual process table, so it
sees those too, with no migration story needed. Cost: one `pgrep` subprocess round-trip (~ms) per
`__init__` call, including the already-common case that finds nothing; negligible next to the existing
5 s retry budget. Ceiling (`ponytail`): matches on `f"{APP_PATH} server"` as a **substring/regex**
against the full command line — a real install path or a tempdir script path never contains regex
metacharacters that would over-match, so this isn't hardened against an adversarial `APP_PATH`. If
`pgrep` itself is missing, `subprocess.run` raises loudly rather than failing open to "no server found"
— a missing tool must not silently defeat a safety check.

**Snapshot `pre_existing` once, inside the flock, before the retry loop.** T4.25's flock already
serializes the whole connect-or-spawn sequence across threads/processes; the liveness check has to run
*after* acquiring it (not before), else two racers could each see "no server" before either spawns and
both decide to spawn — the exact bug being fixed, just moved one layer up. One check per call suffices:
if `pre_existing` was true, we never spawn for the rest of that call regardless of what happens next: if
false, we spawn at most once (i==0), same as T4.25.

**`proc is None` fully replaces the old "did we spawn" test.** In the original code `proc` was always
set by i==0 (spawn was unconditional), so the `if proc is not None` guard around kill+wait was dead-ish
defensive style. Now `proc` stays `None` for the whole loop exactly when `pre_existing` was true at
entry (spawning is skipped every iteration in that case), so `proc is None` in the `else:` clause is a
precise, single-source-of-truth signal for "we deliberately never spawned" — no need to re-check
`pre_existing` a second time or carry extra state.

**xdist/`NV_NO_SPAWN` path: one connect attempt, not the 5 s retry loop.** The brief says "raise
immediately." A probe that's explicitly forbidden from spawning has nothing to gain by waiting out a
budget sized for "give a spawn time to bind" — if nothing answers on the first attempt under this mode,
nothing ever will from this process. `test_xdist_worker_connects_to_a_responsive_server_without_spawning`
proves the single attempt isn't flaky by synchronizing the test's fixture server to be bound *before*
constructing the client (that's a test-fixture concern, not a production retry the real code needs).

**`RemoteCmd.PING` — deliberately not used.** "Alive" here means "a process matching `<APP_PATH> server`
exists" (pgrep); "responsive" means "a raw `connect()` succeeds" — both already well-defined by the
existing code (the retry loop already treats connect-success as sufficient to proceed, and the task
explicitly keeps "what a probe does after connecting" out of scope). An RPC-level `PING` after connecting
would be a heavier, semantically different check (does the *device*, not just the *socket*, respond) and
would change post-connect behavior, which is explicitly out of scope for (a).

**Existing T4.25 test assertions changed from `len(self.procs)` to `len(self.spawned_servers)`.** This
is a necessary, not cosmetic, adaptation: the fix legitimately shells out to `pgrep`/`ps`, so those two
tests' original "count every Popen call" assertion stopped meaning "count server spawns" the moment this
patch landed — proven by first running the change with the old assertions (see below): both T4.25 tests
failed on `self.procs` count, and `test_failed_spawn_is_killed_not_orphaned`'s `self.procs[0]` no longer
even indexed the right process (pgrep's Popen call now sorts before the real spawn). `self.procs` still
tracks everything for teardown; `self.spawned_servers` is a new list populated only by Popen calls shaped
like `[APP_PATH, "server", sock_path]` while `subprocess.Popen` is patched, i.e. spawns the code under
test actually made (excludes pgrep/ps diagnostic calls and the tests' own pre-spawned fixture servers,
which are created before the patch context and appended to `self.procs` directly). Both T4.25 tests'
*behavioral guarantee* — spawn exactly once, kill an orphan — is unchanged and still verified.

**Not touched:** `ensure_app()` — called unconditionally at the top of `__init__` in all modes, exactly as
before. It already no-ops once the app is installed (the universal precondition for any of this code
being reachable at all), so xdist/`NV_NO_SPAWN` probes don't gain a new side effect in practice; changing
its ordering or gating was not part of this scope.

## Open questions / what's left for T4.40 (b) and (c)

This patch is pure hygiene at the client's open path — it makes "two servers holding the same device"
much harder to reach from *this* process, but it is **not the fix for the panic mechanism itself**. Per
the revised RCA in HANDOFF_2026-08-26.md §2 (15:00 revision): both panics happened ~10 s after a *fresh*
client's `_early_ip_init` began clear→FLR→boot against a GPU whose previous GSP-RM session was never
confirmed unloaded — not at a stale-server teardown moment as first hypothesized. So even with (a) fully
in place, a *single* fresh client opening NV against a wedged prior session can apparently still panic
the host; (a) only removes the *additional* hazard of a second concurrent server/client doing so at the
same time. Concretely still open:
1. **(b)** Does `RemoteCmd.RESET` (the FLR in `TinyGPUDriver.cpp:191`) actually halt a wedged GSP-RM, or
   can it still DMA into its own now-stale queues during the new boot? `_early_ip_init` (`nvdev.py:127`)
   re-enables bus-master unconditionally and never re-checks GSP health before doing so.
2. **(c)** Nothing in this patch prevents a *single* legitimate client (no duplicate involved) from
   opening NV while a dock measurement or a live fault is in progress — that policy question is still
   fully open and orthogonal to server-count discipline.
3. This patch's error messages assume a human is present to read "do NOT pkill it under a live fault" —
   worth double-checking that no automated recovery path (a cron/health-check agent) reacts to this new
   `RuntimeError` by pkilling the named pid, which would defeat the warning's entire purpose.
4. Not verified against a real TinyGPU.app binary (out of scope / against the hard safety rules for this
   task) — only fake subprocess/socket fixtures. First real-hardware exercise of this path should be a
   deliberate, low-stakes check (e.g. one clean open) before it's trusted under a fault scenario.
