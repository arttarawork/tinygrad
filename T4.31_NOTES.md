# T4.31 — OSX docker compile-server container leak + transport hardening

Branch `task/T4.31-compile-transport` off fork master `cb05a6c64`. Fixes the leak that killed three
separate BEAM runs in T4.30 (see `BENCH_NOTES.md`'s "T4.30" section, in worktree `tinygrad-t430`) and
was blocking all nvcc-lane (`DEV=NV`) measurement work.

## 1. The actual spawn mechanism (confirmed empirically, not just read)

**The prompt's working hypothesis was wrong, and the evidence says so plainly:** spawns are
**worker-side**, one per BEAM candidate, not parent-side. `ALLOW_DEVICE_USAGE=0` doesn't block it
because constructing a `Renderer`/`Compiler` from a `Target` string needs no `Device[...]`/GPU access
at all — it's plain object construction.

**Root cause:** `Renderer.__reduce__` (`tinygrad/renderer/__init__.py:79`) is
`return self.__class__, (self.target,)` — every time a `Renderer` crosses a `pickle` boundary,
unpickling **reconstructs it from scratch** via `self.__class__(self.target)`. This is a deliberate,
working pattern: every other backend's `Compiler` also defines a cheap `__reduce__` for exactly this
reason (`ops_metal.py:73`, `compiler_mesa.py:65,108`, `compiler_llvm.py:82`, `compiler_qcom.py:25`),
because reconstructing those is free (no I/O). `NVRTCCompiler`/`NVPTXCompiler` are the odd ones out:
on OSX, `__init__` (`compiler_cuda.py:49,88`, pre-fix) unconditionally calls `self.server(...)`
(`device.py:321-323`), which does `subprocess.Popen(["docker", "run", ...])` — a real, expensive,
stateful side effect, executed **every time the object is reconstructed**, including every unpickle.

`beam_search` (`codegen/opt/search.py:141`) sends **one task per candidate** to the shared worker
pool: `(map if pool is None else pool.imap_unordered)(_try_compile, enumerate(candidates))`, and
`pool = get_worker_pool()` unconditionally (no `pool is None` short-circuit the way
`lower_and_compile` has for `len(todo)==1`). Each candidate is a `Scheduler` carrying a live
`.ren` (`Renderer`). Every one of those tasks gets pickled into the pool's task queue and unpickled
in a worker process — so **every single BEAM candidate spawns its own `docker run`, used to compile
that one candidate, then abandoned.** This is per-candidate, not per-worker-lifetime, which is why
`BEAM_MAX_TASKS_PER_CHILD=500` (T4.30's mitigation attempt) did nothing: that knob only throttles how
often a *worker process* recycles, and is completely decoupled from this per-task spawn.

**Empirical proof, with call-site attribution** (instrumented `Compiler.server()` temporarily —
logged `pid`, class, `(arch, args)`, and a 6-frame stack; reverted before this diff, not committed):

- *Isolated pickle round-trip* (`CUDARenderer(target)` then `pickle.loads(pickle.dumps(r))` x2, no
  GPU, no multiprocessing): **3 constructions -> 3 distinct docker spawns**, all same PID, call chain
  `NVRTCCompiler.__init__:49 <- CUDARenderer.__init__:403 <- <module>`. Proves the mechanism in
  complete isolation.
- *Modest real BEAM run* (`Device["NV"]`, one tiny 16x16-add kernel, `PARALLEL=2`, `amt=1`, real
  worker pool): pre-fix, **34 spawns** for a single `beam_search()` call (round-1 candidate count was
  only 14) — pid breakdown: 1 in the parent (`Device["NV"]` opening its renderer once, legitimate),
  ~30 split across two worker PIDs via the exact chain
  `NVRTCCompiler.__init__:49 <- CUDARenderer.__init__:403 <- get:387 <- worker:114 <- run:108 <-
  _bootstrap:320` (stdlib `multiprocessing/pool.py` internals — i.e. "unpickling a task in a pool
  worker"), plus a **third** worker PID appearing near the end (pool recycling —
  `BEAM_MAX_TASKS_PER_CHILD` default 16 — starting a fresh process whose first task also needs a
  fresh container). `docker ps -aq` peaked at **28 simultaneous** containers for this one tiny kernel.
  Scaled to a real model (dozens of kernels, each with several rounds of dozens of candidates), this
  is exactly consistent with T4.30's "143 containers within 15-25s" and "287 before crash."

**Secondary, compounding leak:** even bounding the per-task spawn, `multiprocessing.Pool`'s
`maxtasksperchild` recycling replaces a worker's OS process periodically; the outgoing worker's
subprocess (the docker CLI client) is never explicitly torn down (no `atexit`/`__del__`, unlike
`compiler_qcom.py:23`'s `__del__` which does `self.compiler_process.kill()` for its own equivalent
server) — an orphan every `BEAM_MAX_TASKS_PER_CHILD` tasks, on top of the per-candidate leak above.

## 2. The fix

Two files, both `tinygrad/`, ~56 lines total (below the 80-line stop threshold; not cross-cutting —
`device.py`'s change only touches the one shared method, `compiler_cuda.py`'s only touches the two
OSX-docker classes).

**`tinygrad/runtime/support/compiler_cuda.py`** — a process-local cache, `_server_cache: dict[(cls,
arch, args), Popen]`, checked by a new `_get_server()` before calling `self.server(...)`, used in
place of the direct call in both `NVRTCCompiler.__init__` and `NVPTXCompiler.__init__`. Each worker
process gets its own dict (separate interpreters under `SpawnContext`), so repeated unpickles of the
same `(class, arch, args)` in the *same* OS process reuse the *same* live docker container instead of
spawning a fresh one — turning "one container per candidate" into "one container per worker process,"
which was always the intended mental model. `proc.poll() is not None` invalidates a dead entry
(covers both the primary fix and doubles as opportunistic zombie reaping). A module-level
`atexit.register(_reap_servers)` kills any still-alive cached process when the process exits —
including a *recycled* pool worker's own graceful exit — closing the secondary leak (§1) too.
`_compile_with_retry()` wraps `compile_server()` and retries exactly once, respawning via
`_get_server()`, on a `CompileTransportError` (never on a plain `CompileError` — see below).

**`tinygrad/device.py`** — hardens `Compiler.compile_server()`: the write and both `_read_exactly`
calls are now wrapped in `try/except (OSError, CompileError)`, re-raised as a new
`CompileTransportError(CompileError)` naming the transport (`pid`, original exception) explicitly.
This replaces an uncaught `BrokenPipeError` (previously killed the whole process with an opaque
`errno 32`, no indication *what* died) and reclassifies the EOF case (`_read_exactly`, T4.14) — both
are transport deaths, never a legitimate "compile failed" signal (a real compile failure always
completes the wire protocol with a 0-byte reply; `_read_exactly(f, 0)` never touches the socket, so it
can never raise for that case). The pre-existing `raise CompileError("Compilation Error")` for a
truly empty reply is untouched, stays a plain `CompileError`, and is **never retried** — the retry in
`compiler_cuda.py` only catches `CompileTransportError` specifically. This affects `compiler_qcom.py`
too (same shared method) — strictly better error messages there for free; QCOM's own leak (identical
missing-`__reduce__` shape as NV, real subprocess in `__init__`) is a **flagged, not fixed** finding —
no QCOM hardware in this environment, out of scope for this task.

**Verified with the same instrumentation, before removing it:**
- Same modest-BEAM-run repro, post-fix: **34 spawns -> 3** (1 parent + 2 workers, `PARALLEL=2`) for
  an equivalent workload. `docker ps -aq` never exceeded the process count.
- Transport hardening, direct test: baseline compile OK; killed the live `compiler_process`
  externally; next `.compile()` call **transparently respawned and returned byte-identical output**
  (new pid); a genuinely bad CUDA source raised a plain `CompileError` (not
  `CompileTransportError`, confirmed by type), the server was **not** discarded/replaced, and the
  *next* valid compile on the same instance still worked — a real compile error doesn't get silently
  retried or corrupt the persistent server.

**Known residual gap (documented, not fixed — narrow and pre-existing):** `terminate_worker_pool()`
(`engine/worker.py:46-49`, called on `KeyboardInterrupt` only) uses `Process.terminate()` (SIGTERM),
which does not run `atexit` handlers by default — a container could still leak on a Ctrl-C mid-search.
Out of scope: rare, interactive-only, pre-existing for every other resource the workers hold too, and
fixing it generally would mean signal-handling changes cross-cutting enough to trip the STOP
threshold for a problem this task's crashes never actually exercised (all three deaths were during
normal execution, not user interrupts).

## 3. Acceptance test — `qwen3:8b DEV=NV JITBEAM=2 PARALLEL=6`, forced-fresh search

The exact cell that died three times (T4.30: 111 stuck containers + wedged `docker.sock`; identical
crash on a fresh colima; `BEAM_MAX_TASKS_PER_CHILD=500`+`PARALLEL=4` also wedged at 287 containers).

```
DEV=NV JITBEAM=2 PARALLEL=6 IGNORE_BEAM_CACHE=1 NO_COLOR=1 PYTHONPATH=. \
  /Users/artur/Documents/tinygrad/.venv/bin/python extra/benchmark_llm.py \
  --model ~/Library/Caches/tinygrad/downloads/758503d8d53a73f74e958e63fde121e2 \
  --prompt-tokens 512 --decode-tokens 128
```

`IGNORE_BEAM_CACHE=1` added deliberately (matches T4.30's own methodology) — without it, this exact
config's beam cache is already warm from T4.30's prior successful run and the test would trivially
"pass" without exercising the compile path at all.

**Result: completed cleanly, exit code 0.**

| | before (pre-flight) | during (peak sampling, 10 min) | after |
|---|---:|---:|---:|
| `docker ps -aq` | 0 | **5-7**, never higher | 0 |
| `TinyGPU.*server` count | 1 | 1 | 1 |
| swap used | 1110.69 MB | — | 1110.69 MB (flat) |

Container count matches the design exactly: `PARALLEL=6` workers + 1 parent = 7 max, and it never
exceeded that band across the full ~450s search (sampled every 15s). Pre-fix, the equivalent window
in T4.30 hit 143+ containers within the first 15-25 seconds alone.

**Output:**
```
load 6.433s
WARNING: BEAM found no viable candidate this round (1 tried, 0 failed: {}) for    2
warm 449.560s
prefill 113.836 tok/s 38.09 GB/s
decode 47.905 tok/s 295.61 GB/s
```
The one WARNING is T4.27's documented benign termination path (a round's last candidate deduped via
`seen_libs`/the 1000x-compute filter — the exception counter is empty, `{}`), not a compile/transport
flake — same signature T4.30 Cell 1 saw on its successful run.

**decode 47.905 tok/s** — consistent with (in fact +2.2% over, within BEAM-timing-search noise) the
last recorded number for this exact config, `BENCH_NOTES.md`'s 46.87 tok/s (T4.30's earlier,
cache-eviction-unblocked run) — confirms the fix changes *only* the transport, not what BEAM finds.
This also unblocks T4.30 cell 2's pending re-validation; the number above supersedes its "unconfirmed"
status.

**Bonus: warm time dropped from 1196.0s (T4.30's prior successful run of the same config) to 449.6s —
2.7x faster.** Not a headline claim (different session, not a controlled A/B), but directionally
expected: reused warm containers skip the `docker run` cold-start (image already resident, container
already up) on every candidate after the first, instead of paying it hundreds of times.

## 4. NAK lane and non-OSX paths — confirmed unaffected

- **NAK** (`DEV=NV:NAK`): structurally untouched — `NAKRenderer`'s compiler
  (`compiler_mesa.py`'s `NAKCompiler`) never spawns a subprocess and already had its own cheap
  `__reduce__`; zero lines of `compiler_mesa.py` touched. Verified live:
  `DEV=NV:NAK` sum + matmul both succeed (renderer confirmed `NAKRenderer`), `docker ps -aq` stayed
  at 0 before and after.
- **Non-OSX**: every change in `compiler_cuda.py` is inside an `if OSX:` branch already present
  pre-fix; the `else:` (native `nvrtc`/`nvjitlink`) branches are byte-identical to before. The
  `device.py` change touches only `Compiler.compile_server()`, which native NVRTC/nvjitlink never
  calls (it goes through `nvrtcCreateProgram`/`nvJitLinkCreate` directly) — only the OSX NV path and
  QCOM's non-aarch64 path call it, both unaffected in behavior beyond the improved error type.

## 7. PR-readiness verdict

**Ready.** Small, surgical, upstream-shaped (mirrors the existing `compiler_qcom.py:23` `__del__`
cleanup precedent and every other backend's cheap-`__reduce__` pattern already in tree — this isn't a
new architecture, it's NV catching up to a contract every sibling backend already honors). All gates
green. Real-hardware acceptance test — the exact cell that killed three prior sessions — now
completes, with container count staying in the single digits for the full run instead of climbing
into the hundreds, plus a real (if uncontrolled) 2.7x warm-time speedup as a side effect of not
cold-starting a container per candidate. NAK lane and non-OSX paths verified/reasoned unaffected.

No STOP condition triggered: the fix stayed at 56 lines (not >~80, not cross-cutting), and the leak
was definitively tinygrad's own doing (the `Renderer.__reduce__` / eager-subprocess-in-`__init__`
mismatch), not colima- or Docker-Desktop-specific — confirmed by reproducing the exact mechanism in a
zero-GPU, zero-multiprocessing pickle round-trip.

**Flagged but not fixed (separate task if wanted):** `compiler_qcom.py`'s non-aarch64 path has the
identical bug shape (real subprocess spawned in `__init__`, no custom `__reduce__`) — untouched here,
no QCOM hardware in this environment, and fixing it would mean importing `_get_server`-style caching
into a file this task has no way to verify against real hardware.
