# T4.49 — quantify abandoned-candidate interference in BEAM timings

File:line refs = fork branch `task/T4.49-beam-interference`, based on master `7ca254099` (same
commit T4.47_RCA.md cites; worktree `/Users/artur/Documents/tinygrad-t449`). Context:
`T4.47_RCA.md` §mechanism (`beam_search`'s device-timeout abandonment, `search.py:154-160`,
no cancellation, no sync).

**Question.** Does an abandoned BEAM candidate — still executing on the device after the host
gives up on it — contaminate the NEXT candidate's timed measurement (noise, systematic inflation,
different winners) enough to matter for the published NV-lane BEAM numbers?

**Verdict up front:** on the NV lane specifically, the literal contamination hypothesis (next
candidate's *measured value* includes the abandoned kernel's runtime) is **refuted** by both the
source-level wait-chaining and a structural fake proof — the hardware queue makes that
impossible. What *is* real: (a) `BEAM_DEV_TIMEOUT`'s millisecond-scale abandonment is **not
actually active on NV** at ms-scale — `can_recover=False` silently promotes every device-timeout
wait to the ~30s default, so this path only engages for genuinely pathological (near-fault-grade)
hangs, not routine 3x-slower candidates; and (b) when a genuine multi-second-plus hang *does*
occur, immediately-following candidates are at real risk of a false-abandonment cascade (dropped
from consideration, wall time burned) even though their own kernels never got to run — this is a
distinct failure mode from "corrupted timing," and it is rare, not routine. See Phase 2 for the
live A/B (does not exercise this path — no real hangs occurred, which is itself the expected,
on-target result given (a)).

## Phase 1.1 — source-flow mechanism (file:line)

### The abandonment path
`beam_search`'s per-candidate timing call and its handler (`codegen/opt/search.py:154-160`,
current baseline — matches T4.47's citation exactly):
```python
154   try: tms = _time_program(prg, var_vals, rawbufs, early_stop=beam[0][1]*3 if len(beam) else 1.0,
155                            allow_test_size=allow_test_size, clear_l2=hasattr(dev, 'invalidate_caches'),
156                            dev_timeout=getenv("BEAM_DEV_TIMEOUT", 1))
157   except Exception as e:
158     if BEAM_DEBUG: print(f"BEAM failed for opts: {candidates[i].applied_opts}\n{e}")
159     if isinstance(e, RuntimeError):
160       fails[type(e).__name__] += 1
161       continue
162     raise
```
`_time_program` (`search.py:39-46`) turns `early_stop` into a millisecond timeout ONLY when
`dev_timeout` is truthy: `timeout = int(early_stop * 1e3) if dev_timeout and early_stop is not
None and early_stop < math.inf else None` — this `timeout` is threaded through
`time_call(timeout=)` (`engine/realize.py:291`) → `ExecContext.timeout` → `exec_kernel`
(`engine/realize.py:180`, `rt(..., wait=ctx.wait, timeout=ctx.timeout)`) → `HCQProgram.__call__`
(`runtime/support/hcq.py:359-381`).

Candidate timing runs **sequentially, single-process, single-threaded** on the main process: the
`multiprocessing.Pool` (`beam_pool`) only ever runs `_try_compile` (CPU-only codegen; workers set
`ALLOW_DEVICE_USAGE=0` in `_init_worker`, `search.py:83-85`, so they cannot open a device). All
device execution/timing happens in the `for i, proc, exc_name in (...).imap_unordered(...)` loop
in the main process (`search.py:141`), one candidate at a time, on the one `dev = Device[...]`
object for the whole search. This rules out any cross-process concurrent-device-access path —
the only device-serialization question is within a single process/device.

### `HCQProgram.__call__` always chains new work behind the previous signal
```python
372   q = unwrap(self.dev.hw_compute_queue_t)().wait(self.dev.timeline_signal, self.dev.timeline_value - 1).memory_barrier()
374   self.dev.prof_exec_counter += 1
375   with hcq_profile(self.dev, queue=q, desc=self.name, enabled=wait or PROFILE) as (sig_st, sig_en):
376     q.exec(self, kernargs, global_size, local_size)
378   q.signal(self.dev.timeline_signal, self.dev.next_timeline()).submit(self.dev)
380   if wait: self.dev.synchronize(timeout=timeout)
```
Every single kernel launch (BEAM candidate or not) builds ONE queue object containing, in order:
`wait(timeline_signal, timeline_value-1)` → `timestamp(sig_st)` (via `hcq_profile`'s
`queue.timestamp(st)` before `q.exec`) → `exec(kernel)` → `timestamp(sig_en)` → `signal(new
value)`, then submits it as one unit. The abstract contract (`runtime/support/hcq.py:110-133`,
docstrings, not just convention) is explicit:
- `timestamp()`: "records the current time in a signal **after all previously enqueued commands
  are completed**"
- `signal()`: "sets the signal to the given value, **ensuring all previous operations are
  completed**"
- `wait()`: "halts execution until the signal is greater than or equal to a specific value"

So candidate N+1's own `wait` targets exactly the value candidate N's queue will signal on
completion (`next_timeline()` hands out sequential values; `timeline_value - 1` at N+1's launch
time is N's target — `hcq.py:443-445`). Because N+1's `timestamp(sig_st)` is enqueued into the
*same* queue object, *after* that wait, it cannot be processed until N's completion signal fires.

**NV-specific hardware confirmation (not just the abstract contract):** `NVComputeQueue._submit`
always submits to `dev.compute_gpfifo` (`ops_nv.py:230`, `:719`) — ONE persistent GPFIFO ring per
device, shared by every candidate timed on it, processed strictly in submission order by the GPU
command processor (classic pushbuffer semantics: `_submit_to_gpfifo` writes one ring entry and
rings the doorbell, `ops_nv.py:152-164`). `wait()` compiles to `NVC56F_SEM_EXECUTE
operation=acq_circ_geq` — a hardware semaphore-acquire (`ops_nv.py:111-113`). `signal()`/
`timestamp()` compile to `NVC56F_SEM_EXECUTE operation=release release_wfi=en` (`ops_nv.py:117,
213,220`) — `release_wfi=en` is NVIDIA's own "wait-for-idle" flag: the command processor holds the
release (and its timestamp) until the engine has gone idle, i.e. until the preceding kernel grid
has actually retired. This is a hardware-level guarantee, not an emergent property of scheduling.

**Consequence:** candidate N+1's *measured* window (`sig_en - sig_st`) cannot start before
candidate N's kernel completes, on NV, regardless of whether the host waited for N. The literal
hypothesis in this task's framing — "the next candidate's measured time provably includes it" — is
**structurally impossible** via the normal exec path. See Phase 1.2 for a live proof.

### The load-bearing correction: `BEAM_DEV_TIMEOUT` does not actually fire at ms-scale on NV
`HCQCompiled.synchronize` (`hcq.py:428,436`):
```python
436   try: self.timeline_signal.wait(self.timeline_value - 1, timeout=timeout if timeout is not None and self.can_recover else None)
```
`self.can_recover` gates whether the CALLER's `timeout` (BEAM's `early_stop*3` ms) is honored at
all. Repo-wide, `can_recover=True` is set in **exactly one place**: `ops_amd.py:1049,
can_recover=self.is_am()` (AMD's AM/PCI driver path only — a device family this project has
explicitly descoped, per `CLAUDE.md`). **NV never sets `can_recover`** — grep confirms zero hits
in `ops_nv.py`; `HCQCompiled.__init__`'s default is `can_recover:bool=False`
(`hcq.py:394`/`423`). This is not an oversight: `ops_nv.py:34-42`'s `_fault_recovery_hint`
comment (T4.23/T4.37 lineage, already in this baseline) states it explicitly: *"NV never sets
can_recover (hcq.py), so there's no safe in-process reset."* Confirmed live under the project's
own MOCKNV recipe (Phase 1.2): `Device["NV"].can_recover == False`.

So on NV, `timeout if timeout is not None and self.can_recover else None` **always** evaluates to
`None`, and `HCQSignal.wait` (`hcq.py:283,291`) falls back to `getenv("HCQDEV_WAIT_TIMEOUT_MS",
30000)` — **30 real seconds** by default, not BEAM's `early_stop*3` ms (typically low
single-digit-to-tens of ms for a normal candidate pool). `BEAM_DEV_TIMEOUT=1`'s intended
ms-scale abandonment of "candidates ≥3x slower than the best" is therefore **effectively inert on
NV** — it is not a routine, frequent event. The `RuntimeError("Wait timeout...")` path on NV can
only actually fire for a candidate that hangs for ~30 seconds (or whatever
`HCQDEV_WAIT_TIMEOUT_MS` is set to) — which is squarely in "genuinely faulted/pathological
kernel" territory, matching T4.47's own observation that every wait-timeout it traced back
correlated with a real device fault, not ordinary slowness. This refines (does not contradict)
T4.47 §mechanism's point 1: abandonment is "routine" **by design**, and would be routine on a
`can_recover=True` device (AMD/AM) — on NV it is gated behind a ~1000x larger threshold than the
BEAM value would imply, so it is rare in practice.

### The cascade, when a genuine hang does occur
Because N+1's own `wait` chains behind N's pending signal (previous section), and the host does
not wait for N before submitting N+1 (`search.py:157-161`'s `continue` is immediate), N+1's own
`dev.synchronize(timeout=...)` call is *also* blocked on N's completion. `HCQSignal.wait`
(`hcq.py:283-295`) resets its own timeout clock on **any** observed progress of the signal value
(`if self.value != prev_value: start_time = ...`) — so a candidate queued behind a *fast-finishing*
predecessor is not penalized. But a candidate queued directly behind a still-hung one sees no
progress at all until the hang resolves; if N's hang outlasts N+1's own wait budget, N+1 raises the
identical `RuntimeError("Wait timeout...")` and is `continue`d — **dropped from consideration —
even though N+1's own kernel never started executing.** This can chain to N+2, N+3, ... for as
long as N stays hung. This does not corrupt any *recorded number* (a dropped candidate contributes
no row to `timed`), but it can: (a) silently shrink/bias the candidate pool for that beam round
(good candidates excluded purely by queue position, not by their own merit — a possible source of
different winners), and (b) burn wall time roughly proportional to (hang duration / per-candidate
timeout) — consistent with T4.47's own "grinding runs in a faulted state... run 2b ground ~10 min
post-fault" observation. This is the same phenomenon T4.47 already characterizes as a fault storm,
seen from the timing-interference angle requested here — not a new, independent contamination
source, and (per the previous section) gated behind the same rare, ~30s-hang precondition.

### Minor/second-order note: `clear_l2`
`_time_program`'s `clear_l2` (`search.py:154-156`, `hasattr(dev, 'invalidate_caches')`) issues an
NV `rm_control` ioctl directly (`ops_nv.py:834-839`, `NV2080_CTRL_CMD_FB_FLUSH_GPU_CACHE` /
`...BUS_FLUSH_WITH_SYSMEMBAR`) — a synchronous RM call, **not** enqueued on `compute_gpfifo`. It is
therefore not gated by the wait-chain above. If a prior candidate is genuinely still resident and
touching memory while this flush runs, cache-state purity for the next candidate's measurement
could be marginally affected. This only matters during the same rare hang window as the cascade
above, is third-order relative to it, and was not chased further (budget).

## Phase 1.2 — structural fake proof

Ran under the project's established GPU-free MOCKNV recipe (`TASKS.md:86`,
`OCELOT_PATH=.venv/lib/libgpuocelot.dylib DEV=MOCK+NV:PTX`) — the REAL `ops_nv.py` /
`support/hcq.py` code (real `HCQProgram`, real `HCQCompiled.synchronize`, real
`NVComputeQueue`/GPFIFO path), gpuocelot-emulated engine, no physical GPU. Script:
`extra/t449/fake_proof_wait_chain.py`. Live-confirmed `Device["NV"].can_recover == False` under
this recipe too.

Reproduces exactly what BEAM's abandonment does at the raw `HWQueue` level: submit a candidate
whose completion is deliberately withheld ("hung"), abandon it via a short wait exactly like
`search.py:157-161`, then — with no cancellation, no sync — submit and time the next candidate.
(Test pattern lifted from the existing `test/device/test_hcq.py::test_wait_late_set`, which
already establishes withheld-signal + timeout-then-resolve as the project's own way to exercise
this.)

Full run output (`HCQDEV_WAIT_TIMEOUT_MS=300` pinned so the demo doesn't require a real 30s wait —
must be set before interpreter start, `tinygrad.helpers.getenv` is `@functools.cache`d so mutating
`os.environ` mid-script is silently inert):

```
[setup] iface=MOCKIface can_recover=False HCQDEV_WAIT_TIMEOUT_MS=300
[claim 2] synchronize(timeout=50) actually raised after 300 ms (not ~50 ms)
[A] submitted candidate A (target=4), gated on fake_signal>=1 (withheld)
[A] abandoned after 50 ms host wait; A's kernel is still 'running' (fake_signal unresolved)
[B] submitted candidate B (target=5) immediately after abandoning A: submit took 0.04 ms (non-blocking)
[B] confirmed: sig_st/sig_en still unset (0) -- B has not executed while A is still pending
[cascade] B's own wait ALSO timed out after 50 ms, though B's kernel never ran
[drain] once A resolved, B drained 0.1 ms later (total wall cost since B was submitted: 50.0 ms)
[claim 3] B's measured duration (sig_en - sig_st) = 6.75 us -- does NOT include A's withheld runtime (A hung for 50 ms of wall time)

VERDICT: no overlap, no measured-value contamination (claims 1/3 hold); can_recover=False makes
BEAM_DEV_TIMEOUT a no-op on NV at ms-scale (claim 2 holds); a genuinely hung candidate DOES risk
cascading false 'Wait timeout' drops on immediately-following candidates, at real wall-clock cost,
without corrupting any recorded timing number.
```
(A harmless, expected cosmetic warning prints at interpreter exit —
`NV synchronization failed before finalizing: Wait timeout: 300 ms!` — from
`HCQCompiled.finalize()`'s best-effort teardown sync (`hcq.py:501-503`, "Try to finalize device in
any case", swallows `RuntimeError`); an artifact of pinning `HCQDEV_WAIT_TIMEOUT_MS` process-wide
to 300ms for the demo, not a defect in the proof.)

Every assertion in the script passed (it would `raise SystemExit`/`AssertionError` on any
violation of claims 1-3). This is a clean, non-contrived proof: it exercises the actual production
`HCQProgram`/`HCQCompiled`/`NVComputeQueue` code, not a hand-rolled fake device.

### Verdict

**Zero abandonments occurred in either run** — expected, and itself a confirmation of the Phase 1
finding: on healthy NV hardware with `can_recover=False`, `BEAM_DEV_TIMEOUT`'s ms-scale abandonment
essentially never fires (would need a ~30s hang), and this was a healthy GPU with no faults. This
run therefore cannot and does not exercise the rare cascade mechanism characterized in Phase 1 —
by construction (the gating protocol requires a healthy GPU), no live A/B can. What it *does*
confirm: candidate timing distributions are statistically indistinguishable between the two runs
(mean/median/max all within noise), and run B's extra `synchronize()` call before all 3333
candidates cost **no measurable wall time** — B's total search time was 13% *faster* than A's, well
within ordinary run-to-run system variance (thermal/scheduler/clock-boost state), not a cost of
syncing. This matches the Phase 1.2 fake proof: syncing an already-idle device (the normal case,
confirmed here — nothing was ever left running) is near-free.

The one number that looks alarming in isolation — **18/25 kernels picked different `applied_opts`
between A and B** — is **not attributable to the sync instrumentation or to abandonment
interference**: there were no abandonments in either run for it to be caused by, and the raw timing
distributions are essentially identical between A and B. The honest explanation is ordinary BEAM
measurement noise across two independent fresh searches: several of the diffs are between
near-tied alternatives (e.g. `LOCAL axis=0 arg=4` vs `arg=2`, `GROUP arg=16` vs `arg=8`) — exactly
where sub-microsecond timing jitter (thermal state, OS scheduling, GPU clock boost) flips which
candidate's `min(tms)` wins. **This was not isolated with an A/A control** (budget did not allow a
third run) — that is the natural follow-up if this number needs to be pinned down further, but it
is a property of BEAM search generally, not of this task's sync instrumentation specifically: with
zero abandonments in either run, there is no mechanism from Phase 1's analysis that could make
`sync_before` cause pick differences.

**Bottom line:** on the NV lane, abandoned-candidate interference is **not material** for the
published BEAM numbers under normal (healthy-hardware) operation — confirmed by source analysis
(structural impossibility of measured-value overlap; `BEAM_DEV_TIMEOUT` inert at ms-scale on NV),
a structural fake proof, and this live A/B (zero abandonments, indistinguishable timing
distributions, no wall-time cost to defensive syncing). The only place interference is real is the
rare genuine-hang cascade (Phase 1's cascade mechanism), which is a fault-adjacent event, not a
routine search-noise source — the same phenomenon T4.47 already tracks as a fault storm.

## Recommendation

**Immaterial for the routine case — no code change needed on the BEAM search path for the
timing-contamination question this task asked.** The one place worth a follow-up is the rare
cascade: if T4.47's F1 (drain-before-verdict) or F2 (first-sleep drain) land for fault-detection-
latency reasons, they would *also* close this task's cascade risk as a side effect, since both stop
`beam_search` from silently grinding through chained false-timeouts behind a genuinely wedged
device. No new fix is needed specifically for timing contamination — the wait-chaining mechanism
already prevents the literal hypothesis this task set out to test. (F1-F3 from T4.47 remain about
**fault detection latency**, a related but separate concern from this task's timing-contamination
question — this task does not add to their urgency, it just confirms they'd incidentally cover the
cascade too.)

## Caveats

- Single A/B run pair = indicative, not statistically powered. qwen3:8b/512-context is a light
  search; heavier searches (larger models, wider BEAM) could exercise the hang path more.
- Phase 2 targets the **common case** (healthy hardware, no faults) by construction (the gating
  protocol requires a healthy GPU) — it cannot, and is not intended to, exercise the rare
  genuine-hang cascade characterized in Phase 1. That mechanism's existence rests on Phase 1's
  source analysis + the GPU-free structural proof, not on Phase 2 data.
- This does **not** claim to explain T4.15's multiplier decay; no data collected here speaks to
  that.
