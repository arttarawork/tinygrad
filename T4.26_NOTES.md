# T4.26 — IQ3_XXS dequant redesign: candidate evaluation and verdict

Gates T4.22's upstream PR (closes #17316). T4.22 fixed the byte blowup (LUT gather materializing
all MoE experts) by replacing Tensor-gathers with compile-time `select_const` decision trees;
IQ4_XS's 16-leaf tree is a clean win everywhere, but IQ3_XXS's 256-leaf tree regressed no-BEAM
wall-clock 2.4-13.6x (T4.22, synthetic) and, at real 40-block model scale, stayed 2.18-2.6x
*slower* than the original buggy over-fetch baseline even fully BEAM'd (T4.29) — the synthetic
"net win with BEAM" verdict did not survive contact with the real model. This memo evaluates four
candidate redesigns and reports one implemented, measured change.

## Verdict up front

**No candidate reverses T4.29's verdict.** IQ3_XXS should NOT go upstream yet. One candidate (B,
below) is a real, zero-risk, ~1.8-3.1x tightening of the *already-shipped* `select_const` tree —
implemented and kept on this fork — but it does not close the gap to the pre-fix baseline's
no-BEAM speed, let alone to what BEAM would need to beat at real scale. Candidates A/C/D are
refuted or out of scope; see below. **PR recommendation: ship IQ4_XS alone upstream now; keep
IQ3_XXS's byte-correctness fix + this tightening fork-local (BEAM'd-only), revisit upstream only if
a genuine fused-gather primitive appears (A/C).**

## Methodology

All measurements: `Transformer.from_gguf` + `.generate()` on a synthetic gpt-oss GGUF mirroring
`test/unit/test_llm_gptoss.py::TestGPTOSSDecodeByteBudgetIQ`'s exact dims (DIM=HIDDEN=256,
N_EXPERTS=32, EXPERTS_PER_TOK=4, NUM_BLOCKS=2, ggml_type=18, random structurally-valid block
bytes — same config T4.22/T4.15 used for their own synthetic IQ3_XXS harness). Script:
`t426_iq3_bench.py` (ad hoc, not committed, left in the session scratchpad). Per-call wall time
over prefill + 6 decode calls (call 0 = prefill, call 1 = JIT capture, calls 2-6 = steady state),
plus `GlobalCounters.global_mem` on one more steady-state call. Three-way A/B via `git stash`
(T4.22's own documented method) and a temporary swap-in of the pre-T4.22 commit's literal
gather-based `ggml_type==18` block (`git show 5b93d2c9c^:tinygrad/llm/gguf.py`), each restored
immediately after measurement. No device other than METAL/CPU touched (hard rule: no GPU/dock this
session). Cross-check: the original-gather-vs-shipped-tree ratio measured here (2.66x slower
no-BEAM steady-state on METAL) matches T4.22's own isolated-microbench ratio (2.67x) almost
exactly, despite this harness measuring the whole model step, not just the dequant op — good
evidence the harness is faithful.

## Candidate A — plain indexed LOAD instead of a one-hot-mask REDUCE

**Mechanism checked, not merely assumed.** Read `Tensor.__getitem__`'s advanced-indexing lowering
(`tinygrad/mixin/op.py:104-138`): every tensor-valued index — one dim or several — goes through
`i._one_hot_along_dim(...)` then `(mask.where(x, 0)).sum(sum_axis, ...)`. There is no "linear
address, no mask" path for a single advanced index (the file's one linear-indexing shortcut,
lines 108-116, only fires for *multiple consecutive* int-shaped tensor indices, and even then it
recurses back into the same one-hot path since after collapsing it's still one advanced index).
`Tensor.gather` (`mixin/op.py:1026-1044`) is the **same** one-hot-mask-then-sum pattern. ONNX's
`Embedding`/`GatherElements`/`Where`-index paths (`tinygrad/nn/onnx.py:612,929,952`) are too. I
grepped the whole tree for an alternative gather primitive; there isn't one — every value-dependent
lookup in this codebase funnels through a REDUCE over a one-hot mask, which is exactly what
`buffer_in_reduce` (`schedule/rangeify.py:258-266`) exists to catch when the masked table is a real
buffer. So `weight[sel]`'s own gather doesn't "avoid" the check via a different lowering — it
*triggers the same lowering*, but as the outermost consumer, not nested inside another bufferize
candidate's `src`, so it's the `idx` under evaluation, not part of the `src` being cost-checked.

**Is a true indexed load even representable?** `tinygrad/uop/spec.py:84`'s `Ops.INDEX` validator
only requires int-dtyped (or masked-invalid) address components — it does not forbid an address
expression that itself contains a `LOAD` (a genuine data-dependent/gather address, `buf[idx_buf[i]]`
in C terms). So the IR isn't the blocker. But nothing in this codebase — Tensor level or UOp level —
constructs one; there is no precedent to extend, and inventing this from scratch means teaching
rangeify's scheduler to place two dependent buffer reads in one fused kernel where the *value* of
one read selects the *address* of the other — a different, harder scheduling problem than anything
`remove_bufferize` currently solves (which only ever substitutes affine/range-indexed accesses).
That's a multi-week core-compiler feature, not a T4.26-scope change, and it's the same feature
candidate C hopes upstream already built (it hasn't — see below). **Refuted as in-scope; flagged as
the real general fix, worth an upstream issue, not a PR from this task.**

## Candidate B — bit-plane / structural decomposition of the 256-entry grid

**Checked the actual grid data, not just the docstring's claim.** `_ggml.iq3xxs_grid`'s 256 words,
unpacked into 4 bytes each, use only **8 distinct byte values**: `{4,12,20,28,36,44,52,62}`. Values
0-6 are affine (`4+8i`), but value 7 breaks the pattern (62, not 60) — **no closed-form formula**
recovers a component from its 3-bit slot, confirming the code's own comment ("not bit-decomposable
like the parity above"). Checked whether code order groups by output value (which would allow a
shallower tree over ranges instead of individual codes) — it doesn't; codes with the same v0 aren't
contiguous or evenly spaced. So the *ambitious* reading of candidate B (a genuine bit-formula, or a
per-component tree shallower than 256-leaf) is **refuted** — this is a curated combinatorial
codebook (same class as an E8-lattice VQ codebook), not an arithmetic one, exactly as T4.22 already
concluded.

**A real, much smaller lever survived: eliminate 4x redundant tree construction.** The shipped code
calls `select_const(code, grid_vals[c::4])` **four separate times** (once per interleaved
sub-value, `c` in 0..3), each building an independent 255-node balanced binary tree over the same
256-entry space — 1020 total select nodes — to extract four bytes that are **already packed
together** in the raw grid word (`_ggml_iq_grid`'s own docstring: "ggml packs each iq grid entry as
N bytes ... in a single word"). Selecting the packed `uint32` row **once** (255 nodes) and
unpacking via a cheap post-select shift+mask (`packed.rshift(8*c).bitwise_and(0xFF)`) is
definitionally the same value per component — proven bit-exact two ways: (1) an exhaustive
pure-Python check over all 256 codes comparing the old per-component derivation against the new
packed-then-unpack derivation (zero mismatches), (2) the existing `test/unit/test_gguf.py`
gguf-py-ground-truth tests (`test_dequantization_iq3_xxs`, `test_gguf_gemv_iq3_xxs`, both grid
tests) and `TestGPTOSSDecodeByteBudgetIQ` all pass unmodified. **Dodges `buffer_in_reduce`
identically to the shipped design** — the packed value is still selected via `.where()` over
Python-int constants, zero buffer reads, zero REDUCE ops in the expression; confirmed by the byte-
budget test still asserting near-gathered bytes (962,564 B, actual/gathered=1.599x, unchanged from
the shipped tree). **Implemented** (`tinygrad/llm/gguf.py`, `ggml_type==18` block) and is the one
change this session ships — see Verdict and Numbers above for the measured 1.7-3.1x win. It is a
tightening of the accepted design, not a new one: same idiom, 3 fewer lines than before, no new
risk surface.

## Candidate C — does upstream's new_rangeify already fix the root cause?

**Checked directly, not inferred from commit titles.** Diffed our fork's
`tinygrad/schedule/rangeify.py` (`remove_bufferize`/`buffer_in_reduce`, the exact function T4.22
identified) against upstream tip `ecf79e260` (fetched as `FETCH_HEAD` in
`/Users/artur/Documents/tinygrad-dock`, read-only `git show`): **byte-for-byte identical** — zero
diff on the isolated function body. Also diffed `tinygrad/mixin/op.py`'s `__getitem__` advanced-
indexing block: **also byte-for-byte identical**. The two commits named in the brief
(`a5678317c` "split rangeify to prepare.py", `dc04c7820` "lil fixes from new_rangeify") are a pure
file-reorganization — `pm_mops`, `found_after`, `fix_store_hazard`, `split_reduceop`,
`resolve_function`, `expand_bitcast` and friends moved into a new `schedule/prepare.py` — the
fusion-refusal mechanism itself, and the gather-lowering that trips it, are untouched as of
upstream's current tip. **Refuted: no free ride.** The general fix (candidate A) has not landed
upstream either; if/when it does, re-run this same diff before reconsidering an IQ3_XXS PR.

## Candidate D — relax `buffer_in_reduce` for small constant tables

**Evaluated honestly against T4.22's own prior rejection, not re-litigated from scratch — and
independently corroborated by this session's own read of the code.** Two separate problems:

1. **The only existing relaxation path doesn't activate here, and T4.22 already proved it
   empirically.** `remove_bufferize`'s `PCONTIG > 2` branch (`schedule/rangeify.py:258-266`) is
   structurally built around *local/shared-memory* tiling (`AddrSpace.LOCAL` `STAGE` ops,
   `local_indexes`, `is_pcontig`/`is_subs` partitioning) — an attention-kernel shape, not a global
   constant-table gather. T4.22's own session confirmed this isn't just a theoretical mismatch:
   **`PCONTIG=0/2/3` gave byte-identical schedules** on this exact IQ3_XXS case — the path never
   engages regardless of the flag. Re-deriving a *new*, purpose-built relaxation (rather than
   reusing PCONTIG's) doesn't dodge problem 2.
2. **Even a correct-looking new relaxation would produce a reduce-feeds-reduce fusion, and that
   shape is already proven wrong in this codebase.** Allowing `buffer_in_reduce` to say "fuse
   anyway" for a small table means inlining a REDUCE (the one-hot-mask-sum gather over the 256-entry
   table) *inside* the consumer's own REDUCE (the MoE expert-selection sum) — nested reduces. T1.7
   (`TASKS.md` line 411, `PCONTIG_ATTN_NOTES.md`) already found this exact shape numerically wrong
   elsewhere in this codebase: 0.52 max abs error vs numpy on softmax/SDPA, masked for a long time
   only because the schedule cache's key ignored `PCONTIG` (fixed by T4.9), making the fusion tests
   self-referential rather than a real check. Building a *correct* general nested-reduce fusion is a
   rangeify-correctness research project on its own, not a bounded T4.26 change, and would compete
   with an in-flight upstream rangeify rewrite (#17493 per T4.22's notes) most likely to conflict
   with exactly this function. **Refuted — same conclusion as T4.22, now with this session's own
   code-reading corroboration of why the PCONTIG path structurally can't reach this case.**

## PR recommendation

- **Ship IQ4_XS's fix upstream now, alone.** Zero caveats found anywhere across T4.22/T4.15/T4.26:
  clean win on bytes, compile, and no-BEAM runtime, every lane tested (CPU/METAL/NAK/nvcc).
- **Do not ship IQ3_XXS's fix upstream yet.** Its byte-accounting correctness is real and should
  stay on this fork (production here always runs `JITBEAM>=1`), now with the T4.26 packed-select
  tightening applied (1.7-3.1x cheaper to compile, 1.8-2.0x faster no-BEAM, same byte win, same
  bit-exactness). But upstream's default is `BEAM=0`, and even this tightened version is still
  ~1.5x slower than the pre-fix baseline's no-BEAM path on the *same tiny synthetic harness* T4.22
  used to justify "net win with BEAM" — a bar T4.29 already showed collapses at real 40-block model
  scale (2.18-2.6x slower even fully BEAM'd). A PR carrying IQ3_XXS today would trade a real bug
  (88 GB/token) for a real regression on upstream's actual default config, on top of a real one-time
  compile-cost tax on shared CI runners (T4.28) — smaller now (3.1x cheaper) but not eliminated.
- **The PR text for IQ4_XS-alone should explicitly scope out IQ3_XXS**, citing #17316's IQ3_XXS
  symptom as "root-caused, fix prototyped, held pending a no-BEAM-safe redesign" so a reviewer
  doesn't wonder why only one of the two types named in the issue is fixed.
- **Revisit IQ3_XXS for upstream when, and only when,** either (a) a genuine data-dependent gather
  primitive lands in tinygrad's IR/scheduler (candidate A's real fix — worth its own upstream issue,
  not attempted here), or (b) upstream's rangeify rewrite independently starts fusing small-buffer
  gathers into reduces (candidate C — confirmed absent as of `ecf79e260`; cheap to re-check on
  future syncs via the same two-function diff this session used).
