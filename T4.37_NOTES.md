# T4.37 — quiesce PCI bus-master on NV fault (closing the 2026-08-26 DART panic)

Code + unit tests only. No GPU touched: no `DEV=NV*`, no device open, no `pkill`, no `launchctl`.
Worktree `/Users/artur/Documents/tinygrad-t437`, branch `task/T4.37-quiesce-on-fault`, base
`cb05a6c64`. Implements the fix designed in `T4.36_DART_PANIC.md` (read in full first).

## 0. The mechanism this closes (recap)

GSP-RM's message queues live in host sysmem (`support/nv/ip.py:367`). A GPU MMU-fault storm makes
GSP DMA fault events into those queues at high rate. Nothing in tinygrad cleared PCI bus-master on
the fault path, so if the server (TinyGPU.app) died while GSP was still alive — e.g. via the T4.23
hint's `pkill` — its DEXT tore down the client's DMA mappings while the GPU could still reach them:
one stray GSP DMA into a now-unmapped IOVA → `AppleT8110DART … REQUIRE failed` → host panic.

**Alternative DART-panic cause considered and ruled out:** upstream PR #15606 (closed) found DART
panics on this same stack caused by stale DEXT instances / init performed out of order, mitigated by
resetting `NV_PBUS_BAR1_BLOCK` (and, on `fmc_boot` chips, `NV_VIRTUAL_FUNCTION_PRIV_FUNC_BAR1_BLOCK_LOW_ADDR`)
during GSP bring-up. That reset is already unconditionally present in this tree, in
`NV_GSP.init_hw()` (`support/nv/ip.py:512-513`, runs on every GSP init right after
`NV_VGPU_MSG_EVENT_GSP_INIT_DONE`) — so that specific cause is already covered here and is not what
T4.36 hit; T4.36's mechanism (bus-master left enabled through a live-GSP mapping teardown) is a
different, still-open gap, which is what this task closes.

Sites B/C/D all use the exact `_early_ip_init` idiom named in the task:
```python
self.pci_dev.write_config_flush(pci.PCI_COMMAND, self.pci_dev.read_config(pci.PCI_COMMAND, 2) & ~pci.PCI_COMMAND_MASTER, 2)
```
**Precedent: upstream PR #16007** ("revoke bus_master during reset", merged 2026-05-01) introduced
`write_config_flush()` (write + read-back, so a remote CFG_WRITE RPC is forced to land before anything
else proceeds) and this exact clear-before-reset/set-after pattern in both `nvdev.py` and `amdev.py` —
the `_early_ip_init` lines cited above ARE that PR. T4.37 is that precedent's extension to the *fault*
path: the pattern previously only ran around an explicit reset; nothing ran it when a fault was merely
detected and no reset had happened yet. All three sites use `write_config_flush`, never bare
`write_config`, for the same reason #16007 does: on the remote path the write is itself an RPC, and
only the read-back forces it to actually land before the function returns/raises.

B and C reach `pci_dev` directly (`self.pci_dev` — `PCIIfaceBase.__init__` sets it on the iface
itself, the same object `NVDev.__init__` also stores as `self.pci_dev`; either attribute path reaches
the identical `PCIDevice`/`RemotePCIDevice` instance). D is on `NVDevice`, not `PCIIface`, so it goes
through `self.iface.pci_dev`, guarded by `self.is_nvd()` (see §3).

Total diff excluding tests: 21 added / 5 removed lines — under the ~40-line budget.

## 2. The `_fault_recovery_hint` rewrite (task item 2)

Old hint told the user to `pkill -f 'TinyGPU.*server'`. That instruction is the panic trigger. New
hint (`ops_nv.py:41-42`):

> " NV device is in an unrecoverable fault state (PCI bus-master now cleared) -- start a FRESH CLIENT
> to recover (it performs a controlled reset). Do not `pkill` the server while a fault is live."

"Fresh client" = start a new tinygrad process/session against the same (still-running) server; its
`_early_ip_init` (`support/nv/nvdev.py:113-127`) does the controlled `RemoteCmd.RESET`
(`support/system.py:413`) around clearing/re-setting MASTER itself — no need to kill the server at
all. I did not attempt an in-process reset shortcut (task said evaluate, don't build): `NVDev` has no
existing "re-run `_early_ip_init` on a live object" entry point, and welding one together from
`_early_ip_init`'s internals (WPR2 check, `init_sw`/`init_hw` on `flcn`/`gsp`, GSP client re-alloc)
is exactly the "large re-init refactor" the task said to avoid. **Recommendation for later**: a
`NVDev.recover()` mirroring AM's `recover()` (`support/am/amdev.py:232-238`) is the natural shape if
someone wants in-process recovery — but AM's own version is "clear `is_err_state`", not a real
reset, so even that precedent doesn't buy a cheap safe path here.

## 3. `is_remote()` decision: **not gated — clear unconditionally**

`PCIIfaceBase` backs both a local `PCIDevice` (bare PCI, e.g. a Linux box without `nvidia.ko`) and a
remote `RemotePCIDevice` (macOS TinyGPU-over-Thunderbolt). Sites B/C/D clear MASTER whenever
`is_err_state`/hang fires, regardless of which. Reasons:
1. **Mirrors the existing idiom exactly.** `_early_ip_init` (`nvdev.py:121-127`) clears/sets MASTER
   unconditionally on both local and remote `pci_dev` — there is no local/remote branch there today.
   Adding one here for symmetry only would be an inconsistency, not a simplification.
2. **Correct on a local card too.** A local PCI device left bus-mastering after a fault can still DMA
   into stale/freed host mappings; nothing about that hazard is remote-specific. The DART/Thunderbolt
   IOMMU is what makes a *stray* DMA panic the host outright on macOS, but leaving MASTER on after a
   known fault is not a good idea on local hardware either.
3. **Free on the happy path.** The next client's `_early_ip_init` sets MASTER again unconditionally
   before doing anything else, local or remote — so clearing it here costs nothing even if the
   analysis were wrong for the local case.
4. `is_remote()` is a method on `NVDevice` (`ops_nv.py:648`), not on `PCIIface`/`NVDev` — using it at
   sites B/C would mean threading `self.dev.is_remote()` through, for a branch that changes nothing.

## 4. Step 3 finding: `device_fini()` had the *same* gap via a different trigger

Traced the call chain: `device.py:417` (`Device.finalize()`, called at process-lifetime end) →
`PCIIface.device_fini()` → `NVDev.fini()` (`nvdev.py:104-105`) → `for ip in [gsp, flcn]: ip.fini_hw()`
→ `NV_GSP.fini_hw()` = `rpc_unloading_guest_driver()` (`support/nv/ip.py:518`), a GSP **RPC call**
that needs GSP alive and able to DMA a response into the host sysmem queue to complete.

**Finding:** pre-fix, `fini()` never touched bus-master. So a **normal process exit** (no `pkill`
involved at all) that reaches `device_fini()` while `is_err_state=True` left MASTER set; when the
client's socket to the server later closes (any process exit does this), the server's DEXT tears
down that client's mappings exactly as it does on `pkill` — same panic precondition, just reached via
a quiet exit instead of an explicit kill. This is a real, distinct path to T4.36, not just symmetry
homework — fixed at `ops_nv.py:615-620`:
```python
def device_fini(self):
  self.dev_impl.fini()
  if self.dev_impl.is_err_state:
    self.pci_dev.write_config_flush(pci.PCI_COMMAND, self.pci_dev.read_config(pci.PCI_COMMAND, 2) & ~pci.PCI_COMMAND_MASTER, 2)
```
Gated on `is_err_state` (not unconditional) to keep the change scoped to the documented failure mode
— a clean shutdown's `fini()` behavior is otherwise untouched, matching this file's existing style of
touching only what a specific finding requires.

**Caution, addressed: upstream PR #16536** ("Disable bus mastering on AMD PCIe device teardown",
CLOSED) cleared MASTER in AMD's `fini()` and broke CI (Mac pytest, UsbGPU Benchmark, both tinybox red
benchmarks); nimlgen flagged the benchmark failures and geohot closed it. This is the same shape of
change as this section, so it needs a direct answer, not just a passing mention:
- **Root cause of #16536's break, read from `amdev.py:168-181`:** AMD's boot path has a `partial_boot`
  fast path (`regSCRATCH_REG7` already matches → skip a full reset) that wraps the *entire*
  clear/reset/set-MASTER sequence inside `if not self.partial_boot:` — so on the (common, since
  benchmarks reinit the same device repeatedly) fast path, **nothing ever re-enables MASTER** if a
  prior `fini()` had cleared it. An unconditional clear in `fini()` plus a warm-restart path that
  skips re-enabling it is exactly the combination that leaves the device permanently unusable.
- **Why this fix doesn't share that failure mode:** (1) gating strictly on `is_err_state` means the
  clear **never fires on a normal/clean teardown at all** — proven by
  `test_device_fini_leaves_bus_master_when_clean` (§8) — so every currently-green CI/benchmark run
  (all of which exit clean) sees zero behavior change, unlike #16536's unconditional clear which fired
  on every teardown. (2) Unlike AMD, **NV's `_early_ip_init` has no partial-boot-style fast path**:
  `NVDev.__init__` (`nvdev.py:91-96`) calls `_early_ip_init()` unconditionally on every construction,
  and the WPR2-check inside it only gates whether an *extra* hard reset happens — the final
  `write_config_flush(..., | PCI_COMMAND_MASTER, ...)` (`nvdev.py:127`) sits **outside** that `if`, so
  it runs unconditionally on every single new client regardless of what a previous session's `fini()`
  left behind. There is no NV code path that constructs a device and skips re-enabling MASTER, so a
  next client always recovers a bus-mastering-clear left by this fix. (3) `MOCKIface` has no
  `device_fini` at all (only `PCIIface` defines it, confirmed by grep over `ops_nv.py:405-593` — zero
  matches), so no mock/CI path exercises this code today either way; the mock-NV gate (§9) passing
  unchanged is expected, not just observed.
- Net: this satisfies "gate the clear on that flag only" for the one case task step 3 asked about, and
  is not the "normal-teardown change" #16536 was (and that is explicitly out of scope here).

**Ordering, same reasoning as on_device_hang (§5):** the clear happens *after* `self.dev_impl.fini()`
returns, not before — `fini_hw()`'s RPC still needs bus-mastering GSP to answer.

## 5. Ordering: clear MASTER *after* any RPC that still needs GSP alive

`sleep()` has nothing after the `is_err_state` check but the raise, so clear-then-raise there is
direct. `on_device_hang()` and `device_fini()` both call GSP RPCs (`rm_control` for the SM/MMU fault
report; `rpc_unloading_guest_driver` inside `fini_hw()`) that need the GPU to still be able to DMA a
response back — clearing MASTER *before* those would likely hang or fail them (bus-master disabled
means the PCIe endpoint can no longer master any transaction upstream, including the DMA write GSP
needs to answer an RPC). So in both, the clear is the **last thing before raising/returning**, after
whatever GSP RPC that call already needed to make. This is also why `on_device_hang`'s clear sits
right before its final `raise`, not at the top of the function.

## 6. Idempotency

No special-casing needed: `cmd & ~PCI_COMMAND_MASTER` on an already-clear bit is a no-op by
construction, so calling any of the three sites twice in a row is naturally safe — proven by
`test_pciiface_sleep_clear_is_idempotent`.

## 10. Hardware verification check (for the main session)

`PCI_COMMAND` offset is `0x04`; `PCI_COMMAND_MASTER` bit value is `0x4` (bit 2) — both from
`tinygrad/runtime/autogen/pci.py:12,16`. From a live `PCIIface` instance (e.g. `dev.iface` where
`dev` is the `NVDevice`, or the iface object directly if held elsewhere):

```python
from tinygrad.runtime.autogen import pci
cmd = dev.iface.pci_dev.read_config(pci.PCI_COMMAND, 2)
print(f"PCI_COMMAND=0x{cmd:04x}  MASTER={'SET' if cmd & pci.PCI_COMMAND_MASTER else 'CLEAR'}")
```
Expect `MASTER=CLEAR` immediately after a `Device fault detected` / hang exception is observed, and
`MASTER=SET` again only after a **fresh client's** `_early_ip_init` has run (its own print,
`"WPR2 is up. Issuing a full reset."`, or just re-checking this after constructing a new `NVDevice`,
confirms the reset path ran).
