## 2. What the memory is (per token and fixed) — the numbers that decide any window
- KV cache 18 KB/token (int4) / 35 (int8); plus ~12 KB/token of JIT-planned score arena per prefill family (2 slots × H=24 × chunk 32 × fp32).
- Fixed: weights (file size) + GDN states (~0.15 GB) + the vision encoder on METAL (not the card).
- **JIT families: three (greedy text, sampled text, image prompt), ~1.5 GB each at 131k — 4.6 GB — unless `JIT_SHARED_ARENA=1`** (T4.105,
  validated bit-identical): then one arena ≈ 1.6 GB, and greedy/sampled share one family anyway (temperature is decided inside the graph).
- Usable card memory ≈ 23.2 GB (every OOM lands there). A serving setting = weights + fixed + families + ctx × per-token ≤ 23.2.

## 3. The kernels (all on integration/t6, PR #44)
- `NV_CUSTOM_QUANT=1`: dp4a decode gemv (tokens ≤ 4) + `NV_WMMA` tensor-core prefill gemm, both for Q4_0/Q4_1/Q8_0/Q4_K/Q5_K/Q6_K/IQ4_XS/IQ4_NL/
  Q3_K/IQ3_XXS/IQ3_S (IQ2/Q2_K remnants stay generic). Fragment identity from the hardware warp lane (the lowerer splits a 32-wide LOCAL range
  by its div/mod usage; `test_llm_nv_gemm.py` pins the (4, 8) render); the gemm always reads a byte view of the packed weight.
- `GDN_NV_FUSED_DECODE=1`: the fused GDN scan serves decode. `nv_dense.py`: fp16 gemv for the small dense heads (copies made at load).
- `KQUANT_STAGE=0` (required on the card), `KV_INT4=1`, `STATE_CACHE_DEVICE=METAL`, `VISION_DEVICE=METAL`, `JIT_SHARED_ARENA=1` (recommended),
  `SDPA_HEAD_GROUPS` (0 = per-KV-head groups: score arena ÷ 4 at ~9 % prefill; off by default), T4.102's unroll budget in the optimizer.
- Tooling (durable copies in `~/Documents/tinygrad-bench-data/scripts/`, README there): deploy.sh, the device chains, ctx/serve-memory probes,
  the real-tensor validators, the WMMA probe + simulator; `prompts24.jsonl` + dumps beside them.

## 6. How Hermes ran on the XL @213k candidate (09-12 06:24 → 12:45) — the lessons

Source: the server request log (59 local requests), Hermes's `agent.log` (per-call in/out/latency, tool names, the fallback), the stream
log (sizes and sentence-repetition only), the unified log (jetsam). Content was not read. One Telegram session, a coding task (a web app):
turn 1 non-thinking (30 calls, 38 min, halted by Hermes's guardrail), turn 2 with `/reasoning high` (= template `xhigh`): 22 local calls
over 1 h 47 min, then the 12:27 emergency restart (T4.106) cut the 23rd call and Hermes finished the turn on DeepSeek.

**Speed is set by the FILLED context, and attention is the whole slope.** Fit over the 59 requests (gen tok/s is integer-rounded in the log):

| filled context | decode | prefill of new tokens | |
|---|---|---|---|
| 2k | 19 tok/s | 94 tok/s | the bench numbers |
| 20k | 7.5 | 36 | the 8.6k-token file write at 19k context took 20 min |
| 40k | 4.5 | 21 | |
| 60k | 3.2 | 15 | the last local calls |
| 100k / 200k (extrapolated) | 2.0 / 1.1 | 9.7 / 5.0 | the 213k window is not usable at these rates |

decode ≈ 44 ms + 4.5 ms per 1k context tokens; prefill ≈ 8.8 ms + 0.95 ms per 1k context tokens per new token. The GDN blocks are O(1) per
token, so the slope is the 16 attention layers reading the int4 KV (18 KB/token): 1.08 GB per decoded token at 60k in ~270 ms = ~4 GB/s
effective on a 936 GB/s card — the generic tinygrad decode-attention kernel (int4 dequant + full-length softmax) is ~200× off
bandwidth-bound, and prefill attention (57 ms/token at 60k) is similarly far from tensor-core rates. **→ T4.107** (split-KV
flash-decoding kernel for decode; T4.103b tiles for prefill). Until then the practical window is ~30k, whatever the file: Hermes's
compression threshold (65,536) should come down to ~32k, and "largest 4-bit context" is not a useful recipe criterion yet.

**What the 3.7-hour turn was spent on (turn 2):**
- 15.6 min: `/reasoning high` switched on between turns → the effort instruction changes the prompt's front → the whole 35.2k session
  re-prefilled cold (39 tok/s). Decide the reasoning level before a session starts.
- 10.4 min re-prefill + 15 min generation in one call: a mid-turn user message (a steer at 09:53) became the new "last user query", so
  Qwen's template dropped the earlier think blocks → the prompt diverged at the 35.2k boundary snapshot → 13.1k tokens re-prefilled at
  21 tok/s. Structural: every user message during a thinking tool loop costs a re-prefill of the loop's non-think tokens; the boundary
  snapshot (T4.96) is what keeps it partial. Tool-loop snapshots were skipped ("boundary pinned", 2 GB cap) but would not have helped —
  the divergence is before them.
- 97 min: the last local call at 61.6k context — 3 tok/s nominal, ~1.5 effective: T4.106's leak put the Mac into memory pressure 3 min
  in (jetsam idle-kill sweeps at 10:53, 11:2x, 11:5x, 12:2x); it had produced ~16k chars of reasoning (181 sentences, 0 % repeated —
  the loop breaker never fired all day; 0–2 % repetition in the seven big think blocks) when the restart cut it. `xhigh` = 64k budget:
  at 3 tok/s a single think block can run for hours. `/reasoning medium` (16k cap) is the right default at these speeds.
- 18 min on DeepSeek V4 Flash: the restart's connection errors → two retries → a compression attempt (also on the dead local server) →
  `fallback_providers[0]` (deepseek-v4-flash): 99 cloud calls, 12:27 → 12:45, context 48k → 119k+, **9.99 M input tokens (nearly all
  cache hits) + 57k output**, two terminal commands blocked waiting for approval (one timed out after 300 s), then a 3,080-char answer
  from DeepSeek. Restarting the server while Hermes is mid-turn hands the turn to the cloud silently. Options: drop the cloud entry from
  `fallback_providers` (keep only the local 35B), or accept it and never restart with Hermes live except in an emergency.
