# T4.43 — QCOM compile-server has the T4.31 bug shape too

Branch `task/T4.43-qcom-server-cache` off fork master `a770d485a` (post T4.31/T4.33 sync).

## Verdict: bug confirmed, fixed

`compiler_qcom.py`'s non-aarch64 path has the **identical** bug shape T4.31 fixed in
`compiler_cuda.py`'s OSX docker path: `QCOMCompiler.__init__` spawned a fresh, persistent
compile-server `subprocess.Popen` on every construction, uncached. `Renderer.__reduce__`
(`tinygrad/renderer/__init__.py:79`, unchanged) reconstructs the `Renderer` — and with it a fresh
`Compiler` — via `self.__class__(self.target)` on every multiprocessing unpickle, and `QCOMCLRenderer.
__init__` (`tinygrad/renderer/cstyle.py:594-598`) unconditionally does `self.compiler =
QCOMCompiler(target.arch)`. So every BEAM candidate handed to a worker
(`codegen/opt/search.py`'s `pool.imap_unordered`, one task per candidate — T4.31's mechanism, not
re-verified here since it's unchanged) would unpickle a fresh `QCOMCLRenderer`, construct a fresh
`QCOMCompiler`, and spawn its own qemu/docker server, used once and abandoned.

## Why this is *not* an aarch64-only edge case

`platform.machine() == "aarch64"` is Linux-arm64 naming. **Darwin arm64 (this Mac, and any Apple
Silicon dev box) reports `'arm64'`**, not `'aarch64'` — confirmed by direct interpreter check
(`platform.machine()` → `'arm64'` on this worktree's host). x86_64 hosts obviously aren't
`'aarch64'` either. So the buggy branch is not a rare cross-compile corner: it's the path every
non-Linux-aarch64 dev/CI machine takes, symmetric with T4.31's OSX-docker path (which is similarly
"every Mac", not an edge case).

## Mechanism, file:line (pre-fix)

- `tinygrad/runtime/support/compiler_qcom.py:18` (pre-fix) — `self.compiler_process =
  self.server(cmd, arch)` called directly in `__init__`, no cache, no key. Every construction spawns.
- `tinygrad/runtime/support/compiler_qcom.py:25` — `__reduce__` returns `QCOMCompiler, (self.arch,)`
  — a plain reconstruct-on-unpickle, same shape `Renderer.__reduce__` assumes is cheap for every
  backend except the out-of-process compiler ones.
- `tinygrad/renderer/cstyle.py:594-598` — `QCOMCLRenderer.__init__` constructs `QCOMCompiler(target.
  arch)` fresh every time, wiring the per-construction spawn into every `Renderer` reconstruction.
- `tinygrad/runtime/support/compiler_qcom.py:35` (pre-fix) — `compile()` called `self.compile_server
  (src, self.compiler_process)` directly, so a dead transport (`CompileTransportError`, already
  raised correctly by the *shared* `Compiler.compile_server` in `device.py` — T4.31's device.py half
  of the fix is generic and QCOM already benefited from it) was never retried; it just propagated and
  killed the run.
- `tinygrad/runtime/support/compiler_qcom.py:23` (pre-fix) — `__del__` did `self.compiler_process.
  kill()` unconditionally on non-aarch64. This is a *second*, independent bug once a cache is added:
  a GC'd `QCOMCompiler` instance (e.g. the previous BEAM candidate's, dropped after use) would kill
  the shared cached process out from under the next candidate's reuse, silently degrading the fix
  back toward one-spawn-per-candidate. NVRTCCompiler/NVPTXCompiler never had this problem because
  they never defined `__del__` at all — reaping is atexit-only, by design (T4.31).

## The fix

Moved T4.31's `_server_cache`/`_reap_servers`/`_get_server`/`_compile_with_retry` out of
`compiler_cuda.py` into a new shared module, **`tinygrad/runtime/support/compiler_server_cache.py`**
— the logic was already 100% generic (duck-typed on `compiler.server()`/`.compile_server()`/
`.compiler_process`, keyed on `(type(compiler).__name__, arch, args)`), so this is a pure move, zero
behavior change for the CUDA side. Both `compiler_cuda.py` and `compiler_qcom.py` now import
`_get_server`/`_compile_with_retry` from it; the cache dict itself is one process-global object
shared by both compiler families (harmless — the key's `type(compiler).__name__` component already
partitions CUDA entries from QCOM entries).

`compiler_qcom.py` changes:
- `__init__` (non-aarch64): stores the computed command as `self.compiler_cmd`, then calls
  `_get_server(self, self.compiler_cmd, arch)` instead of `self.server(...)` directly.
- `compile()` (non-aarch64): calls `_compile_with_retry(self, src, self.compiler_cmd, self.arch)`
  instead of `self.compile_server(...)` directly — now gets the one-retry-on-dead-transport recovery
  for free, matching CUDA.
- `__del__`: non-aarch64 branch dropped entirely (was `self.compiler_process.kill()`). The aarch64
  branch (`llvm_qcom.cl_compiler_destroy_llvm_instance`, unrelated native-LLVM-instance cleanup, not
  a subprocess) is untouched. Reaping the cached subprocess is now atexit-only, via
  `compiler_server_cache.py`'s `_reap_servers`, exactly mirroring NVRTCCompiler/NVPTXCompiler.

The aarch64 branch (real hardware, native LLVM bindings) is untouched byte-for-byte — it never
touches `server()`/`compile_server()`/`compiler_process` at all.
