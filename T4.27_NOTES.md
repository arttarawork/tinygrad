# T4.27 — beam_search's silent fallback to the unoptimized seed kernel

Host-side codegen fix, no GPU touched (NULL device only). Branch `task/T4.27-beam-silent-fallback`
off `0a8924772` (T4.15, same branch — T4.15 root-caused this as a documented FINDING but explicitly
did not fix it; this task is that fix).

## 1. Mechanism, confirmed from the code (matches T4.15's finding exactly, one refinement)

`beam_search` (`tinygrad/codegen/opt/search.py`, pre-fix line numbers) seeds `beam = [(s, inf)]` — `s`
being the caller's untouched, zero-opts Scheduler (`postrange.py:336-337`, `apply_opts`'s `beam>=1`
branch at `postrange.py:340-345`). Each round:

- `_try_compile` (was lines 58-80) wraps compile in `try/except RuntimeError: ...` then
  `except Exception as e: if BEAM_STRICT_MODE: raise e` else drop — **any exception, of any class,
  becomes a bare `None`** unless `BEAM_STRICT_MODE` is set (and that env var only guards the second
  clause, not the first). The caller only ever sees `if proc is None: continue` (was line 138)  —
  no exception object, no class name, nothing.
- If **every** candidate in a round fails this way, `timed` stays empty, so `opts = sorted(timed,...)`
  is `[]`. The only branch that would advance `beam` past its current value,
  `elif len(opts) > 0 and opts[0][1] < beam[0][1]: beam = opts[:1]` (was line 168), is guarded by
  `len(opts) > 0` and never fires. `exiting` is forced `True` by the same emptiness
  (`exiting = len(opts) == 0 or ...`), so the `while` loop ends this round. Net effect for a
  round-1 wipeout: `beam` is returned exactly as seeded — **the literal untouched `s` object**,
  `applied_opts == []`, score `inf` — with zero output at any verbosity short of reading the return
  value yourself.
- **Refinement over T4.15's finding:** I initially assumed "score stuck at `inf`" was the right
  final-return test, but `_time_program` can itself return `[math.inf]*cnt` on an `AssertionError`
  (line 50) for a candidate that *did* compile — so a real, distinct-from-`s` candidate can legally
  end up in `opts` with score `inf` too. The correct test for "we're about to hand back the untouched
  seed" is object identity, `beam[0][0] is s`, not `beam[0][1] == float("inf")`. Used identity in the
  fix (search.py:187).
- Confirmed empirically (not just read) both ends of this on the `NULL` device (real renderer/compile
  pipeline, zero hardware, `_alloc` is a no-op) — pre-fix, a fake `_try_compile` that fails every
  candidate makes `beam_search` return `result is s` with **zero captured stdout** at any DEBUG level;
  post-fix, the same setup prints two WARNINGs and returns a kernel with real `hand_coded_optimizations`
  opts applied. Script output preserved in this session's transcript, not committed (ad hoc, matches
  T4.15's own convention of not committing throwaway repro scripts).
- Downstream (`postrange.apply_opts`, the diskcache) **cannot** distinguish "beam searched and found
  no improving move" from "beam gave up": both produce `applied_opts == []` (or, pre-fix, a cached
  empty list once `diskcache_put` persists it — a related pre-existing footgun, see §4).

## 2. What changed (`tinygrad/codegen/opt/search.py`, +24/-7)

1. `_try_compile` now returns a 3-tuple `(idx, result|None, exc_class_name|None)` instead of 2. The
   exception class is captured in **both** except clauses (RuntimeError and the wholesale `Exception`
   catch) — `type(e).__name__`, a plain string, chosen specifically because `_try_compile` runs inside
   a `multiprocessing` worker (`engine/worker.py`, `SpawnContext`) and a string is guaranteed picklable
   where an arbitrary exception instance (e.g. one wrapping a ctypes/driver handle) might not be.
2. Per-round loud diagnostic: when a round has real candidates but zero survive
   (`if candidates and not opts`), print a `colored(..., "red")` WARNING (matching this file's own
   `colored`/DEBUG-print idiom, not gated behind `DEBUG`/`BEAM_DEBUG` — gating it would reproduce the
   exact invisibility bug this fixes, since T4.15 found the existing `BEAM_DEBUG` print lives
   downstream of the cache-hit early-return and never fires on the failure path anyway). Reports
   candidates tried, total failed, and a `Counter` of exception-class → count (compile failures *and*
   timing `RuntimeError`s both feed the same counter — both are genuine per-candidate failures; the
   intentional `seen_libs` dedup and 1000x-compute filters are deliberately excluded from "failed"
   since they're not errors).
3. Final-return diagnostic + fallback (`beam[0][0] is s and candidates`): if the search never moved off
   the seed *and* there was something to try (excludes the benign "kernel has no tunable axes at all"
   case, which would trivially have `candidates == []` on every round and is not a bug), print a second
   WARNING and apply `hand_coded_optimizations()` — the exact function `postrange.apply_opts` already
   calls when `beam == 0` (`postrange.py:346-350`) — instead of returning the bare seed. This makes the
   worst case "as good as not having asked for BEAM" instead of "worse than not having asked."

## 3. What I deliberately did NOT change, and why

- **Did not narrow the `except Exception` in `_try_compile` to specific classes.** The task flagged
  this as worth evaluating. T4.15's own dock evidence names a real non-`RuntimeError` case
  (`BrokenPipeError` from the flaky Docker/NVRTC transport) that legitimately means "this candidate
  didn't work, try another" and must stay non-fatal — but I have no way to enumerate the *complete*
  legitimate set from this environment: I'm barred from touching the GPU/dock this task is scoped
  around (the one place the flakiness is proven to occur), and this file is shared by every backend
  (CPU/CLANG/LLVM/AMD/NV/METAL/WEBGPU), each with its own compiler-toolchain failure modes I can't
  exercise here either. Guessing the "safe to propagate" set risks turning a transient flake on some
  backend I've never run into a hard crash of the entire search, which is a worse regression than the
  silent-fallback bug this task fixes. Decoupled the two concerns instead: keep the broad catch (so
  no backend gets newly fragile), but make every swallowed class visible via the `Counter` (§2.2) so
  the *next* run has the evidence to justify narrowing it. **Recommendation for whoever picks this
  up:** run with the new WARNING's `Counter` output on a real flaky/slow backend for a while first;
  if `KernelOptError`/`TimeoutException`/transport errors (`BrokenPipeError`, `ConnectionError`,
  `subprocess.CalledProcessError`) dominate and nothing else ever shows up, narrowing to exactly those
  becomes a data-backed change instead of a guess.
- **Did not restructure the search loop, the diskcache key, or `BEAM_STRICT_MODE`'s asymmetric scope**
  (it guards only the second `except`, not the first, pre-existing and out of scope here).
- **Did not fix the diskcache poisoning a transient flake permanently** — `diskcache_put` (last line)
  unconditionally caches whatever `beam[0][0].applied_opts` ends up being, same as before. Falling back
  to `hand_coded_optimizations()` makes the *cached* result strictly better than an empty list, but a
  one-off compile-server hiccup still permanently caches "hand-coded opts" instead of retrying real
  BEAM next time, since the cache key (`ast`/`amt`/`device`/`suffix`) has no notion of "this was a
  degraded result." Fixing that needs a cache-key/versioning change — bigger, riskier, and not what
  this task asked for; flagging it as a follow-on.

## 4. Tests — `test/opt/test_beam_search.py` (new module; none existed under `test/opt/` before)

Both build a real ast/Scheduler on `Device["NULL"]` (real renderer + "compiler", zero hardware, the
allocator's `_alloc` is a no-op) so `get_kernel_actions`/`_try_compile`'s real code runs, then
monkeypatch `search_mod._try_compile` to control which candidates "fail" without needing real
(flaky) hardware:

- `test_all_candidates_fail_warns_and_falls_back`: every candidate fails with a **non-RuntimeError**
  class (`BrokenPipeError`, chosen to mirror T4.15's actual dock evidence, not the easy
  already-was-caught case). Asserts both WARNINGs fire with the real candidate count and the
  exception class name in the text, and that the returned kernel matches
  `hand_coded_optimizations(s.copy())` exactly (not the untouched seed).
- `test_partial_failure_stays_quiet_and_still_optimizes`: first 2 of 6 candidates forced to fail
  (`RuntimeError`), the rest run through the **real** NULL compile/time path. Asserts no WARNING
  fires and BEAM still finds and returns a real, non-empty `applied_opts`.

**Proven failing pre-fix**, two ways:
1. `git stash push -- tinygrad/codegen/opt/search.py` (keeping the new test file), reran: both tests
   fail — `ValueError: too many values to unpack (expected 2, got 3)` at the old
   `for i, proc in (...)` line, because the pre-fix code has no concept of the 3-tuple/exception-class
   return at all.
2. Direct mechanism repro against the same stashed (pre-fix) code, using the *old* 2-tuple fake
   `_try_compile` signature so it actually runs instead of erroring: captured stdout is the empty
   string and `result is s` is `True` — i.e. the exact silent-seed-return bug, reproduced on demand,
   zero hardware. Restored the fix with `git stash pop` afterward.

## 6. PR-readiness verdict

**Ready to propose upstream as-is, pending Artur's go-ahead** (per the standing no-PR-without-go-ahead
policy). Diff is small (+24/-7 in one file, matches the T4.14/T4.17 bar), touches only
`codegen/opt/search.py`, doesn't restructure the loop, reuses an existing sibling code path
(`hand_coded_optimizations`) rather than inventing new behavior, and the fallback is a strict
improvement (never worse than pre-fix; falls back to exactly what non-BEAM runs already do). The one
genuinely opinionated part — silently changing what `BEAM` returns in the failure case instead of only
adding logging — is called out explicitly above and in the commit for Artur to veto independently of
the diagnostics half if preferred; the diagnostics half (§2.1-2.2) has no behavioral downside at all
and would be worth landing even standalone.

**Worth reporting upstream independent of a PR, yes.** The bug is generic, not dock-specific: any
slow/flaky/OOM-prone compile backend (a busy shared build box, a remote compile server, a
resource-constrained CI runner) hits the exact same silent degradation, and the failure mode — BEAM
measuring as *worse than no BEAM at all* with zero diagnostic — is exactly the kind of thing that
erodes trust in the optimizer for reasons that have nothing to do with the search heuristics
themselves. It's also cheap for a maintainer to verify independent of hardware (the `NULL`-device
repro above, or literally the pre-fix mechanism check in §1, takes seconds).
