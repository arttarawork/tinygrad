## 0. Safety note: why the original validation run is implicated in panic 2

Mined from the surviving transcript (`~/.claude/projects/-Users-artur-Documents-tinygrad/d9cf3c0c-e9ed-4794-ba21-e3ea71b3dc79/subagents/agent-a2a7e6761f7d417e7.jsonl`) and verified against source in this tree:

The original agent's gate script (`t433_gates.sh`, recovered verbatim from the transcript's Write
tool-call — the on-disk copy in that session's scratchpad did not survive) ran its `unit` stage as
bare `PYTHONPATH=. python -m pytest test/unit -q` — **no `DEV=CPU`**. On this Mac, with no `DEV`
override, `Device.DEFAULT` resolves to `"METAL"`. `test/unit/test_llm_device_map.py:194,382` gate
two test classes with `@unittest.skipUnless(Device.DEFAULT == "METAL" and "NV" in
Device.get_available_devices(), ...)`. This decorator is evaluated at class-definition time, i.e.
at module import/collection time — so merely *collecting* `test/unit` (not running any NV test) is
enough. Verified from source (`tinygrad/device.py` in this tree): `Device.get_available_devices()`
constructs each backend to check availability; `NVDevice.ifaces = [NVKIface, PCIIface, MOCKIface]`
and `Compiled._select_iface`'s "never fallback to mock ifaces" filter means that when nobody asked
for an explicit `MOCK` interface, `MOCKIface` is excluded from the candidates and the real
`NVKIface`→`PCIIface` path is tried — `PCIIface` is the real macOS TinyGPU/PCI hardware path. So an
unguarded `pytest test/unit -q` run on this Mac attempts to open the real eGPU purely as a
side effect of collection, independent of `DEV.DEFAULT` doing anything special (its ONLY
protection is short-circuiting the `and` in the skip-guard's own condition).

This is confirmed, not speculative: HANDOFF_2026-08-26.md §2's reconstructed timeline shows the
**baseline** ("pre") run of this exact same unguarded script *also* hit this path at 11:57:31 EDT
("T4.33's baseline gate run probes NV (test_llm_device_map.py:194 at collection) against the
wedged-session server → spawns a new server") — before the merge even existed — and it is the
**post-merge** run of the identically-unguarded script that coincided with panic 2 at 12:06:34
(started ~12:05:45, "reaches the same NV probe within seconds"). **The danger was in the gate
script's missing `DEV=CPU`, not anything specific to the merged code.** Both the pre and post
invocations opened real NV hardware; the post one is the one that landed inside the panic window,
most likely because the pre-run's spawn left a stale/faulted server in place (T4.38-class leak)
that combined with T4.35's own 12:00:30 fresh-client reset to create the multi-server precondition
T4.40 names as necessary for the DART panic.

**This re-run enforces `DEV=CPU` on every single invocation without exception** (verified from
source before running anything: `tinygrad/test/unit/test_nv.py`, `test/opt/`, `test/backend/`, and
`test/test_tiny.py` contain zero unconditional `Device["NV"]`/`get_available_devices()` calls — the
*only* landmine in this whole surface is the two decorators above, and `DEV=CPU` makes
`Device.DEFAULT != "METAL"`, which short-circuits both). `test/device/test_hcq.py` is never run
except under the verified-safe `DEV=MOCK+NV:PTX` mock recipe (see §1).

**Operational lesson for future tripwire checks**: `pgrep -fl "TinyGPU.*server" | wc -l` overcounts
when a *different, concurrently-running* agent's own shell command contains that search string as
literal text (its own embedded safety check) — that other process's multi-line `-c` script argv has
embedded newlines, which `wc -l` counts as extra "matches". Hit live during this validation (see
§1 baseline `after-backend` tripwire): 1 real other-agent process (`tinygrad-t440a` worktree,
running its own gate script) counted as "6". Fixed in this run's tripwire by counting PIDs via bare
`pgrep -f` (always one numeric PID per line, immune to embedded newlines) and confirming each PID's
*actual* command path contains `/Applications/TinyGPU.app` via `ps -p <pid> -o command=` before
treating it as a real trip. No real TinyGPU.app server process was seen at any point in this
validation (confirmed via `ps aux | grep -i TinyGPU.app`, zero hits, both before this run and at the
false-positive moment).
