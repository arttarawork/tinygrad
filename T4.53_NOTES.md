# T4.53 — storm-culprit kernel identified, mechanism traced, NV-only deny-combo guard shipped

Base: `40b229288` (the validated `beam-diag` tree, F1/F2/F3 from T4.48 present). Worktree
`/Users/artur/Documents/tinygrad-t453`, branch `task/T4.53-storm-culprit`.

## TL;DR

The faulting candidate is **not** the DeltaNet-scan kernel T4.34 originally suspected. It's the
**MoE expert-weight gather** — `ExpertWeights.__call__`'s `self.weight[sel]` fancy-index at
`tinygrad/llm/model.py:50` (this checkout) — compiled into a kernel that does a 256-way (one per
MoE expert, GGUF-confirmed `qwen35moe.expert_count = 256`) linear scan to find the selected
expert's slab, then reads a 176 MiB (184,549,376-byte) raw quantized-weight buffer at an address
built from that scan result. The exact same 6-opt combo — `[LOCAL(1,16), GROUP(2,0), UNROLL(2,0),
UNROLL(2,4), UPCAST(1,2), GROUP(1,0)]` — reproduced the identical fault 2/2 independent runs
(T4.50, tonight). The opt-combo's defining structural feature: it turns **two independent reduce
axes** of the same kernel into GROUP_REDUCE (shared-memory cross-thread reductions), one of which
is itself a remnant of an axis already split by UNROLL. Static analysis of the generated address
arithmetic did not find a provable overflow (see "Code inspection" — the bound is exact, not
loose). Given that, the shipped fix is a **deny-combo guard** (NV-only, ~4 lines, fake-tested
failing-then-passing): reject a 2nd independent GROUP_REDUCE axis on NV.

## 1. Instrumentation (committed)

`tinygrad/codegen/opt/search.py`: `BEAM_LAUNCH_LOG` env-gated launch log, off by default.
- New module constant `BEAM_LAUNCH_LOG = getenv("BEAM_LAUNCH_LOG", 0)`.
- `_time_program` prints `LAUNCH {time.time():.3f} {name}` right before the candidate's actual GPU
  launch, when the flag is set. `name` was a dead kwarg (no call site ever passed it, always
  defaulted to `"test"`) — reused rather than adding a new parameter.
- The call site in `beam_search` builds `name` only when the flag is on (`X if BEAM_LAUNCH_LOG
  else "test"` — the expensive side never evaluates when off, so the hot path is unaffected):
  `f"{s.ast.key.hex()[:12]} {s.colored_shape()} {candidates[i].applied_opts}"` — a short AST-id
  (structural hash of the *pre-opt* kernel, stable across all candidates/rounds of that one
  kernel), the kernel's original shape (recognizable at a glance, and doubles as a stronger
  identity check than the hash alone), and this candidate's opts.

This prints once per candidate, immediately before its GPU launch+wait — so the last N lines
before an abort name the last N candidates actually launched, resolving T4.50's "may be an
earlier one" uncertainty by construction.

## 3. Kernel identification (GPU-free, per the brief)

`s.ast.key` turned out to be **device-tagged**, not portable across devices — Tensors in
`model.py` are created with an explicit `device=` from the start (e.g. `Tensor.zeros(...,
device=x.device)`), so the same logical kernel gets a different structural hash per device. A
known-safe NV kernel hash (`157815dd11ee`) confirmed this: it does not appear anywhere in an
equivalent Metal run. Fell back to **shape-signature matching** instead (same original
`colored_shape()`, which is renderer/device-independent): a `DEV=METAL` run of the identical CLI
command (`JITBEAM=1 BEAM_LAUNCH_LOG=1 --benchmark 2`) found kernel `e01e10a5b4fd` with the
identical original shape `8 2048 2 4 2 32` (2 GLOBAL + 4 REDUCE). `DEV=NULL` was tried first per
the brief's suggestion but can't drive this repro: its allocator/copyin/copyout are all no-ops, so
even GGUF header parsing (which round-trips real bytes through the Buffer/Tensor machinery) fails
before any kernel is reached — Metal was the practical GPU-free (NV-free) substitute.

Reconstructed the exact candidate GPU-free: a small script
(`/private/tmp/.../scratchpad/t453_regen.py`) monkeypatches `search_mod.beam_search` to intercept
the Scheduler once its shape matches the target, applies the exact 6 opts from the fault via
`Scheduler.apply_opt()` (bypassing search — same Scheduler/opts the brief asks for), and dumps the
real `to_program()` output (Metal source, uop count) before raising to stop the run early. All 6
opts applied cleanly (no `KernelOptError`) — the candidate is legal per every existing check, on
both NV and Metal. Final uop count: **2697** (below T4.34's cited 4362-9409 range for the
DeltaNet-scan candidates — another data point that this is a different kernel).

The regenerated Metal source (`kernel void r_8_64_16_2_8_2_2_4_4(...)`) immediately named it:
```c
device float* data0_16384, device float* data1_4096, device int* data2_256,
device float* data3_8388608, device unsigned char* data4_184549376, device float* data5_8388608
...
int alu0 = (gidx1+248);
int alu3 = ((val0.y!=alu0)?0:1);
int alu4 = ((val0.z!=alu0)?alu3:2);
... [253 more sequentially-dependent ternaries, one per data2[] slot] ...
int alu257 = ((val63.w!=alu0)?alu256:255);
int alu258 = (<256-way OR of val_i.{x,y,z,w}==alu0>) ? alu257 : 0;   // "which of 256 experts is this?"
```
`data2_256` is a 256-int table; the 255-deep ternary chain plus the explicit 256-way OR-guard is a
linear search for "which slot equals my target", clamped to `0` if nothing matches. This is
GGUF-confirmed: `qwen35moe.expert_count = 256` (read directly from the model's KV metadata), and
`720896 * 256 = 184,549,376` exactly equals `data4`'s size. **This is `ExpertWeights.__call__`'s
`self.weight[sel]` gather** (`tinygrad/llm/model.py:48-51`, this checkout — CLAUDE.md's existing
`model.py:27,129` reference for the same `.contiguous()`-guarded MoE expert path is from a later
commit on `memory`; this T4.53 branch is pinned at the older `40b229288`, hence the line drift):
tinygrad lowers the fancy-index `self.weight[sel]` into exactly this "compare against every
candidate, select on match" reduce, not a native gather. **T4.34's "Python-unrolled loop makes an
irregular, hard-to-optimize kernel" instinct was directionally right — it's just the MoE routing
gather's unrolled 256-way compare, not `_attention`'s `for t in range(T_pad)` scan** (which, worth
noting, only ever runs 1 iteration here: `chunk_size` is forced to 1 for recurrent-block models on
non-AMD devices, `tinygrad/llm/model.py:761`, so `T_pad == 1` throughout this repro).

## 4. Opt-by-opt trace (what the fault candidate actually does to this kernel)

Applying the 6 opts in order (`t453_regen.py`'s trace, shape after each):
```
start                                          8 2048    2 4 2 32
LOCAL(1,16)    2048 -> 128(GLOBAL) x 16(LOCAL)  8  128 16 2 4 2 32
GROUP(2,0)     3rd REDUCE (the 2nd "2") -> GROUP_REDUCE, full size (no split)
UNROLL(2,0)    the "4" -> fully UNROLLed
UNROLL(2,4)    the "32" -> 8(REDUCE) x 4(UNROLL)
UPCAST(1,2)    128 -> 64(GLOBAL) x 2(UPCAST)
GROUP(1,0)     the "8" (remnant of the 32-split above!) -> GROUP_REDUCE, full size
final: GLOBAL(8) GLOBAL(64) LOCAL(16) UPCAST(2) GROUP_REDUCE(8) GROUP_REDUCE(2) REDUCE(2) UNROLL(4) UNROLL(4)
```
The load-bearing structural fact: **the kernel ends up with two separate GROUP_REDUCE axes from
two different original reduce dimensions**, and one of them (`GROUP(1,0)`'s target) is not a
"fresh" axis — it's the outer half of an axis `UNROLL(2,4)` had already split two steps earlier.
Two independent shared-memory cross-thread reductions, one nested behind an unroll-remnant, in one
kernel. `apply_opt`'s existing checks (divisibility via `shift_to`, the "no GROUP_REDUCE inside
another reduce" check, the shared-memory-size budget check) all pass — this combination is legal
by every check that exists today, on every backend tested.

## 5. Code inspection — the suspect read

The gather-selected expert index (`alu258`, bounded `[0,255]` by construction — the OR-guard
clamps a no-match to `0`, not to garbage) feeds the address into the 176 MiB quantized buffer:
```c
int alu270 = (gidx0*11264) + (lidx0*352) + (alu258*720896) + (Ridx1_0_0*176) + alu259;
// ... later, at the actual load:
unsigned char val64 = *(data4_184549376 + (alu270 + 16));   // ... up to +5779 seen at other loads
```
Worst-case address (every term at its declared max: `gidx0<=63`, `lidx0<=15`, `alu258<=255`,
`Ridx1_0_0<=1` — the `for` loop is literally `< 2` in the rendered source — `lidx2<=7` folded into
`alu259`, plus the largest literal offset actually used, `+5779`):
```
63*11264 + 15*352 + 255*720896 + 1*176 + 28 + 5779 = 184,549,375
```
Buffer size is 184,549,376 bytes (valid indices `[0, 184549375]`) — the computed worst case lands
**exactly on the last valid byte**, not past it. The within-one-expert-slab budget
(`gidx0*11264+lidx0*352+Ridx1_0_0*176+alu259+5779`, max `720,895`) is also an exact fit against
the 720,896-byte-per-expert slab size. This is a byte-perfect, not loose, bound — I could not find
a provable static overflow in this address expression by hand. Two honest caveats on that: (a) a
9-term affine expression checked by hand is exactly the kind of place a small error survives
review — I did not re-derive it a second way or write a solver to double-check; (b) more
importantly, **this is the Metal-rendered address expression, not NV's** — Metal (CStyle) and
NV's actual renderer (PTX or NAK, depending on config) are different code generators downstream of
the *same* opt-application logic (which I verified is renderer-agnostic and looks structurally
sound — `shift_to`'s substitution is a plain, exact index-preserving affine split). A bug specific
to how the NV backend lowers this same index math, or to how it allocates/offsets the *two*
independent shared-memory buffers for the two GROUP_REDUCEs, would be invisible to this
inspection and is not ruled out. Getting NV's actual PTX/SASS for this candidate would need
compiling on NV specifically, which is outside this task's DEV=NV grant (repro-only).

**Honest verdict: code looks structurally sound as far as GPU-free inspection can show; the live
hypothesis is an NV-renderer- or NV-shared-memory-allocation-specific bug in handling two
independent GROUP_REDUCE axes in one kernel (one of them an unroll-remnant), not a generic
UOp-level index bug.** This is a real, still-open unknown — flagged for whoever next has NV PTX
access.

## 6. Fix vs. guard: shipped a deny-combo guard

A generic fix isn't possible without confirming the exact mechanism (§5), which needs NV-side
compiler output this task wasn't scoped to collect. What's ~10 lines and directly justified by two
independent, byte-identical reproductions is a **deny-combo guard**: refuse a 2nd independent
GROUP_REDUCE axis on NV. `tinygrad/codegen/opt/postrange.py`, `apply_opt`'s existing GROUP/GROUPTOP
check block:
```python
check(self.ren is None or self.ren.target.device != "NV" or AxisType.GROUP_REDUCE not in self.axis_types,
      "T4.53: a 2nd independent GROUP_REDUCE axis is denied on NV (reproducibly faults silicon)")
```
Deliberately **not** a blanket "only one GROUP ever" rule: the existing test
`test_local_and_grouped_reduce` (`test/opt/test_kernel_opts.py`) already exercises
`[Opt(OptOps.GROUP, 0, 2)] * 4` — repeatedly re-splitting the *same* axis into nested
GROUP_REDUCEs, a different (and apparently fine) pattern from this fault's *two independent* axes
both grouped. The new check only fires once a GROUP_REDUCE from a prior opt already exists
*and* the renderer targets NV; every other backend (Metal, verified clean by the T4.50 flagship
run and by this task's own Metal regen) is untouched, and NV keeps every other opt combination
BEAM already explores.

Device-string gating on `self.ren.target.device` follows existing precedent in this exact function
(`check((self.ren is not None and self.ren.target.device == "DSP") or amt <= 16, ...)` a few lines
up, for UPCAST).

**Scope of what this removes from NV's search space.** A denied opt doesn't error the search: it
raises `KernelOptError`, the exact same exception every other illegal opt in this function already
raises (bad divisibility, GROUP-inside-a-reduce, shared-mem budget, ...), and `get_kernel_actions`
(`search.py`) already catches `KernelOptError` per-action and simply excludes it from that round's
candidate set (`except KernelOptError: pass`) — this is the established "narrow the search, don't
break it" path, not new failure handling. Concretely the guard removes: for any kernel that (a)
has ≥2 independent (non-nested) REDUCE axes to begin with — most kernels don't; a plain matmul or
elementwise+single-reduce kernel is never affected — and (b) has already had one of them grouped,
BEAM loses the option to *also* group a second one on NV specifically. It keeps every other lever
(LOCAL, UPCAST, UNROLL, repeated-regroup-of-the-*same*-axis per `test_local_and_grouped_reduce`,
GROUP on a *different* single axis alone) and every other backend's full search space. Given the
fault is 2/2-reproducible on exactly this two-independent-GROUP_REDUCE shape and the affected
kernel population is small (this MoE expert-gather kernel is the only one seen so far with the
right structure), trading that narrow slice of NV search space for not faulting the device is an
easy call until §5's root cause is confirmed and a more surgical fix (or a clean bill of health)
can replace this guard.

**On T4.34: refuted, not just "a different data point."** T4.34's structural suspicion named the
DeltaNet-scan kernels (`_attention`'s `for t in range(T_pad)` loop, candidate uop counts
4362-9409) as the storm's likely source. This repro's evidence directly contradicts that for the
actual reproduced candidate: the faulting kernel is `ExpertWeights.__call__`'s `self.weight[sel]`
MoE gather (§3), its uop count under the fault opts is 2697 (outside T4.34's cited range), and
`T_pad == 1` throughout this repro (chunk_size is forced to 1 for recurrent-block models off-AMD,
so the scan never actually unrolls beyond one step here) — there is no live mechanism by which the
DeltaNet scan could be this candidate. T4.34's *general* instinct (a Python-level-unrolled loop
produces an irregular kernel BEAM can misoptimize) was directionally right; it was aimed at the
wrong specific loop. Any doc/task row citing DeltaNet-scan as the storm suspect should be updated
to point at the MoE expert-gather instead, specifically for this reproduced candidate — DeltaNet's
own scan remains unexamined by this task (not cleared, just not implicated by what was reproduced
here) and would need its own repro if still suspected.

**Follow-up to file for the true renderer root cause.** A new task (`T4.54` or similar): take the
exact 6-opt candidate this task pinned (`bed36ea1e95e`/`e01e10a5b4fd`, shape `8 2048 2 4 2 32`,
opts `[LOCAL(1,16), GROUP(2,0), UNROLL(2,0), UNROLL(2,4), UPCAST(1,2), GROUP(1,0)]`) and, in a
dedicated NV compile-only session (no execution needed, so no fault risk — `to_program()` alone,
the same call this task's Metal regen script used, just pointed at NV's actual renderer), dump the
real PTX or NAK output and diff its shared-memory offset/barrier sequencing for the two
independent GROUP_REDUCE buffers against Metal's `threadgroup float buf2[512]` allocation (§5) —
specifically whether NV allocates/indexes the two reductions' shared memory regions with the same
"exact, non-overlapping" tightness this task found in Metal's byte-address arithmetic. That would
either confirm an NV-renderer-specific shared-memory bug (giving a precise, mechanism-level fix
that could subsume this guard) or clear the renderer, redirecting suspicion back to genuine silicon
behavior under this candidate's register/branch pressure (the 255-deep sequentially-dependent
ternary chain, §3).

**Fake-tested** (`test/opt/test_beam_search.py`, `TestSecondGroupReduceDeniedOnNV`, 2 new tests):
builds a real ast with two independent reduce axes (`a.sum(0) + b.sum(1)`, NULL device — no
hardware), applies opts through a bare `Renderer(target=Target(device="NV"))` — no live device
needed at all. `test_second_group_denied_on_nv`: 1st `GROUP` succeeds, 2nd raises
`KernelOptError`. `test_second_group_still_allowed_off_nv`: the identical sequence through
`Renderer(target=Target(device="METAL"))` (same `has_local` capability, different device) does
not raise — proves the guard is NV-only, not a capability regression. Verified both fail without
the fix, pass with it (`git stash` the one-line diff, rerun, restore).
