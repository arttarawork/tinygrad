## 2. The structural guarantee

`compile_cached` (device.py:316-321) has **no exception handling of its own**. `lib = self.compile(src)`
(line 319) is a plain assignment from a function call; if `self.compile(src)` raises anything, Python
never reaches line 320 (`diskcache_put`) — the exception propagates straight out of `compile_cached` to
its caller. This means: **`diskcache_put` can only ever be reached with whatever `self.compile(src)`
returned on a normal (non-raising) return.** The entire question reduces to: can any transport flake make
`self.compile(src)` — all the way down through `NVRTCCompiler.compile` (compiler_cuda.py:84-85) →
`_compile_with_retry` (compiler_cuda.py:31-38) → `compile_server` (device.py:326-338) for the OSX docker
path — return successfully with a wrong/truncated/empty value, instead of raising?

### 3a. "Garbage length" is not a real failure mode here

For the length prefix itself to be *wrong-but-well-formed* (not short — a short read is case 1/2 above),
the bytes actually delivered would have to differ from the bytes actually written, i.e. genuine
bit-level corruption in transit. Both transports in play are OS pipes (`subprocess.PIPE`, the OSX docker
path) — POSIX pipes deliver bytes reliably, in order, uncorrupted; they can fragment a message into
multiple `read()`s (handled by `_read_exactly`) or terminate early via EOF (handled, case 2), but they do
not flip bits. There is no length-prefix-corruption vector to test against this transport; it would only
be a concern over an actually lossy medium (raw TCP without a checksum layer, wireless), which this code
never uses. No test added for this row; it's ruled out by the transport's own delivery guarantee, not by
inspection of tinygrad code.

### 3b. The write-side gap — real, but not a caching risk (flagged, not fixed)

`compile_server`'s outbound write (device.py:331) —
`unwrap(proc.stdin).write(struct.pack("I", len(src.encode())) + src.encode())` — never checks
`.write()`'s return value or loops to send the remainder. `proc.stdin` is opened with `bufsize=0`
(device.py:325, `Compiler.server`), which per the Python subprocess docs makes it a raw, unbuffered
stream whose `.write()` can legitimately return short for large payloads (source files large enough to
exceed the pipe's buffer — T4.14's own commit message cites 623KB sources as realistic). T4.14 fixed
exactly this asymmetry on the **read** side; the **write** side was not in its scope and remains
unguarded.

This is real, but it cannot poison the cache, because the receiver blocks rather than proceeding with a
partial request. `compileserver.py`'s main loop (quoted in full in §1):
```
7     while (amt:=sys.stdin.buffer.read(4)):
8       try: lib = compiler.compile(sys.stdin.buffer.read(struct.unpack("I", amt)[0]).decode())
```
`sys.stdin.buffer` is a `BufferedReader` (T4.14's commit confirmed this empirically: "already loops
internally"). `BufferedReader.read(n)` blocks until it has assembled exactly `n` bytes or hit true EOF —
it does not return early just because the client's single `write()` call happened to flush less than the
full message. So a truncated client write leaves the **server** blocked inside `.read(struct.unpack(...))`
at compileserver.py:8 waiting for bytes that will never arrive (the client, having already "successfully"
returned from its short `.write()`, moves straight on to *reading* a reply rather than sending more), and
the **client** blocked inside `_read_exactly` (device.py:332) waiting for a reply the server can never
produce. The round trip deadlocks; `compile_server` never returns (good or bad); `compile()` never
returns; `compile_cached`'s line 319 assignment never completes; `diskcache_put` (device.py:320) is never
reached. A hang is a real, separate defect (a `DEV=NV` OSX-docker run could wedge indefinitely on a large
kernel with no diagnostic), but it structurally cannot be the "poisoned success" or "silently truncated
blob" this task is checking for — nothing is ever written anywhere. Not exercised as a live test (a test
that actually hangs is not something to add to a suite); the argument above is a full trace of both sides
of the protocol, not a guess. Left flagged for a future task, out of scope here — fixing it would be a
hang/robustness fix, unrelated to cache correctness, and this task's own scope is the caching question
specifically.

## 4. The retry path in detail (`compiler_cuda.py:31-38`, quoted in full in §1)

On a `CompileTransportError` (line 35), the retry evicts the cache entry (line 36) and calls
`_get_server(...)` (line 37), which — since the entry was just popped — unconditionally calls
`compiler.server(cmd, arch, *args)` (compiler_cuda.py:28), i.e. `subprocess.Popen(...)` again
(device.py:323-325): a **brand-new** process with its own, independent stdin/stdout file descriptors. The
retried `compile_server(src, ...)` call (compiler_cuda.py:38) reads exclusively from this new pipe; there
is no mechanism by which bytes left sitting in the old (abandoned) process's pipe could be read as part
of the new round trip — they're different file descriptors entirely. So a successful retry's payload is
provably that second, independent round trip's own bytes, never a mix with the first (failed) attempt. If
the retried attempt *also* raises `CompileTransportError`, `_compile_with_retry` does not catch it a
second time (no loop, no third attempt, line 38 is a bare `return` with no surrounding `try`) — it
propagates straight out, and by §2's structural guarantee, `compile_cached` never reaches `diskcache_put`.
`test_retry_success_is_cached_with_correct_payload` and `test_retry_exhausted_not_cached` (added, §6) pin
both halves of this.

**Related, out-of-scope finding (flagged, not fixed):** compiler_cuda.py:36 (`_server_cache.pop(...)`)
evicts the dead entry from the cache dict but never calls `.kill()`/`.terminate()` on the evicted `proc`.
If the old process is not actually dead (e.g. the docker CLI client is alive but the container inside
died, or the death was pipe-level only), it leaks until `atexit`'s `_reap_servers`
(compiler_cuda.py:20-23) runs at process exit. This is a resource leak in the same family T4.31 already
fixed for the happy path, not a cache-correctness issue — orthogonal to this task's mandate, not touched.

## 5. Verdict

**Exonerated. No source change made.** Every path from a transport flake to `Compiler.compile(src)`'s
return value either (a) raises `CompileTransportError`/`CompileError`, which `compile_cached` cannot
catch and route around `diskcache_put` (§2), or (b) deadlocks before either side produces anything (§3b),
which also never reaches `diskcache_put`. The two `CompileError`-family exceptions are exhaustive over
every way `compile_server`'s three I/O operations (write, read-length, read-body) can fail: `OSError`
(dead pipe) and `CompileError` (`_read_exactly`'s own EOF-detection, plus the pre-existing empty-reply
case) are the only exception types the wire protocol can produce, and both are explicitly caught and
reclassified at device.py:334-336. There is no fourth way for `self.compile(src)` to return without either
completing a full, byte-exact round trip or raising.

- `TestCompileCachedRetryPath`: `test_retry_success_is_cached_with_correct_payload` (dead-then-healthy

production code changed. `test_eof_mid_body_not_cached` specifically pins what would have been a real gap
pre-T4.14: before that fix, `compile_server` used `.read(size)` directly (no loop), so a short/EOF read on

would then have happily cached. That pre-T4.14 shape is exactly the window this task was asked to
re-check for; T4.14 (and T4.31's additional hardening) already closed it, which is what this test now pins
against a regression.
