# T4.46 — make BEAM candidate-failure causes distinguishable

Host-side codegen diagnosability fix, no GPU touched (`NULL` device only, `DEV=CPU` throughout).
Branch `task/T4.46-beam-failure-names` off fork master `7ca254099` (carries T4.27; does **not**
carry T4.39, which lives unmerged on `task/T4.39-beam-inf-cache`).

## 1. Mechanism

`_try_compile` (`tinygrad/codegen/opt/search.py`) reports a swallowed candidate failure back to
`beam_search` as a plain string, `type(e).__name__` (T4.27). `beam_search` tallies those strings into
a `Counter[str]` and prints them verbatim in its WARNING line. Before this fix, three causes fed that
Counter:

1. **The `BEAM_TIMEOUT_SEC` SIGALRM.** `timeout_handler` raised `TimeoutException`, a bespoke
   `class TimeoutException(Exception): pass` — **not a `RuntimeError`**. This is the one part of the
   task's framing that turned out to be inaccurate and worth stating precisely: a timeout was already
   named distinctly from `RuntimeError` in the Counter (confirmed empirically below — pre-fix it shows
   as `{'TimeoutException': 1}`, never `{'RuntimeError': ...}`). But because it isn't a `RuntimeError`,
   it skipped `_try_compile`'s `except RuntimeError` branch entirely and fell into the generic
   `except Exception` branch instead — a real, separate bug: under `BEAM_STRICT_MODE` a timeout was
   (and, see below, no longer is) re-raised and crashed the worker, while the uop cap and every other
   `RuntimeError` never did, and a timeout never got the `except RuntimeError` branch's
   `DEBUG >= 4: traceback.print_exc()` tracing.
2. **The uop cap.** `raise RuntimeError("too many uops")` — indistinguishable from cause 3 by name.
3. **Genuine runtime/compile errors** — also plain `RuntimeError` in every backend that raises one.

So the double failure was: (1) vs. (2)/(3) were already distinguishable by name but wrongly split
across exception hierarchies (a latent `BEAM_STRICT_MODE`/tracing asymmetry), while (2) and (3) were
genuinely indistinguishable from each other. Tonight's `{'RuntimeError': 21}` wipeout was case (2)
and/or (3) conflated; a real timeout in the same round would separately have shown as
`TimeoutException` and not been part of that number at all — which is exactly why "diagnosing that it
was actually the 10s timeout took extra instrumentation" (a human has to know `TimeoutException` isn't
mentioned anywhere in the printed name, so scanning for the word "timeout" or "RuntimeError" alone
doesn't find it).

## 2. Fix (`tinygrad/codegen/opt/search.py`, +10/-4)

Two module-level classes, both `RuntimeError` subclasses so `_try_compile`'s existing
`except RuntimeError as e: exc_name = type(e).__name__` keeps catching them unchanged (verified: no
edit needed to that branch, or to `except Exception`, or to `BEAM_STRICT_MODE`'s gating expression):

```python
class BeamCompileTimeout(RuntimeError): pass  # SIGALRM fired before to_program finished
class BeamUopLimit(RuntimeError): pass        # candidate's uop count >= BEAM_UOPS_MAX
```

`timeout_handler` now raises `BeamCompileTimeout()` (replacing `TimeoutException`, which had exactly
one producer and zero other references anywhere in the repo — `grep -rn "TimeoutException"` outside
this file returns nothing, so this is a straight rename, not an added alias). The uop-cap site now
raises `BeamUopLimit("too many uops")` (same message, same call site, only the class changed).

**Side effect worth flagging, not hidden:** moving the timeout from `Exception` to `RuntimeError`
does change *which* `except` branch catches it — from `except Exception` to `except RuntimeError`.
That's the point (the task explicitly asked for a `RuntimeError` subclass so "the existing
`except RuntimeError` catches both subclasses"), but it also folds in the two behaviors that clause
carries: a timeout is no longer re-raised under `BEAM_STRICT_MODE` (previously it always was,
regardless of the flag's original "catch compile flakes, not timeouts" intent — arguably this fix
*corrects* an inconsistency rather than introducing one, since the uop cap was never re-raised under
strict mode either), and a timeout now gets `traceback.print_exc()` at `DEBUG>=4` like every other
`RuntimeError` (previously never printed via this path). No gating logic or env var was added or
changed to preserve or suppress this — it's an inherent, one-line consequence of the class hierarchy
change the task asked for, called out here per the task's own "verify that" instruction rather than
adjusted around.

`timeout_handler` has exactly one call site (`_try_compile`'s own `signal.signal` registration) and
`BEAM_TIMEOUT_SEC`/`BEAM_UOPS_MAX` are read nowhere else in the repo (`grep -rn` across all of
`tinygrad/`, `test/`, `extra/` confirms it) — the change is fully local to `search.py`, no STOP
condition triggered.

## 3. Tests — `test/opt/test_beam_search.py` (extends T4.27's module; its 2 existing tests untouched)

New `TestBeamFailureCauseNames`, same real hardware-free `NULL`-device `_build_seed()` as T4.27, real
`beam_search()`/`_try_compile()` (not fully swapped out like T4.27's own tests) so the new exception
classes actually get raised and actually flow through the real WARNING/Counter path:

- `test_uop_cap_surfaces_beam_uop_limit`: forces `BEAM_UOPS_MAX=1` and asserts `"BeamUopLimit"` (and
  not `"RuntimeError"`) in the captured WARNING text.
- `test_alarm_timeout_surfaces_beam_compile_timeout`: forces `BEAM_TIMEOUT_SEC=1`, restricts the round
  to exactly one candidate (`get_kernel_actions` monkeypatched to return one), and monkeypatches
  `to_program` to `time.sleep(2)` — the SIGALRM at 1s must interrupt the sleep before it returns.
  Skips via `self.skipTest` if `signal.alarm` is unavailable. Asserts `"BeamCompileTimeout"` (and not
  `"TimeoutException"`) in the captured WARNING text. Costs ~1s wall time (one forced alarm), not 10s.

**Why forcing via env var directly doesn't work, and what these tests do instead:** `getenv()`
(`tinygrad/helpers.py`) is `@functools.cache`'d process-wide, and `BEAM_TIMEOUT_SEC`/`BEAM_UOPS_MAX`
are read via bare `getenv(...)` calls, not `ContextVar`s — so `Context(BEAM_UOPS_MAX=1)` would raise
(no such `ContextVar` registered) and a raw `os.environ["BEAM_UOPS_MAX"] = "1"` would only take effect
if it happened to be the *first-ever* call to `getenv("BEAM_UOPS_MAX", 3000)` in the whole pytest
process — not reliable once T4.27's own `test_partial_failure_stays_quiet_and_still_optimizes` (which
calls the real `_try_compile`) has already run in the same session and cached the ambient default.
Confirmed by tracing `getenv`'s source, not assumed. Both new tests instead monkeypatch
`search_mod.getenv` itself (delegating every other key to the real one) — the same "patch the name
`search.py` actually looks up" idiom T4.27 uses for `_try_compile` and T4.39 uses for
`diskcache_get`/`diskcache_put`. `CACHELEVEL=0` (T4.27's own pattern, simpler than T4.39's
`_FakeDiskCache` since neither new test cares about cache contents) keeps the real
`~/Library/Caches/tinygrad/cache.db` untouched — `diskcache_get`/`diskcache_put` are never called at
`CACHELEVEL=0`.

**Proven failing pre-fix**: `git stash push -- tinygrad/codegen/opt/search.py` (keeping both new tests
and T4.27's originals), reran against `7ca254099`'s `search.py`:

```

FAILED test/opt/test_beam_search.py::TestBeamFailureCauseNames::test_uop_cap_surfaces_beam_uop_limit
```

This is the direct, empirical confirmation of §1's finding: pre-fix, the timeout case shows
`TimeoutException`, never `RuntimeError` — the task's framing of "all three surface as RuntimeError"
undersold how the timeout was already partly distinguishable, just under an inconsistent, untraced
exception hierarchy. `git stash pop` restored the fix before the real gate run; T4.27's own 2 tests
passed both before and after (unaffected — their kernel never approaches either limit).
