# T4.52 — fast teardown on a faulted NV device

GPU-free. Fixes the ~490s / ~120-echo teardown storm T4.50 named ("storm anatomy SOLVED: '123 faults' =
1 real fault + 2 surfacing lines + 121 deterministic TEARDOWN ECHOES") by short-circuiting the one shared
function every echo funnels through.

## 1. Echo source trace (file:line, from real evidence)

Evidence: `t450_storm_validation.log` (session scratch) and `t429_nvcc_beam1.log`, both on
`tinygrad-beamdiag`/`tinygrad-t429`. Every one of the 61-121 per-run "Device fault detected" occurrences is the
**same** call chain, confirmed by grepping the 2 lines preceding every `RuntimeError: Device fault detected`
occurrence in `t450_storm_validation.log`: **all 61 land on `ops_nv.py:655`** (the only place that string is
constructed) as their deepest frame — e.g. `t450_storm_validation.log:45107-45134`:

```
LRUAllocator.free_cache()                      device.py:264-267   (or Buffer.__del__ / HCQCompiled.finalize's
  -> Allocator.free()                          device.py:233-234    atexit sweep -- all 3 entry points funnel
    -> HCQAllocatorBase._free()  [@suppress_finalizing]  hcq.py:552-556  <- THE SHARED CHOKE POINT
      -> for dev in buf.mapped_devs: dev.synchronize()  hcq.py:554
        -> HCQCompiled.synchronize()                     hcq.py:428-440
          -> self.timeline_signal.wait(...)               hcq.py:436
            -> HCQSignal.wait() -> self._sleep(...)        hcq.py:294
              -> NVSignal._sleep() -> iface.sleep(200)      ops_nv.py:47
                -> PCIIface.sleep(): drains stat_q,          ops_nv.py:631-637
                   is_err_state True -> raise RuntimeError("Device fault detected...")  ops_nv.py:655
```

`grep -c` confirms the shape: `t450_storm_validation.log` has exactly 61 `RuntimeError: Device fault detected`
occurrences, 61 matching `hcq.py:436, in synchronize` and 61 matching `ops_nv.py:655, in sleep` as the deepest
frame of each -- one raise per teardown-time `dev.synchronize()` call, always via the identical path. (A
`raise self.error_state` cache-hit at `hcq.py:429` would *also* show `ops_nv.py:655` as its deepest frame --
CPython prepends new frames to an already-raised exception's traceback rather than replacing them -- which is
why grepping "the line right before the message" alone can't distinguish a fresh raise from a cached re-raise;
it doesn't matter for the fix, since both paths are eliminated by not calling `synchronize()` at all.) The
"~121" figure in TASKS.md's T4.50/T4.52 rows is from a different (larger-cache) run; the mechanism is identical
and the exact count is just "however many buffers are still cached on the faulted device at fault time" --
confirmed non-viable to pin down further without live hardware, and not needed for the fix.

Only ONE choke point exists for all three teardown drivers the task named ("LRU `free_cache`->`_free`-
>`synchronize`, buffer `__del__`s, `HCQCompiled` finalize"): they are not three code paths, they are three
different **callers** of `Buffer.__del__` -> `Allocator.free` -> `HCQAllocatorBase._free`, which is the one
place that iterates `buf.mapped_devs` and calls `dev.synchronize()`. Fixing `_free` fixes all three callers at
once (ponytail: one guard in the shared function beats a guard in each caller).

## 2. The guard

`tinygrad/runtime/support/hcq.py`, +20/-1 (one new module-level helper + a 2-line change to `_free`'s loop):

```python
def _dev_already_faulted(dev) -> bool:
  return bool(getattr(getattr(getattr(dev, "iface", None), "dev_impl", None), "is_err_state", False))

  @suppress_finalizing
  def _free(self, buf:HCQBuffer, options:BufferSpec|None=None):
    for dev in buf.mapped_devs:
      if _dev_already_faulted(dev): continue
      dev.synchronize()
    for d, mb in buf.mappings.items(): d.allocator._unmap(mb)
    if hasattr(self, '_do_free'): self._do_free(buf, options)
```

**Why `is_err_state` and not `HCQCompiled.error_state`** (the existing per-device cached-exception field,
`hcq.py:424/429`): `error_state` is only set inside `HCQCompiled.synchronize()`'s own `except` block
(`hcq.py:437-438`). T4.47's RCA (and T4.48's F1, which aborts `beam_search` via a *duck-typed* `is_err_state`
probe that deliberately bypasses `HCQCompiled.synchronize()` -- `iface.sleep(0)`, never `dev.synchronize()`)
mean the fault is routinely known (`is_err_state` True) well before anything ever sets `error_state` on the
device object. Guarding on `error_state` would still let the *first* teardown buffer's `_free()` go through
the full raise (since `error_state` is still `None` at that point) -- failing the done-criterion "ZERO
per-buffer sync/free RPCs and zero echoes" on a fake device constructed with `is_err_state=True` up front.
Guarding on `is_err_state` (mirroring `codegen/opt/search.py`'s T4.48 `_device_faulted` duck-type, NV/AMD-only,
degrades to `False` -- never `AttributeError` -- for every other backend) gets the true zero.

**Why not also drain via `iface.sleep(0)` first** (as `_device_faulted` does, to catch a fault nobody has
discovered yet): that drain is itself a new per-buffer RPC. Adding it here would satisfy the fault case but
regress the *healthy* case -- a new, previously-nonexistent RPC on every buffer free of a perfectly healthy
device. `_free`'s guard is deliberately passive: it only ever reads a flag that something else already set.

**Why `_unmap`/`_do_free` still run unconditionally** (not skipped): read `PCIIfaceBase.free()`
(`system.py:281-284`) and `NVAllocator._do_free`/`_do_map` (`ops_nv.py:383,385`, both `self.dev.iface.free/map`)
-- these are local VA-space/mmap bookkeeping against the *client's* memory manager, never a GSP RPC. They are
safe and cheap to run on a faulted device, and today (pre-fix) they never even get reached on that path, since
the unconditional `dev.synchronize()` raises before the loop ever falls through to them -- so running them is a
strict improvement (real client-side cleanup instead of dead code), matching the task's suggested design
("frees only client-side bookkeeping instead of raising per buffer").

## 3. What stays loud (unchanged)

- **The first, not-yet-discovered fault.** `_dev_already_faulted` reads `is_err_state` passively; if nobody has
  drained the stat queue yet, it's `False`, the guard doesn't fire, `dev.synchronize()` runs exactly as before,
  and discovers + raises the fault through the untouched chain in §1. Covered by
  `test_free_still_raises_on_first_undiscovered_fault`.
- **`device_fini`/`fini()`'s single unload-RPC attempt and the T4.37/T4.40b MASTER clears**
  (`ops_nv.py:615-629`) -- not touched by this diff at all (zero lines changed in `ops_nv.py`). The `cmd 47`
  timeout the task mentions is that single attempt, already gated to run once; T4.37/T4.40b's existing
  `TestNVQuiesceOnFault`/`TestNVQuiesceOnInitFailure` suites (12 tests, all still passing, see §4) are the
  controls proving this.
- **T4.23's healthy-OOM behavior.** OOM is a distinct code path (`Allocator.alloc`/`_alloc` raising
  `MemoryError`, `device.py:228-232`), not `_free`. `_free` only runs when something is being freed (LRU
  eviction *of a healthy device*, GC, teardown) -- for a healthy device `is_err_state` is always `False`, so
  `_dev_already_faulted` is always `False`, so the loop body is byte-identical to pre-fix
  (`test_free_still_synchronizes_healthy_device`).
