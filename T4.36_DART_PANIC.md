# T4.36 — the 2026-08-26 01:15 DART kernel panic: analysis (GPU-free investigation, 2026-08-26 AM)

## What panicked
`panic(cpu 11): (dart-apciec2) AppleT8110DART.cpp:2183: REQUIRE failed` — task `kernel_task`, backtrace entirely in
`AppleT8110DART`/`IODARTFamily` (Apple Silicon's IOMMU for the PCIe controller behind the Thunderbolt eGPU tunnel;
`apciec2` = that controller). No TinyGPU / tinygrad frames. All other cores were idle. First panic in 58 days of uptime.
A DART `REQUIRE` in this driver fires when **a device issues a DMA to an IOVA the DART has no translation for**, i.e. the
3090 (or its GSP firmware) touched host memory that was not (or no longer) mapped for it. `kernelPanic.txt` has nothing
further (no fault IOVA / stream ID recorded); the unified-log tail from the panic minute was lost (normal for a panic);
TinyGPU keeps no log file; the killed agent's transcript did not survive the reboot.

## What was running
T4.29's first attempt: `Qwen3.6-35B-A3B-UD-Q3_K_XL` (16.85 GB, IQ mix) all-NV on `DEV=NV:NAK`. Its no-BEAM headline run
finished ~00:45; by 01:15 it was in the **`JITBEAM=1` fresh-search rung** — the same *qwen3.6 + BEAM search* family that in
T4.34 (hours earlier) produced a **reproducible GPU MMU-fault storm (109 faults, twice)**. The agent's brief carried this
project's standard fault protocol: *"Device fault → `pkill -f 'TinyGPU.*server'` → respawn → retry once."*

## Mechanism audit — every way the GPU can reach a host address, and whether it can go stale

## The mechanism (ranked #1, consistent with every observation)
1. BEAM-1 fresh search on qwen3.6 executes candidate kernels; one reads OOB → GPU MMU fault storm (T4.34 class). The GSP
   is now **DMAing fault events into its host-resident queues at high rate**.
2. The protocol says `pkill` the server. The DEXT tears down that client's DMA mappings — **the GSP's queues included** —
   while the GPU still has bus-master enabled and the GSP firmware is still running (WPR2 stays up; that is precisely why
   the next client prints "WPR2 is up. Issuing a full reset.").
3. Between the unmap and the next client's bus-master clear (seconds to minutes), the GSP DMAs a fault/RPC record into a
   now-unmapped IOVA → `AppleT8110DART ... REQUIRE failed` → **host panic**.
Why ~20 earlier `pkill`s were harmless: the GPU was quiescent (no in-flight GSP DMA) when killed. Why T4.34's two pkills
under fault did not panic: probabilistic — the window has to line up with a DMA. The third fault storm of the day lined up.
**The recovery protocol I wrote is the hazard.** It is not "the dock is flaky"; it is "we yank the IOMMU out from under a
running firmware."

## Suspects retained at lower rank
- **#2 T4.21 blob placement / T4.22 IQ trees**: first real-model use on this file at this moment, but neither touches host
  DMA mappings; they can only trigger the chain via GPU faults (which BEAM candidates already do). Not a DART mechanism.
- **#3 T4.25 residual server-side race**: two servers holding the device — a second server's teardown could unmap the
  first's memory. The flock fix (in master) makes this unlikely, but confirm exactly ONE server before any dock run.
- **Demoted: T4.18/T4.20 slabs** (never freed; nothing is ever unmapped client-side). **Refuted: T2.2 PTE batching.**

## Rules until fixed (in the RESUME banner)
1. **Never `pkill` the TinyGPU server while the GPU is in a fault state.** A wedged GPU with `Device fault detected` must be
   quiesced FIRST (clear bus-master) — or the machine may panic when the server dies.
2. **No BEAM search on the dock** (BEAM candidates are what fault the GPU) until T4.37 lands. No-BEAM runs on tiny models
   are the only sanctioned dock activity, and only after T4.32's smoke test.
3. Confirm exactly one TinyGPU server before any run.

## The fix — T4.37 (small, client-side, upstream-shaped) + one upstream issue
- **Quiesce on fault**: in the fault path (`PCIIface.sleep()` before raising, and `on_device_hang`), **clear PCI bus-master**
  (`write_config_flush(PCI_COMMAND, cmd & ~PCI_COMMAND_MASTER)`) so a faulted GPU cannot DMA anywhere; the next client's
  `_early_ip_init` already re-enables it around its reset. Mirrors AM's own pattern (`amdev.py:176-181`). ~4 lines.
- **Controlled recovery instead of `pkill`**: the client already has `RemoteCmd.RESET` (`system.py:413`, used by
  `_early_ip_init`). The recovery hint (T4.23) should name a client-side reset path (clear bus-master → `reset()` →
  re-init) rather than killing the server; never tear down mappings under a live GSP.
- **Upstream issue (tinygpu_releases, Artur's go)**: the DEXT should clear bus-master (or reset the device) *before*
  tearing down a client's DMA mappings on disconnect/server exit — the server currently lets a live GSP outlive its
  mappings, which can panic the host. Same ticket as the ~128-slot ceiling and the missing unmap verb.
- **T4.34 stays open** as the trigger (BEAM candidates faulting the GPU on this config) — with T4.37 in place it becomes a
  recoverable fault instead of a host panic, which is the precondition for investigating it safely.
